## Architecture Overview
FLAI is a self-hosted multimodal AI assistant running on a **single consumer NVIDIA GPU (8/12/16+ GB)**. It orchestrates multiple models (multimodal, reasoning, embedding, SD, LTX-Video, Wan 2.2 video) through a strict GPU queue with VRAM-aware scheduling.
  - **Entrypoint:** `app/__init__.py:create_app()` (Flask)
  - **Blueprints:** `app/routes/` — auth, chat, admin, queue, tts, messages, sessions, documents, backups, events, debug, rlm
  - **Modules:** `modules/` — base/router, multimodal, sd_cpp, cam, rag, audio, tts, slm, search, video, rlm
  - **Task progress stages:** `task_progress` SSE events drive localized status labels («Analyzing request...», «Searching documents...», «Searching web...», «Loading reasoning model...», «Thinking...»). `reasoning_thinking` is emitted via `status_callback` — both LLM backends fire it right after `POST /v1/chat/completions` returns (model loaded, generation starts), because the entire `reasoning_content` phase streams no content tokens. Labels live in `chat.html` TRANSLATIONS (`stage_*` msgids), stage→key map in `events.js:STAGE_LABEL_KEYS` (+ `STAGE_COUNTER_KEYS` for `results`/`chunks` counts); each indicator ticks elapsed seconds and one element per session is kept (phase chains cross task ids).
  - **Background tasks:** `app/tasks/` — `dry_load.py` (dry-load after admin save; also scheduled for context-only changes, with a context-aware rollback that restores `context_length`, and model swaps reverting to the **previous admin-chosen model** — never a hardcoded fallback model; without a rollback target the rollback refuses and leaves the config untouched), `health_monitor.py` (crash-loop watchdog; **skips its whole tick while `ResourceManager.is_gpu_busy()` is active** — SD, video, or an `ensure_vram_for` unload+wait cycle — or while a worker holds `_gpu_lock` (`RedisRequestQueue.is_gpu_task_active()`), because a health check spawned mid-wait respawns the model being unloaded and starves the VRAM wait; on repeated failures it **marks the module unhealthy** for 10 minutes and never swaps the model — a hardcoded fallback absent on disk once silently broke multimodal on a deployment). Fact extraction runs on the background queue (idle only, `memory_extract_task`, under `_gpu_lock`) on the resident multimodal model — the strict JSON schema in `prompts/{ru,en}/memory_extract.template` is parsed by `app/memory_facts.py` (questions, low confidence and duplicates rejected, at most 5 facts) and stored with `kind`/`confidence` in the SLM wrapper, which keeps them in its own SQLite because the daemon drops metadata; the extractor runs only when the message looks personal (`looks_personal()`). Recall injects up to 3 newest `kind=profile` facts always and other facts only above `SLM_MIN_RECALL_SCORE` (0.5) — measured before the change, 0 of 30 real messages produced a fact and recall returned image prompts at 0.63. `flask memory-report` shows the store and the injection, `flask memory-purge --source auto_import` removes the raw messages the history import stored, `flask memory-profile [--apply]` consolidates the facts into one block that leads every recall, and `flask memory-eval --dataset q.jsonl [--no-profile]` scores hit@k/MRR/injected facts. Automatic extraction is off on a CPU-only host (`SLM_AUTO_EXTRACT=auto`, one call is ~30 s of the chat model; `on`/`off` override); the explicit remember path works either way. Extraction is the lowest-priority job: `background_gate_open()` requires both user queues empty and no `memory_extract:interrupt` flag (refreshed by every chat/API request, TTL `MEMORY_EXTRACT_QUIET_S` = 45 s), and the extractor streams so it can abort between chunks and re-queue itself with nothing written (a short run is held back by the client's 1500-char loop guard and finishes atomically in ~3 s; the gate is what keeps it from starting during a conversation). The prompt language is detected from the message (`detect_language`), not the UI language — an English account answering in Russian extracted `[]` otherwise. Fact merge runs on background queue (CPU-only, no LLM). Both excluded from queue status display and user counter. SLM profiles are tied to user accounts: `userdb.delete_user()` GDPR-erases and removes the user's daemon profile via the wrapper's `/delete-profile` route (non-blocking, warning on failure).
  - **Background Tasks subsystem (v12.6):** long-running background jobs decomposed into checkpointed steps, executed at low priority (classes 3/4/5 derived from the user's service class 0/1/2, hidden from the admin panel) and **preempted by chat**. `app/tasks/executor.py` — one global daemon thread (agent loop: planner → executor → verifier) over `tasks`/`task_steps` in PostgreSQL; **one active task globally** (class asc, created_at asc; awaiting_user/frozen release the slot); the **gate** before each step = chat queues empty + `!ResourceManager.is_gpu_busy()` + no chat request within `TASK_QUIET_PERIOD_S` (60 s sliding window — every chat enqueue writes `task:last_chat_activity`); **abort inside a step** on any chat request: the hook in `app/queue.py` raises Redis `task:step_cancel:<step_id>` (TTL 3600), the runner polls it between stream chunks, the step dies `interrupted` and re-executes on resume; `TASK_TOTAL_BUDGET_S` (24 h) counts **pure execution** (every attempt incl. aborted/checkpoint/retries — waits never count), on expiry the task is `expired` with a final summary from the intermediate results. Direct steps (`llm`/`search`/`calculate`) run in-process via `runner.py` (no `_gpu_lock` — chat never waits); media sub-tasks (`image_gen`/`image_edit`/`video_gen`/`rlm`) go through the existing queue at the task's class with the **slow-worker gate guard** (deferred to Redis `task:deferred_subtasks` while the gate is closed, requeued when it opens) and one peek per executor cycle (`TASK_SUBTASK_POLL_CYCLES`, default 10, before a liveness check). Clarifying questions: `question` step → task `awaiting_user`, the answer is a `user_input` step linked by `parent_step_id`; the answered task returns to the front of selection and the previously running task goes back to `queued` with its step `interrupted` (`preempted`). Checkpoints: a verifier judges each step against `checkpoint_criteria`; failure → corrective retry with the mismatch description (≤`TASK_STEP_MAX_ATTEMPTS` = 3 total), then the step is `failed` and the task continues. Plan reviews run after information steps (`llm`/`rlm`/`rag`/`search`/`crawl`/`history`), failures/skips, fresh answers or an exhausted plan, and every `TASK_REPLAN_EVERY_N` ordinary media steps; growth is bounded by `TASK_MAX_REVISIONS` and `TASK_MAX_STEPS`. The continuity sheet is an internal guard (never a planner step); `continuity` is excluded from the planner capability list and both plan templates. Media verification returns `severity`/`repairable`/`score`: a repairable defect (extra/duplicated object, wrong text or time, a small detail) edits the current artifact before the next generation (`TASK_STEP_MAX_REPAIRS`, one edit after each of up to 3 generations, low strength), a new composition regenerates; when every attempt fails, all 3–6 candidates are ranked by `score` and the closest is kept as a «best effort» artifact. Full restart recovery from the DB (`_mark_interrupted_by_restart`). Internal API `app/routes/tasks.py` (`/api/tasks*`, owner-scoped, `⚠️ ` errors, stop = `task:cancelled:<id>` + immediate cancel for queued/frozen/awaiting_user, delete = cancel flag + status `cancelled` first then FK-cascade delete); SSE updates ride the shared per-user stream as `task_update` (`app/tasks/events.py`); UI = the Tasks tab between Documents and Sessions (`chat.html` + `app/static/js/chat-tasks.js`, task view is a mode of the chat main window keyed by `window.currentTaskId`, `isTaskViewActive()` guards the chat SSE render paths). `app/tasks/tools.py` TOOL_RUNNERS is the **skills seam**. Details → `docs/TASKS.md`; tests: `tests/test_tasks_*.py`.
  - **Video generation — two backends (v12.8):** `VIDEO_BACKEND=ltx|wan` selects one of two containers that answer the same contract (`POST /v1/video/generations`), so the queue, VRAM gate, image-to-video and UI are shared. **LTX** (default, `with-video`, `flai-ltxvideo`) — LTX-Video 2B 0.9.8 distilled, 8 steps, up to 10 s (768×512×240 @ 24 fps), measured peak 3057 MB; 8/10 GB cards are capped at 512×512×120. **Wan** (`with-video-wan`, the same `flai-sd` container as image generation) — Wan 2.2 TI2V 5B Turbo Q4_K_M (Apache-2.0), 4 steps, CFG 1.0, Euler, flow-shift 3.0, 5 s (832×480×121 @ 24 fps); measured **209 s** and **15 340 MB** card-wide on a 16 GB card. sd.cpp writes avi/webm only, so `sd_wrapper` converts to mp4 (h264) with the ffmpeg bundled in the image. Wan needs `--diffusion-model` (not `-m`, which fails with «get sd version from file failed»), frames must be `4n+1` and sides multiples of 32. VRAM: `app/vram_estimate.py:wan_video_vram_mb()` = 9 800 MB base (Q4 3.4 GB + VAE 0.4 + umt5 6.0 + CUDA context) + 0.1075 MB per latent unit with 16/4 strides; below 12 GB the umt5 encoder is streamed from RAM (`--offload-to-cpu`, `WAN_OFFLOAD_BELOW_VRAM_MB`) and the base drops by 6 GB. Preset chain 832×480×121 → 640×384×121 → 512×288×121 → 512×288×49 drives `_fit_wan_to_vram()` (never upscales) and the wrapper repeats the same step-down on OOM. Wan's own `sd-cli` is one-shot, but `unload_video_pipeline()` still unloads a resident LTX pipeline before the gate — a back-to-back LTX→Wan run otherwise leaves it loaded. The `flai-ltxvideo` base CUDA context survives `/v1/unload`; Wan's margin covers that residual. A longer request is cut to 121 frames with a localized notice (`apply_backend_limits`). The multimodal parameter prompt is backend-aware (`prompts/{ru,en}/create_video*.template` take `{video_model}`, `{video_res_*}` and `{video_frames_rule}`). Deploy: `--with-video` / `--with-video-wan`, mutually exclusive; the script writes `VIDEO_BACKEND` into `.env`. The key is also a saved admin setting: `VideoModule._refresh_backend()` re-reads backend, URL, model and timeout on every entry point, so switching in Admin → Settings applies without a restart. Wan's safety margin is 100 MB against a 500 MB desktop reserve (`vram_margin_mb`), because its estimate is a measured peak and already sits above it; LTX keeps 1 GB. Details → `docs/VIDEO.md`.
  - **LLM client:** `app/llamacpp_client.py` with `DirectLlamaBackend` and `LlamaSwapBackend`. Both `call()` and `chat()` accept `temperature` parameter. Router classification uses hardcoded `temperature=0.1`. **Router action-time & session micro-context (v12.1):** the router decides the action time first (`prompts/{ru,en}/base_text.template` «ACTION TIME» section): past-tense requests («we watched», «you showed earlier», «yesterday's snapshots») route to `[-HISTORY-]`, and the action categories (incl. camera — only a request to see the room state NOW) never capture questions about the past. `process_message()` accepts `recent_context` built by `BaseModule.build_router_context()`: the last `ROUTER_CONTEXT_MESSAGES` real messages via `get_session_recent_history()` in `app/db.py` (newest tail, generation-marker pair filter, current message excluded, each ≤`ROUTER_CONTEXT_MSG_CHARS` chars) plus up to `ROUTER_SLM_FACTS` SLM long-term facts; `_route_text_action()` in `app/queue.py` feeds it per request. Env: `ROUTER_CONTEXT_MESSAGES` (6) / `ROUTER_CONTEXT_MSG_CHARS` (240) / `ROUTER_SLM_FACTS` (2). `_translate_llama_swap_error()` translates llama-swap errors to user language. `_strip_generic_reasoning()` threshold `>=2` markers (synced with JS client), overbroad Russian patterns removed to prevent false positives; a structured reply (JSON object/array or a fenced code block — task plans, verifier verdicts) is exempt, and the streaming `_ReasoningStreamFilter` only ever strips the not-yet-emitted head, so a marker inside an answer cannot splice buffered text. **Repetition-loop detector:** streaming content goes through `_LoopGuard` (hold-back 1500 chars, `_repetition_cutoff` detects ≥3 equal-gap repetitions of the last-200-char block); both backends route in-loop content AND end-of-stream remainders (`_stream_buffer` + `_reasoning_stream` + `_loop_guard` flushes, in that order) through the guard so short answers are never dropped or reordered. Safety net `strip_repetition_loop()` in `app/queue.py:_process_reasoning_request()` cuts loops missed in streaming. Transient HTTP 502 from llama-swap (JIT load under reasoning `ttl=1s`) is retried up to 3 attempts in `chat_stream()` for the reasoning model, and `_process_reasoning_request()` retries once more and logs the body when the collected stream is a 502/«HTTP error» marker.
  - **Queue:** `app/queue.py:RedisRequestQueue` with **fast worker (CPU) and slow worker (GPU)**. Cancel support for all task types: image gen/edit (pre/post checks), video gen (background checker thread + container restart), streaming tasks (Redis flag). Reasoning tasks retry once when the model returns empty output (thinking-only after `_strip_thinking_tags()`) — `_process_reasoning_request()` loops the generation up to 2 attempts; the retry is fast because the first attempt already loaded the model just-in-time. No retry on task cancellation or on genuine LLM error strings.
  - **Per-request token usage counters:** `_process_request()` opens ONE usage account (`app/utils.py` begin/record/finish family) for every LLM task type; all LLM calls accumulate real `prompt_tokens`/`completion_tokens` via `_record_prompt_tokens()` (`app/llamacpp_client.py`); requeues carry the half-account in `request_data` (`request_id`/`usage_accum`/`submitted_at`); `_save_and_respond()` consumes it (full `submitted_at`-based duration, real totals into the result dict + `messages.prompt_tokens` column; `consume_usage=False` for the camera message pair). Header format `🔢 (↑out ↓in) tok` is rendered by `tokenStatsHTML()` (`chat-utils.js`) — only known sides are shown; the `window.displayMessage` wrapper (`chat-init.js`) must forward ALL 19 positional parameters (guard: `tests/test_js_signatures.py`).
  - **RLM deep analysis (v12.0):** an explicit "Deep analysis" toggle in chat routes a user question + selected documents to an `rlm_analysis` task type (slow worker, GPU). Documents are selected with the panel checkboxes (v12.5: one checkbox set shared with moves — `setDocChecked` mirrors `rlmSelectedDocs` in `chat-documents.js`, which syncs the hidden `#rlm-docs` multi-select); an attached image is described by the multimodal model (`describe_image_for_rlm()` in `modules/multimodal.py`, prompt `prompts/{ru,en}/rlm_image.template`) and the description joins the corpus as an `"Image (file_name)"` document — if the toggle cannot start (no documents and no image, or an image without a question) it is auto-unchecked and the request falls through to the normal send flow. `_process_rlm_task()` in `app/queue.py` orchestrates a reasoning actor loop (RLM_MAX_STEPS=18 as hard ceiling — the per-host allowance comes from the resource ladder in `modules/rlm.py:_resource_step_budget()` (24 GB+→18, 16 GB→12, 12 GB→10, 8 GB→8, CPU/<8 GB→6); the context window never cuts steps — `_obs_trunc_for_context()` compresses observations instead, down to an 800-char floor; RLM_TASK_TIMEOUT=0 auto-derives the wall-clock deadline from the step budget and platform (`_auto_task_timeout()`: GPU 120+90×steps, CPU 240+300×steps; `-1` disables; on expiry the run ends with the localized «task exceeded the time limit» error and the partial trace is saved), RLM_CODE_TIMEOUT=15 s, RLM_OBS_TRUNC=4000) over the corpus = selected documents (not RAG) + image description + web results (SearXNG, RLM_WEB_MAX_FETCHES=5); each step can call the sandboxed `python` tool, an `llm()` sub-call (RLM_SUB_MAX_TOKENS=1024), or `web_fetch(query)`, and `final(answer)` to exit. **Language & completeness guarantees:** the answer language is pinned via `{response_language}` (`prompts/{ru,en}/rlm.template`) plus localized `build_user_prompt()` and `broker_llm()` system prompt; the template forbids `final` before EVERY corpus file is examined, and a premature-`final` guard rejects a `final()` for a multi-file corpus when no `python` call has run yet (`sandbox.python_exec_count`) with a corrective tool message. **Tool-call leak guard (v12.5):** the final step offers ONLY the `final` tool (withholding all tools made Qwen3.6 print the call as plain text that reached the user as «internal dialogue»); `parse_leaked_tool_calls()` parses printed `<function=…><parameter=…>` blocks back into structured calls (leaked `final` → answer, leaked `python` → executes and continues), and a non-final tool executed on the last step grants one bounded final-only finalize call. The templates state `re`/`math` are already available (no `import`, no `lambda`) and failing code must be fixed, not repeated. **OOM protection:** the total corpus size is capped at `RLM_MAX_CORPUS_CHARS` (50_000_000 default) — an oversized corpus is rejected with a localized error before any GPU/VRAM work (never loaded into the forked sandbox). **The whole analysis is ONE GPU task:** it JIT-loads the resident reasoning model and holds the GPU lock for its full duration (`ResourceManager.mark_rlm_busy()` extends `is_gpu_busy()` so the v11.5 watchdog skips); the per-step reload cost (reasoning `ttl=1s`) is accepted, and the image description phase runs before it under `ensure_vram_for("multimodal")`. **Sandbox:** `app/rlm_sandbox.py` — isolated long-lived fork child; AST whitelist (`validate_code` with `FORBIDDEN_NODES`/`FORBIDDEN_NAMES`/`SAFE_BUILTINS`) + rlimits; no network/FS; `llm()`/`web_fetch()` are IPC callbacks to the parent (`SandboxBroker`). Per-step trace → Redis `rlm_trace:<task_id>`; stages `stage_rlm_*` with a collapsible "Deep analysis (N steps)" summary (the full trace is stored but not rendered yet); sub-model introspection results are NOT persisted to the DB. Env vars: `RLM_ENABLED`/`RLM_ACTOR_MODEL`/`RLM_MAX_STEPS`/`RLM_TASK_TIMEOUT`/`RLM_CODE_TIMEOUT`/`RLM_OBS_TRUNC`/`RLM_SUB_MAX_TOKENS`/`RLM_WEB_MAX_FETCHES`/`RLM_MAX_CORPUS_CHARS` (defaults in `app/config.py`).
  - **Multi-attachment chat (v12.4):** a chat message carries up to `MAX_CHAT_IMAGES` (4) images and/or ONE document. The frontend queues them in `attachedFiles[]` (`app/static/js/chat-init.js`, chips with a ≤38 px thumbnail for images and 🎤/🎵/📄 emoji otherwise; the legacy `attachedFile` single slot is only for the FIRST NON-IMAGE file — voice+image or a document plus images; images always stay in the multi-queue, which is why the legacy `fileData`/`filePath` render parameters are null for them). `POST /api/send_message` reads `getlist("file")` (first image keeps the legacy `file_data` columns; the rest travel in `request_data["images"]`), caps images with a localized 400, downscales every image to `MAX_IMAGE_SIZE_MULTI` (1024) when several are attached. **Every image is saved to disk** (`save_uploaded_file` per extra part; its relative path goes into the content JSON `file_path`), the optimistic render reads the queued images as base64 so they show before the POST returns (BOTH send branches pass `extraParts` — the legacy voice/doc slot reads the queued images too, otherwise voice/doc + images stayed invisible until F5), `displayMessage()` gates the extras split on the legacy `fileData`/`filePath` parameters (`legacyRendersFirst ? ## 🚨 CRITICAL RULES — NEVER VIOLATE

# 1. GPU Queue — Strict Serialization
  - **Tasks run strictly sequentially on GPU.** Both fast and slow workers MUST acquire `_gpu_lock` for any GPU task (chat, multimodal, embedding, reasoning).
  - **NEVER allow two GPU tasks to run concurrently.**
  - **VRAM is unconditionally cleaned between every GPU task.** After each task: unload all llama.cpp models, unload video pipeline, flush CUDA cache. No "predictive" logic. The `ensure_vram_for()` wait loop is self-healing (v11.5): a model reappearing in llama-swap `/running` during the wait was respawned externally and is re-unloaded (idempotent POST) on every poll instead of timing out.
  - **Degradation happens BEFORE model load, not after failure.** `compute_llamacpp_config()` iteratively reduces `n_gpu_layers` until the model fits; the layers left on the CPU are RAM (`estimate_cpu_ram_mb()` — weights + 400 MB, warning in the generated config when it exceeds free RAM minus 1 GB) and `ensure_vram_for()` refuses the load when that part does not fit at all (paging or an OOM kill otherwise). An already-loaded model is never rejected. If it doesn't fit even with 0 layers → return error, don't crash with OOM.
  - **RAG generation NEVER runs on the fast worker.** Fast worker does ONLY `rag.search()` (embedding + Qdrant). Answer generation via reasoning model happens EXCLUSIVELY on the slow worker via `_requeue_reasoning_task()`.
  - **RAG retrieval never drops a user document (file coverage):** the three reasoning-context builders call `rag.search(user_id, query, top_k=20, file_coverage=True)` — for every indexed document of the user missing from the semantic top-k, its best chunk is fetched (per-`doc_id` filter, `limit=1`) and appended (bounded by `coverage_max_files`, default 6) marked with `payload['coverage']=True`; coverage chunks bypass the relevance-threshold filter (`_process_rag_task`/`_process_rag_task_stream`) while the retrieved list itself is bounded by `top_k` plus coverage and trimmed by the prompt token budget — there is no fixed fragment cap — so a low-scoring contract still reaches the reasoning model instead of silently vanishing from the context.
  - **Retrieval defaults (v12.8, set by measurement):** `RAG_HYBRID_ENABLED=true` — the lexical half is now **BM25 over pymorphy lemmas** in PostgreSQL; `ts_rank_cd` had no IDF and length normalisation, so it needed a rarity gate, prefix queries for the stemmer and a title bonus, while BM25 carries all of it in the formula. Measured on two 30-question sets (generated and paraphrased): fused MRR 0.802/0.811 and nDCG@20 0.872 against 0.688/0.653 and 0.765/0.742 with the old full-text half; dense alone already scored 0.787/0.786 and a Qdrant-native BM25 without lemmatization was worst (0.569/0.500). `build_reasoning_messages()` sends a `system` turn (rules, role, date, skills) plus one `user` turn with the evidence first and the question last (`prompts/{ru,en}/reasoning.template` + `reasoning_user.template`); the rolling summary is read from `chat_sessions.summary` and refreshed by the idle `session_summary_task` instead of being generated inside the request (that path loaded the multimodal model mid-answer). `RAG_RERANK_ENABLED=false` — the CPU cross-encoder helps only a narrow 5-fragment window, lowers nDCG in a 20-fragment one and costs ~0.3 s. After reranking `rag.search()` keeps each chunk's cosine score, so the caller's absolute threshold still means the same thing.

# 🚫 Test Runs — Categorical Ban on RAM-Heavy Runs

**The host kills EVERY active opencode process as soon as system memory use (RAM + swap) exceeds 90 %.** A heavy run therefore does not merely slow the host down — it terminates this session mid-work. That kill is automatic, outside anyone's control, and it is not a warning: it is the end of the session.

**Running a test suite whose peak RAM you cannot bound is categorically forbidden.** Not "discouraged", not "ask first, then do it anyway": forbidden. This holds no matter how small the change looks or how confident you are in it.

Why it is absolute: a `pytest` run builds a fresh Flask app per test through the `client`/`test_app` fixtures (`create_app()` → `RedisRequestQueue` worker threads, Qdrant client, events publisher), so a multi-file suite holds hundreds of app instances over its lifetime (a two-file run was measured at 1.1 GiB available — one step from the watchdog). A `SIGKILL` from the memory watchdog hits *all* opencode processes at once.

- **NEVER start a heavy run without an explicit, command-specific approval from the user.** A general "run the tests" is NOT approval for a comprehensive suite. Name the exact command, the collected test count, and why it cannot be narrower — then wait for a "yes".
- **NEVER run the full `pytest` suite, `pytest -m unit` wholesale, or any multi-file suite as a routine check.** Those are merge-gate-scale runs; a merge gate is a decision the user makes, not a default.
- **NEVER run two pytest processes at the same time.** Two concurrent suites are how the host hit 1 GiB available with 49/49 GiB of swap on 2026-09-30.
- **NEVER background a suite and keep working.** The run keeps growing while you edit files and build more app instances, and you cannot watch its memory while you work.
- **NEVER run load tests (`tests/load/`), benchmarks, or anything whose memory use you have not measured.**
- **Default to the narrowest possible run:** one test file, or `::`/`-k` selections over exactly what changed — a handful of tests that finish in seconds. That is always the right first move.
- **Before ANY pytest invocation, state and verify the budget:** `pgrep -c pytest` must be `0` (a finished run can stay resident as a leaked non-daemon thread), `free -h` must show ≥ 4 GiB available, and you must know the collected test count. If you cannot state the peak RAM of the command, do not run it.
- **Stop immediately if available RAM drops below ~4 GiB or swap exceeds half used** — kill the pytest pids (`kill -9 <pid>`), then `free -h` to confirm recovery. A `SIGKILL`ed run leaves the working tree intact.
- **DB-backed suites skip cleanly without PostgreSQL; CI covers the rest.** When in doubt, do not run it — say what you did not verify and let the user decide.
