# Участие в разработке FLAI

Вклад в проект приветствуется. FLAI — это self-hosted, полностью локальная мультимодальная платформа ИИ: что именно она умеет, описано в [README-ru.md](README-ru.md), как устроена — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

**Перед началом:** прочитайте [AGENTS.md](AGENTS.md). Это конституция проекта — ключевые правила, жёсткие ограничения и точные команды. Каждое правило оттуда applies к вашему вкладу.

## Где работать

Разработка ведётся в пронумерованной основной ветке (`v12.3`, `v12.4`, …), а не в `master`. Именование веток:

- Новая функция: `features/v12.4-<краткое-описание>`
- Исправление: `fix/v12.4-<краткое-описание>`

Не коммитьте в `master` — он продвигается только через merge `--no-ff` из ветки разработки и только после ревью.

## Рабочий процесс

```bash
# 1. Форк и клонирование своего форка
git clone git@github.com:<ваш-форк>/flai.git
cd flai

# 2. Установка всех зависимостей для разработки
pip install -e ".[dev]"

# 3. Ветка от текущей основной ветки разработки
git checkout v12.4
git checkout -b features/v12.4-my-feature

# 4. Внесите изменение и проверьте его
ruff check .
mypy app/ modules/
pytest -m unit

# 5. Коммит, пуш, Pull Request в v12.4
git commit -m "feat(module): краткое описание изменения"
git push origin features/v12.4-my-feature
```

## Жёсткие ограничения

Это не обсуждается и будет отклонено на ревью:

1. **GPU-задачи выполняются строго последовательно.** Любая GPU-задача на быстром или медленном воркере обязана захватывать `_gpu_lock`. Две GPU-задачи никогда не работают одновременно. Между каждой GPU-задачей VRAM освобождается безусловно — никакой «упреждающей» логики.
2. **Никакого хардкода маршрутизации.** Классификация запросов идёт через LLM-роутер. Списки ключевых слов и Python-фильтры запросов, обходящие роутер, запрещены.
3. **Сообщения об ошибках для пользователей начинаются с `⚠️ `.** Формируйте их через `_build_error_response()`; никогда не возвращайте пользователю «сырое» `str(e)`.
4. **Никаких автономных коммитов.** Спрашивайте перед `git add`, `git commit`, `git push`, `git tag` и `git revert`.
5. **Резервная копия БД перед любой работой с ней** — изменения схемы, ручной SQL, миграции, импорты. Без исключений.
6. **Любая пользовательская строка переводится.** Оборачивайте её в `_()` и держите в актуальном состоянии оба файла `translations/{en,ru}/LC_MESSAGES/messages.po`.
7. **Новые зависимости должны иметь открытую лицензию** (MIT, BSD, Apache 2.0, MPL). Проприетарные и копилефт (GPL/AGPL) зависимости запрещены — проверьте лицензию до добавления.
8. **Паритет переводов для документации.** Каждый пользовательский или административный `docs/X.md` должен иметь пару `docs/X-ru.md` с той же структурой разделов, в том же коммите.

## Стиль кода

- Должны проходить `ruff check .` (длина строки 120) и `mypy app/ modules/`.
- Весь CSS лежит в `app/static/css/`, весь JS — в `app/static/js/`. Никаких inline-стилей и ссылок на CDN.
- Никаких отладочных print, закомментированных блоков, мёртвого кода и неиспользуемых файлов.
- Комментарии и сообщения журнала — на английском.
- Предпочитайте небольшие сфокусированные модули крупным. Если файл вырос за несколько сотен строк, это обычно сигнал разделить его.

## Как добавить функцию

1. Загляните в [docs/ROADMAP.md](docs/ROADMAP.md) — возможно, функция уже запланирована.
2. Прочитайте нужный файл из `docs/`, на который указывает Карта документации в `AGENTS.md`.
3. Сначала напишите тест, добейтесь его падения, затем — прохождения.
4. Обновите документацию: файл в `docs/`, отвечающий за тему, и README — только если изменение меняет возможности FLAI.
5. Добавьте запись в `CHANGELOG.md`, если изменение видно пользователю.

## Как добавить модель

Файлы моделей, команды скачивания и лицензии описаны в [docs/MODELS.md](docs/MODELS.md). Укажите размер, лицензию и инструкции по скачиванию. Убедитесь, что лицензия открытая.

## Как добавить ключ конфигурации

Переменные окружения описаны в [docs/CONFIGURATION.md](docs/CONFIGURATION.md). При добавлении, удалении или изменении ключа обновите **оба** файла — `.env` и `.env.example`: первый с реальными значениями, второй с плейсхолдерами. Порядок и структура разделов должны совпадать. Никогда не переносите секреты из `.env` в `.env.example`.

## Тесты

Полное руководство — в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md). Коротко:

```bash
pytest                  # всё
pytest -m unit          # только быстрые тесты
pytest -m "not slow"
pytest --cov=app --cov=modules --cov-report=html
```

На машине с ограниченной памятью запускайте один набор за раз: каждый прогон pytest создаёт новое Flask-приложение на тест, и два параллельных набора исчерпают оперативную память.
