# Архитектура — FLAI v12.4

В этом документе подробно описана внутренняя архитектура FLAI. Читайте его при изменении основной логики, очереди, модулей или потоков данных.

Критические правила и команды см. в корневом `AGENTS.md`.

> **v10.0 change:** Архитектура из двух моделей: мультимодальная (`Qwen3VL-8B-Instruct`, всегда резидентна, `ttl=0`, `preload: on_startup`) + модель рассуждений (по требованию, `ttl=1`). Отдельная «chat»-модель (`Qwen3-4B`) удалена. Мультимодальная = роутер LLM + текстовый чат + зрение (анализ и редактирование изображений). После задачи рассуждений `_preload_multimodal_sync()` синхронно перезагружает мультимодальную модель перед ответом. Управление VRAM упрощено: одновременно резидентна только одна модель llama.cpp (мультимодальная либо модель рассуждений), кроме эмбеддинга, который работает в отдельном слоте на CPU / при малом объёме VRAM. `ensure_vram_for_reasoning()` вытесняет мультимодальную модель; после рассуждений мультимодальная модель загружается обратно. `app/queue.py` больше не выгружает/загружает мультимодальную модель в сценариях с камерой или чатом с изображением (она всегда резидентна). `MODULE_TYPES` сокращён до `{multimodal, reasoning, embedding}`.

> **v9.1 change:** Модуль веб-поиска (`modules/search.py`) получил `_fetch_page_content()` — скачивает страницы с пустыми сниппетами SearXNG и извлекает читаемый текст через `trafilatura`. Позже доработано: `_fetch_page_content()` выполняется параллельно через `ThreadPoolExecutor` для коротких сниппетов (<300 символов), а формулировки инструкций смягчены с «USE ONLY THIS DATA» на «use this data as your primary source» в `modules/base.py` и в шаблонах промптов. `format_results_context()` обрезает каждый результат до 2 000 символов и динамически ограничивает общий объём через `get_search_context_limit()` (~30% эффективного бюджета, ~11 тыс. символов при контексте 16 тыс.). `_get_context_for_model()` при превышении бюджета возвращает RAG+SLM без истории (а не пустой результат). Зависит от `trafilatura>=2.0.0`. Тома Docker упрощены: `./app`, `./modules`, `./prompts` теперь монтируются как директории вместо 35 отдельных монтирований файлов; добавлен `PYTHONDONTWRITEBYTECODE=1`. (Явное `categories=general,news` затем было удалено — вызывало rate limiting у DuckDuckGo.)

## Публичный OpenAI-совместимый API (v12.3)

- **Идентификация по Bearer локальна для запроса.** `app/routes/api_v1.py:api_token_required` проверяет персональный для пользователя ключ (дайджест `SHA-256`, хранящийся в веб-панели ключей API) и заполняет `flask.g.api_user` (логин, класс сервиса, язык, стиль…). Блюпринт `/v1` никогда не читает и не пишет сессию Flask, не ставит cookie и не требует CSRF.
- **Это роутер возможностей, а не сервер моделей.** Сообщение чата сохраняется и ставится в очередь точно так же, как веб-сообщение, поэтому решает LLM-роутер, какая подсистема ответит (RAG/поиск/история/рассуждение/изображение/видео). `model`, `tools`, `response_format` и параметры сэмплирования принимаются и игнорируются там, где это указано в документации.
- **`app/api_bridge.py`** отвечает за разрешение сессии (указатели `api_conv:<login>:<sha1(user)>`, закрепление `metadata.session_id`), постановку в очередь, синхронное/SSE-ожидание и реестр владельцев задач в Redis (хэш `api:task:<id>` + отсортированный набор максимум на 500 ID на владельца, `REDIS_RESULT_TTL`); повторно поставленные дочерние задачи отслеживаются только при точном совпадении метаданных владения.
- **Всё тяжёлое проходит через существующую очередь.** Эмбеддинги и транскрипции выполняются как отдельные типы задач `api_*` на быстром воркере; изображения, видео, редактирование и RLM ставятся в очередь на медленном воркере со стандартной блокировкой GPU — генерация моделей никогда не выполняется внутри HTTP-запроса. Медиарезультаты отдаются с проверкой владельца через `GET /v1/flai/tasks/{task_id}/content` с ограничением по realpath внутри `UPLOAD_FOLDER`.
- **Лимиты и ошибки.** `API_RATE_LIMIT` применяется на владельца ключа (OpenAI 429 до постановки в очередь), `API_MAX_CONCURRENT_WAITS` ограничивает число синхронных ожиданий, `API_CORS_ORIGINS` задаёт белый список точных origins браузера, а любая ошибка использует локализованный конверт ошибок OpenAI, начинающийся с `⚠️ `. Полный контракт: `docs/API-ru.md`; тесты: `tests/test_api_v1_*.py`, `tests/test_api_tasks.py`, `tests/test_api_documents.py`, `tests/test_api_rlm.py`, `tests/test_api_sessions.py`, `tests/test_api_inventory.py`.
- **Интерактивный справочник.** Пакет `flasgger==0.9.7.1` (встроенные ресурсы Swagger UI, без CDN) отдаёт написанный вручную файл спецификации OpenAPI 3.0.3 `docs/openapi-v1.yaml` (24 пути / 29 операций) по адресу `/v1/docs` (UI) и `/v1/openapi.json` (документ); оба публичны — спецификация не является данными — и регистрируются в `create_app()` сразу после блюпринта `/v1`, с отключённым `rule_filter`, чтобы строки документации представлений никогда не сканировались. `API_V1_SPEC_PATH` задан абсолютным намеренно (относительный `template_file` разрешается относительно `app.root_path`, а не корня проекта), `app/templates/flasgger/head.html` переопределяет переданный в комплекте шаблон, который подключает Google Fonts, а `tests/test_api_docs.py` ломает сборку, если какой-либо маршрут `/v1` отсутствует в спецификации (и наоборот). Старый `docs/openapi.yaml` (внутренний веб-интерфейс и админка, до `/v1`) остаётся как есть и не отдаётся.

## LLM-клиент

`app/llamacpp_client.py:LlamaCppClient` с двумя бэкендами:

- **`DirectLlamaBackend`** — прямые HTTP-вызовы `llama-server` по `LLAMACPP_URL`.
- **`LlamaSwapBackend`** — вызовы через прокси `llama-swap` по `LLAMA_SWAP_URL`.

Бэкенд выбирается переменной окружения `LLAMACP_BACKEND` (по умолчанию `llama-swap`).

`_ensure_vram()` в `llamacpp_client.py` возвращает `bool` — каждый вызов чата/стрима проверяет VRAM перед POST. Ни одна модель никогда не получит 502 из-за VRAM — при нехватке VRAM возвращается корректное сообщение об ошибке.

## Система очереди

`app/queue.py:RedisRequestQueue` — два воркера со строгой сериализацией GPU.

**Владение воркерами:** воркеры запускаются только в серверных процессах. `create_app()` вызывает `RedisRequestQueue(app, start_workers=not _is_cli_process())` — процесс CLI `flask` (определяется через `sys.argv[0]`) никогда не запускает воркеры. Без этой защиты вызов `docker exec flai-web flask <cmd>` превращался во второго, невидимого потребителя очереди (потоки воркеров с `daemon=False` навсегда подвешивали процесс командной строки; их логи уходили в потерянный вывод `exec`). У `start_worker()` есть дополнительно защита идемпотентности `_workers_started`, поэтому в одном процессе никогда не может быть создан дублирующий набор воркеров.

### Быстрый воркер (в основном CPU; эмбеддинг слабо нагружает GPU)
- Классификация роутером (мультимодальная модель, всегда резидентна)
- Обработка текста
- Аудио (TTS/STT)
- **Только поиск по RAG** (эмбеддинг + Qdrant, ~500 МБ)

Все GPU-задачи медленного воркера ставятся в очередь обратно сюда — быстрый воркер никогда не выполняет генерацию.

### Медленный воркер (нагружен на GPU)
- Мультимодальная (`Qwen3VL-8B` на GPU-уровнях от 12 ГБ, `Qwen3VL-4B` на 8 ГБ и CPU)
- Ответы чата / рассуждений
- SD (Stable Diffusion)
- LTX-Video
- **Рассуждения** (`Qwen3.6-35B-A3B-UD` на GPU-уровнях; `gpt-oss-20b-mxfp4` с нативным MXFP4 в режиме только CPU)
- **Генерация по RAG** (через модель рассуждений)

Строго последовательно — одновременно выполняется только одна GPU-задача.

### Фоновые задачи
`fact_extraction_task` и `fact_merge_task` — фоновые задачи, которые выполняются на медленном воркере после ответов чата. Они определены в `_BACKGROUND_TASK_TYPES` и имеют особую обработку:
- **Не учитываются в статусе очереди** — `get_user_requests_status()` исключает их из отображения `processing` и `queued`.
- **Не учитываются в счётчике очереди пользователя** — `_process_single_task()` пропускает для них `_decrement_user_queue_count()`.
- **Ошибки только логируются** — и `_process_fact_extraction()`, и `_process_fact_merge()` обёрнуты в try/except, поэтому сбои никогда не доходят до пользователей через SSE.
- Они добавляются напрямую в `slow_queue_key` через `redis.rpush()`, минуя `add_request()`.

### Подпись задач
Задачи — JSON с подписью HMAC для защиты от подмены.

## Жизненный цикл моделей на одной потребительской GPU

Все модели llama.cpp используют одну группу с `swap: true` в llama-swap. В любой момент в VRAM загружена не более ОДНОЙ модели.

**TTL**:
- `multimodal` = 0 (никогда не выгружается — постоянно остаётся горячим, вытесняется только когда другой модели нужна VRAM)
- `reasoning`, `embedding` = 1s (выгрузка через секунду после ответа)

Мультимодальная модель предзагружается при старте через `hooks.on_startup.preload: ["multimodal"]`. После задачи рассуждений `_preload_multimodal_sync()` синхронно перезагружает мультимодальную модель перед ответом (на следующем запросе не будет холодного старта).

SD и LTX-Video используют отдельные GPU-контексты.

### Последовательность моделей

1. **Мультимодальная (`Qwen3VL-8B`, ~5.9 GiB вместе с `mmproj`)** — всегда резидентна (TTL=0, предзагружена при старте). Обслуживает ВСЕ три роли: роутер + текстовый чат + зрение (анализ и редактирование изображений). На GPU-уровне 8 ГБ и в режиме только CPU вместо неё используется более лёгкая `Qwen3VL-4B` (~2.5 ГБ + `mmproj`). Размер контекстного окна подбирается автоматически при развёртывании (`_autofit_context()`, 8192–32768 в зависимости от уровня GPU/ОЗУ, минимум 16384, чтобы вмещать количество токенов зрения от динамического дробления изображения на плитки). Вытесняется по требованию (например, ради рассуждений).

2. **Рассуждения (`Qwen3.6-35B-A3B-UD-Q2_K_XL` на GPU-уровнях; `gpt-oss-20b-mxfp4` в режиме только CPU)** — загружается по требованию для сложных запросов. MoE 35B (~3B активны); на GPU-уровнях 8 ГБ используется частичная выгрузка на процессор. Размер контекстного окна подбирается автоматически при развёртывании; TTL=1s → выгрузка через секунду после ответа. После завершения `_preload_multimodal_sync()` синхронно перезагружает мультимодальную модель.

3. **Эмбеддинг (`bge-m3 Q8_0`, 0.5 GiB)** — работает на быстром воркере (только поиск по RAG). TTL=1s → выгрузка через секунду после использования.

4. **SD / LTX-Video** — перед генерацией llama-swap просят выгрузить все модели через `POST /api/models/unload` (реализовано в `resource_manager.py:unload_llamacpp_model()`). Это освобождает ~6 GiB видеопамяти (мультимодальная + `mmproj`). Контейнер LTX-Video **всегда** перезапускается после генерации видео (`_force_restart_ltx_video()`, без ограничения частоты), чтобы освободить CUDA-контекст (~3 ГБ). Затем мультимодальная модель загружается обратно через `_preload_multimodal_sync()`.

### Пример: запрос генерации видео
роутер (мультимодальная, резидентна) → [-VIDEO-] → мультимодальная модель генерирует параметры видео (остаётся резидентной) → видеопайплайн загружается (мультимодальная сначала вытесняется / выгружается) → видео сгенерировано → перезапуск контейнера (освобождён CUDA-контекст) → _preload_multimodal_sync() → мультимодальная модель перезагружена → следующий запрос пользователя выполняется мгновенно

### Режим только CPU: параметры видео

При развёртывании только на CPU (`app/queue.py:_plan_cpu_video` → `modules/video.py:plan_cpu_generation`) запрошенные 768×512×240 планируются **до** генерации с учётом **двух** ограничений:

- **ОЗУ** — меньшее из свободной ОЗУ хоста (`MemAvailable`, `resource_manager._detect_available_ram_mb`) и лимита памяти контейнера LTX-Video из `LTX_VIDEO_RAM_LIMIT_MB` (задаётся в `docker-compose.cpu.yml`); определяющим является лимит контейнера, поскольку OOM там убивает контейнер несмотря на свободную ОЗУ хоста.
- **Время** — `LTX_VIDEO_CPU_TIME_BUDGET_S` (по умолчанию 85% от `LTX_VIDEO_TIMEOUT`), чтобы генерация надёжно завершалась до истечения таймаута клиентского запроса. `estimate_cpu_generation_time_s()` предсказывает реальное время по линейной калибровке CPU-пропускной способности на воксель (`CPU_VOXELS_PER_STEP_S=24_000`, наблюдалось ~495 с/шаг для 384×256×120 на хосте с 12 ядрами), по стоимости декодирования VAE и сборки на кадр (`CPU_VAE_SECONDS_PER_FRAME=45`, откалибровано на прогоне 256×192×57, где только декодирование VAE заняло ~43 мин) и по фиксированным накладным расходам `CPU_TIME_OVERHEAD_S=300` (кодирование T5 + апскейлер + ввод-вывод).

Из форматов 768×512×240 → 384×256×120 @ 12 fps → 256×192×57 @ 6 fps выбирается наибольший, удовлетворяющий ОБОИМ ограничениям; пользователь получает уведомление с точным выбранным форматом (или понятную ошибку «слишком медленно / недостаточно памяти», если не подходит ни один).

### Режим только CPU: параметры изображений

Генерация и редактирование SD на CPU (`modules/sd_cpp.py`) уменьшают в 2 раза **обе** стороны разрешения до отправки запроса в sd-wrapper: 1024×1024 → 512×512 (в ~4 раза меньше пикселей, ≈ в ~4 раза быстрее), чтобы диффузия успевала завершиться в пределах `SD_CPP_TIMEOUT` (раньше она истекала примерно на шаге 3 из 10). При редактировании уменьшаются также исходное изображение и целевой результат до той же уменьшенной вдвое величины. Локализованное уведомление (канал `resize_notice`, сохраняется как системное сообщение ассистента) сообщает пользователю об уменьшенном разрешении.

### Загрузки Model Hub и сопутствующие файлы

`app/model_hub.py` отображает многочастотную GGUF-модель как одну запись, размер которой складывается из всех шардов. Непервые шарды, файлы `imatrix`, MTP/draft-головы и вспомогательные файлы `FastMTP` — это вспомогательные файлы, а не самостоятельные варианты модели. `_companion_files()` связывает совместимые вспомогательные файлы с основным файлом; поддерживаемые модели `noMTP` могут выбрать одну draft-голову Q4_0/Q8_0 (по умолчанию Q8_0). Выбранные сопутствующие файлы проверяются по списку файлов репозитория и учитываются в проверках свободного места на диске и в `.hubmeta`.

Состояние загрузки публикуется в хэшах Redis (`model_hub:job:<id>`); массив `parts` сериализуется в JSON, поскольку хэши допускают только скалярные значения. `get_job()` обращается к тому же хэшу, когда опрос достигает веб-процесса без локального объекта задачи. Браузер показывает активные задачи в отдельной области вне заменяемых результатов поиска, сохраняет ID задач в `sessionStorage` и возобновляет опрос после перезагрузки вкладки. Итоги прогресса округляются вверх до целых МБ. На узких экранах элементы управления и таблицы Model Hub, а также список «Загруженные модели» во вкладке «Модели» прокручиваются горизонтально.

## SLM (SuperLocalMemory)

Базы данных SQLite на каждого пользователя в `/app/data/slm/{user}/.superlocalmemory/memory.db`.

- **Режим демона** (`slm serve start`) постоянно держит модель эмбеддинга в памяти.
- `services/superlocalmemory/slm_http.py` проксирует запросы демону на `localhost:8765` (без подпроцесса на каждый вызов).
- **Изоляция по пользователям**: извлечение (recall) читает напрямую из приватной таблицы пользователя (`atomic_facts`), а не из общей базы демона.
- **Внедрение фактов** — `_get_context_for_model()` в `modules/base.py` сначала забирает факты SLM (единственный вызов `slm.recall(...)` с `limit × 2`), разделяет их по `fact_type` (`session_specific` и `general`), измеряет реальную токенную стоимость, затем заполняет оставшийся бюджет историей диалога (порядок бюджета: запрос → контекст RAG → факты SLM → история; когда бюджет всё же превышен, возвращается RAG+SLM без истории).
- **Remember** сохраняет и в демон (общее), и в базу пользователя (асинхронный подпроцесс).
- **Парсер роутера для камеры**: использует текст после маркера `[-CAMERA-]` (код комнаты), а НЕ `original_query` — так сохраняется совместимость с русскими склонениями.
- **Повтор маршрутизации при ошибке JSON** — `process_message()` повторяет попытку один раз, если роутер возвращает искажённый ответ `{"error": ...}`.
- Факты SLM внедряются в контекст промпта как для мультимодальной, так и для модели рассуждений.
- **Ленивая перепроверка доступности SLM** — `_get_context_for_model()` всегда вызывает `slm.get_context()` (без проверки `slm.available`).
- **Дедупликация SLM** — `_recall_from_user_db()` дедуплицирует факты по содержимому (score `limit × 3`, возвращает уникальные). Настраивается через `SLM_RECALL_LIMIT` (по умолчанию 7).
- **Извлечение фактов** — фоновый поток (`_extract_facts_bg()`) работает только на CPU после ответов чата длиннее 20 символов. Извлекает факты из **запроса пользователя** (не из ответа модели) с помощью правилового сопоставления шаблонов (`app/slm_rules.py`) — без LLM, без блокировки GPU. Самоссылающиеся ответы модели («Чем я могу помочь?», «Вот ваш ответ») и выдуманные новости отсеиваются паттернами `_MODEL_RESPONSE_PATTERNS` и `_MODEL_CONTENT_PATTERNS`. Семантическая дедупликация через эндпоинт `/similarity` перед сохранением. Обёрнуто в try/except — сбои логируются, но никогда не показываются пользователю.
- **Слияние фактов** — `_process_fact_merge()` выполняется в фоновой очереди во время режима сна. Использует правиловый конвейер: `fast_cleanup` → `edit_distance_merge` → `fragment_merge` → `semantic_merge` (через `/similarity`) → `temporal_decay`. Без LLM, только CPU.
- **Сходство в SLM** — эндпоинт `/similarity` в `slm_http.py` проверяет текст-кандидата по существующим фактам с помощью модели эмбеддинга демона. Возвращает оценку косинусного сходства (0.0–1.0). Используется и извлечением, и слиянием для дедупликации.
- **Временное затухание** — факты старше `SLM_TEMPORAL_DECAY_DAYS` (по умолчанию 90) с уверенностью < `SLM_MIN_CONFIDENCE_FOR_DECAY` (по умолчанию 0.5) автоматически архивируются во время слияния.
- **Очистка воспоминаний** — демон пишет и в таблицу `memories`, и в `atomic_facts`, но система читает только `atomic_facts`. `_cleanup_memories_for_user()` удаляет осиротевшие строки `memories` (без активных `atomic_facts`). `_periodic_cleanup()` выполняется каждый час в фоновом потоке демона. Эндпоинт POST `/cleanup-memories` — для ручной очистки.
- **Список навыков** — `prompts/{ru,en}/skills.txt` — единый источник истины для всех возможностей. `format_prompt()` автоматически подставляет `{skills_section}`, если шаблон содержит этот плейсхолдер.
- Фоновый импорт при старте через чекпойнт-таблицу `slm_import_progress`.
- Автоочистка при удалении последней сессии (`_cleanup_slm_if_empty()` в `db.py`).
- **Жизненный цикл профиля соответствует учётным записям** — удаление учётной записи FLAI (`delete_user()` в `app/userdb.py`) также навсегда удаляет её профиль демона SLM через маршрут `POST /delete-profile` обёртки: временное переключение на целевой → стирание по GDPR (с защитой `confirm`, действует только на активном профиле) → восстановление ранее активного профиля → удаление строки профиля. Вердикт стирания проверяется по **счётчикам пользовательских данных** каждой таблицы (`_erasure_user_data_clean()`), а не по флагу `success` демона — `write_commits`/`erasure_receipts` намеренно являются неизменяемыми системными артефактами/журналом, поэтому профили с историей записи всё равно очищаются полностью. Сбои логируются и никогда не блокируют удаление учётной записи; профили `default`, неизвестные, пустые и текущий активный отклоняются.
- Файлы SLM принадлежат пользователю `appuser (UID 1000)` — `start.sh` выполняет `chown -R appuser:appuser` на общем томе.

## Система стилей ответов

`STYLE_INSTRUCTIONS` в `modules/base.py` определяет 5 стилей: `neutral`, `academic`, `professional`, `friendly`, `funny`. Каждый включает явные запреты для улучшения соблюдения малой моделью.

- **Единый источник истины** в `base.py`. Импортируется в `rag.py` и `multimodal.py` (без дублирования).
- Стиль подставляется в промпты через плейсхолдер `{response_style}` в шаблонах.
- Пользователь выбирает стиль через выпадающий список → сохраняется в `session["response_style"]` → передаётся через очередь → подставляется в системный промпт.
- Temperature 0.7 (настраивается в БД) для всех моделей чата/рассуждений — это позволяет генерировать с учётом стиля.
- Классификация роутером всегда использует `temperature=0.1` (жёстко задано в `process_message()`) для детерминированной маршрутизации запросов.

## Расчёт бюджета контекста

`_get_context_for_model()` в `modules/base.py` управляет бюджетом токенов:

1. Сначала забираются факты SLM (две фазы: сначала специфичные для сессии, затем общие)
2. Измеряется фактическая токенная стоимость SLM
3. Рассчитывается бюджет истории: `available_tokens - query_tokens - template_overhead - rag_tokens - slm_tokens`
4. История диалога загружается с ограничением на уровне SQL (окно `SESSION_SUMMARY_MAX_FETCH`)
5. Объединение: RAG + факты SLM + скользящая сводка сессии + история

- **Без жёстко прописанных резервов** — везде используются фактические размеры фактов.
- Запас безопасности: настраивается через `CONTEXT_SAFETY_MARGIN` (по умолчанию 0.85) поверх `CONTEXT_HISTORY_PERCENT` (по умолчанию 80).
- Накладные расходы шаблона: `TEMPLATE_OVERHEAD_TOKENS` (по умолчанию 800).
- Финальная проверка: `_validate_prompt_size()` обеспечивает жёсткий предел 95%.

### v11.3 — калибровка токенов и скользящая сводка сессии

- **Калибровка по реальному токенизатору** (`app/utils.py`): после каждого реального вызова LLM клиент записывает `usage.prompt_tokens` в калибратор символов на токен для каждой пары `(model_type, lang)`. `estimate_tokens()` предпочитает калиброванную медиану символов на токен статической таблице `TOKEN_COEFFICIENTS`, как только накопится ≥3 выборки, сближая бюджет с фактическим токенизатором, который использует модель. Включено для обоих бэкендов (прямой `llamacpp` и `llama-swap`), для стриминга (`stream_options.include_usage`) и без стриминга.
- **Скользящие сводки сессий**: когда токенный бюджет обрезает старую историю, отброшенный префикс сворачивается в компактную сводку, которую генерирует мультимодальная модель (`prompts/{ru,en}/summarize.template`), и сохраняется в `chat_sessions.summary`/`summary_upto_id`. Сохранённая сводка подставляется перед историей, поэтому длинные сессии сохраняют нить диалога. Регенерация сериализуется по сессиям (защита на уровне модуля) и затрагивает только сообщения новее `summary_upto_id`.
- История обрезается строго по токенному бюджету (без ограничения по количеству сообщений); `MAX_HISTORY_MESSAGES` теперь является подсказкой по окну выборки (по умолчанию 90).

## Модуль веб-поиска

`modules/search.py:SearchModule` — обёртка над JSON API SearXNG.

- `search(query, lang, max_results)` → список словарей.
- `format_results_context()` → отформатированная строка для модели рассуждений.
- Проверка доступности через `/healthz`.
- Профиль Docker `with-search`.
- Конфигурация: `SEARXNG_URL`, `SEARXNG_TIMEOUT`, `SEARXNG_MAX_RESULTS`.
- Категория роутера 7 (`[-SEARCH-]`) в `prompts/{en,ru}/base_text.template`.
- **Состав движков** — `searxng/settings.yml` включает `google news`, `bing news`, `yahoo news`, `yahoo`, `bing`, `mojeek`, `marginalia`, `presearch`, `qwant`, `yandex` и `swisscows news` в дополнение к стандартным `google cse` и `duckduckgo`, что повышает устойчивость при отказе отдельных движков. Имена и статусы движков восстанавливаются сборкой образа контейнера; правки требуют предварительного `docker exec flai-searxng chown`, если файл принадлежит root.
- **Повтор и мягкая ошибка** — `_process_search_task()` (быстрый воркер, только CPU) повторяет запрос один раз, когда SearXNG возвращает 0 результатов. Если обе попытки пусты, пользователь получает мягкое локализованное уведомление («Поисковые сервисы временно недоступны из-за ограничений внешних поисковиков. Пожалуйста, попробуйте повторить запрос через несколько минут.») вместо жёсткой ошибки «Результаты веб-поиска не найдены».
- **Нормализация дат** — `enhance_query_with_date()` в `modules/search.py` преобразует относительные указания на дату («позавчера/вчера/сегодня», английские эквиваленты) в абсолютные даты в часовом поясе пользователя (`app.config["TIMEZONE"]`) до POST-запроса в SearXNG: «Какие ИТ новости были вчера?» → «Какие ИТ новости были вчера (14 сентября 2026)?». Иначе движки возвращают общие страницы разделов вместо датированных статей. Запросы без относительных указаний на дату не изменяются — это нормализация запроса, а не маршрутизация.

### Провайдер Tavily (v12.4)

`SearchModule.search_with_fallback()` — единственная точка входа для всего веб-поиска. Когда у запросившего пользователя сохранён ключ Tavily (`app/tavily_keys.py`) и `TAVILY_ENABLED` истинно, сначала выполняется `_search_tavily()` (`POST {TAVILY_API_URL}/search`, `Authorization: Bearer`, `search_depth` из `TAVILY_SEARCH_DEPTH`, `include_raw_content=false`). Результаты Tavily используют тот же контракт `{title, url, content}`; сниппеты короче 300 символов дополняются со страницы через trafilatura — ровно как на пути SearXNG. Относительные даты для Tavily не нормализуются — она разрешает их самостоятельно. Любой сбой (отсутствующий ключ, отключённый провайдер, 401/403, 429, таймаут, некорректное тело, ноль результатов) возвращает к `search()`, неизменной реализации SearXNG. Вызывающий получает `(results, provider)`, чтобы записать в лог, какой бэкенд ответил.

## Веб-краулер (Crawl4AI, v12.4)

Опциональный sidecar-контейнер (`flai-crawler`, профиль `with-crawler`) с образом `unclecode/crawl4ai:0.9.4` (Apache-2.0; включает Playwright + Chromium). Сервер версии 0.9.4 слушает только loopback, если не задан `CRAWL4AI_API_TOKEN` — токен передаётся через compose (env краулера + `CRAWL_API_TOKEN` веб-контейнера), и каждый вызов клиента несёт заголовок `Authorization: Bearer`. Он даёт две возможности, которых не предоставляет обычный поиск:

- **`read_page(url)`** — нативный инструмент чата (быстрый воркер): рендерит одну
  страницу в настоящем браузере через `POST /md` (фильтр fit) и возвращает markdown. Регистрируется только когда контейнер доступен; закрывает пробел, из-за которого вставленные ссылки раньше вообще не открывались. Ярлык статуса в чате локализован («🕸️ Открываю страницу...») через `TOOL_META` + `tool_read_page`.
- **`[-CRAWL-]`** — категория роутера для явных намерений глубокого изучения.
  Тип задачи очереди `crawl_task` выполняется на выделенном однопоточном воркере (без слота быстрого/медленного воркера). **Sidecar намеренно отклоняет объекты стратегии глубокого краулинга для недоверенных запросов**, поэтому BFS живёт в клиенте (`crawl_site`): страницы запрашиваются по одной через `POST /md` (`f=raw` сохраняет ссылки), ссылки того же домена извлекаются из markdown, а стартовый URL глубже корня домена ограничивается префиксом своего пути (старт с `/docs/` никогда не заходит в глобальную навигацию портала). Ограничения: `CRAWL_MAX_PAGES` (50) / `CRAWL_MAX_DEPTH` (3) / `CRAWL_TIMEOUT_S` (300 с реального времени) / `CRAWL_MAX_PAGE_CHARS` (50k) / `CRAWL_MAX_TOTAL_CHARS` (1 МБ). Результат склеивается в секции `## <url>`, **каждая из которых обрезается до остатка бюджета контекстного окна** (`get_search_context_limit()` — исключение для первой страницы однажды давало контексты в 50035 символов и промпты в 25802 токена),
  **ЗАМЕНЯЕТ** документ пользователя, названный по регистрируемому домену
  (существующая цепочка удаления), а фаза на GPU (`_run_document_indexing` + очистка VRAM) выполняется **под блокировкой GPU** (`_gpu_lock`) — эмбеддинги являются реальным инференсом на GPU — до повторной постановки задачи рассуждения с `rag_source="crawler"`. Итоговый документ — обычный пользовательский документ, над которым работают обычный поиск RAG и режим «Глубокий анализ» (RLM).

### Правила роутера при работе с URL

Сообщение с ОДНОЙ ссылкой и вопросом о содержимом этой страницы («что за проект <URL>») не попадает ни в `[-CRAWL-]`, ни в `[-SEARCH-]`: это обычный чат, а ссылку открывает инструмент `read_page`. В категории 6 есть TOP EXCLUSION с буквальным примером — без него классификатор в 2 прогонах из 4 отправлял такие сообщения в веб-поиск (поиск не умеет открывать адреса и отвечать по чужим страницам).

### Деградация

| Ситуация | Поведение |
|---|---|
| Контейнер отключён или недоступен | `read_page` не регистрируется; `[-CRAWL-]` падает с локализованным сообщением (никогда не падает тихо на лёгкий поиск) |
| Сайт отказывает в автоматическом доступе (антибот, стартовая страница) | `SiteBlockedError` → локализованное уведомление «антибот — переключаюсь на обычный поиск», затем выполняется обычный путь веб-поиска (Tavily → SearXNG), а причина добавляется к запросу рассуждения |
| 0 пригодных страниц | Локализованная мягкая ошибка с советом использовать обычный поиск |
| Лимиты достигнуты | Чистая остановка; собранный префикс индексируется |
| Квота документов исчерпана | Локализованная ошибка квоты; содержимое отбрасывается |

### SSRF-позиция

`app/crawler_guard.py` проверяет каждый адрес до того, как он покинет приложение: только http(s), все резолвируемые адреса должны быть глобально маршрутизируемыми, credentials в адресе отвергаются. Остаточный риск: цепочка перенаправлений внутри браузера в контейнере проверяется только собственными механизмами краулера — это задокументировано для операторов, которые дополнительно могут закрыть мосты Docker брандмауэром. Trafilatura остаётся первым шагом извлечения; краулер — вторым шагом для страниц, которым нужен настоящий браузер.

## Классификация роутером и контекст сессии (v12.1)

Классификатор живёт в `modules/base.py:process_message()` (`temperature=0.1`) и читает промпт категорий из `prompts/{ru,en}/base_text.template`.

- **Принцип времени действия.** Шаблон открывается разделом «ACTION TIME» («ВРЕМЯ
  ДЕЙСТВИЯ»), который сначала решает, относится ли запрос к действию в **прошлом** (глаголы прошедшего времени: «смотрели», «обсуждали», «присылал», «вчерашние кадры») — такой запрос уходит в `[-HISTORY-]` — или к действию, которое нужно выполнить сейчас/в будущем. Категории действия (камера, изображение, видео, …) явно никогда не перехватывают вопросы о прошлом; камера сформулирована как «покажи **текущий** снимок», «посмотри состояние комнаты **прямо сейчас**».
- **Микроконтекст сессии.** `process_message()` принимает `recent_context`;
  `BaseModule.build_router_context()` (вызывается из `_route_text_action()` в `app/queue.py` перед классификацией каждого сообщения) собирает его из самых новых сообщений, которые возвращает `get_session_recent_history()` в `app/db.py` (тот же фильтр парных маркеров генерации, что и в `get_session_text_history`, только что отправленное сообщение исключается, каждое сообщение обрезается до `ROUTER_CONTEXT_MSG_CHARS` символов) плюс до `ROUTER_SLM_FACTS` фактов долговременной памяти SLM. Благодаря этому уточнение вроде «мы смотрели снимки с камер?» уходит в историю, а не включает камеру снова.
- Переменные окружения (значения по умолчанию в `app/config.py`):
  `ROUTER_CONTEXT_MESSAGES` (6), `ROUTER_CONTEXT_MSG_CHARS` (240), `ROUTER_SLM_FACTS` (2).

## Поиск по истории разговоров

`modules/history.py` реализует нативный инструмент `history_search` и серверный путь роутера `[-HISTORY-]`.

- `search_history()` ищет по прошлым сессиям с помощью конфигураций полнотекстового
  поиска PostgreSQL для русского, английского и простого текстового поиска, ранжирует совпадения по числу совпавших терминов и ограничивает индексируемый текст сообщений, чтобы большие сообщения с сгенерированным кодом не превышали предел размера `tsvector` в PostgreSQL.
- Содержимое сообщений сериализуется в JSON; модели возвращаются только текстовые
  части, без прикреплённых изображений и медиа.
- Поиск роутера исключает активную сессию и текущее сообщение. Общие запросы обзора
  истории используют сохранённые сводки сессий, если они есть, иначе берут первое/последнее сообщение пользователя из каждой прошлой сессии.
- Поиск поддерживает русские и английские лексические запросы в любом профиле
  интерфейса. Между языками запросы не переводятся.
- `HISTORY_SEARCH_LIMIT`, `HISTORY_MAX_RESULTS_CHARS` и `HISTORY_MAX_MESSAGE_CHARS`
  задают лимиты результатов и индексации.

## Стриминг рассуждений

`modules/base.py:generate_reasoning_response_stream()` выдаёт токены по одному через `_stream_chat()`.

`app/queue.py:_process_reasoning_request()` использует `generate_reasoning_response_stream()` вместо `process_reasoning()`. Токены публикуются через `_publish_stream_token()`.

- **На стороне сервера** `_strip_thinking_tags()` в `app/queue.py` обрабатывает три
  паттерна: (1) блоки ` thinking... response` удаляются целиком; (2) `<|channel|>analysis<|message|>...<|end|>?` (рассуждение) вырезается целиком — `<|end|>` необязателен, чтобы не удалить весь ответ, когда gpt-oss-20b его опускает; (3) `<|channel|>commentary<|message|>...<|end|>` (сам ответ)
  **разворачивается** — теги удаляются, внутреннее содержимое сохраняется.
  Некорректный `<|channel|>...` без `<|message|>` вырезается.
  **`app/llamacpp_client.py:_process_stream_chunk()`** выполняет безусловный сброс
  буфера при переходе `_thinking_active`, чтобы не потерять токены между блоками `analysis` и `commentary`. `_strip_generic_reasoning()` удаляет обычный текстовый chain-of-thought (например, `"Analyze Persona:"`, `"Final Answer Generation:"`); функция живёт в `queue.py` (обёртка над `llamacpp_client._strip_generic_reasoning()`) и применяется в `_process_reasoning_request()`.
- **На стороне клиента** `_stripThinkingTags()` в `events.js` повторяет серверную
  логику и применяется во время стриминга (теги `<|channel|>...` и типовые рассуждения), причём `_stripGenericReasoning()` вырезает типовые паттерны рассуждения в реальном времени.
- **Детектор зацикливания** — `app/llamacpp_client.py` пропускает весь стримимый
  контент через `_LoopGuard` (`_repetition_cutoff`: окно сканирования 4096 символов, блок = последние 200 символов, цикл = ≥3 повторения с одинаковым интервалом). Защита придерживает последние 1500 символов, чтобы обнаруженный цикл был обрезан до того, как дойдёт до пользователя (`⚠️ …прерван из-за зацикливания` / английский эквивалент). **Адаптивная задержка (медленные потоки):** задержка задана в символах, поэтому на машине с CPU (~1,6 ток/с) типичный ответ в 600–1400 символов её никогда не превысит и пришёл бы одним блоком уже после завершения генерации. Поэтому и `_LoopGuard`, и `_ReasoningStreamFilter` динамически сокращают её: после 40 вызовов `feed()` (много мелких подач = медленный поток) задержка линейно уменьшается на 30 символов за каждый дополнительный вызов, с нижней границей 300 символов. Быстрые потоки на GPU (несколько крупных кусков) сохраняют полную задержку; на детект цикла это не влияет (ему нужно 600+ символов истории, а постстримовая страховка обрезает всё, что пропустила меньшая задержка). При чистом завершении потока оба бэкенда сбрасывают буферы в фиксированном порядке — остаток `_stream_buffer` (через `_loop_guard.feed()`), затем `_reasoning_stream.flush()`, затем `_loop_guard.flush()` — поэтому короткие ответы (короче задержки) никогда не теряются и не меняются местами. Серверная страховка `strip_repetition_loop()` в `_process_reasoning_request()` обрезает циклы, пропущенные при стриминге, и делает одну повторную попытку.
- **Статус фазы размышления** — модель рассуждений не стримит контентные токены во
  время `reasoning_content` (размышления), поэтому между «модель загружена» и «первый контентный токен» очередь иначе ничего не показывала бы. Оба бэкенда принимают `status_callback` и вызывают его со значением `"generating"` сразу после возврата POST-а завершения (модель загружена, SSE-заголовки получены); `_process_reasoning_request()` превращает это в стадию `reasoning_thinking` («Обдумываю ответ...»), которую фронтенд тикает счётчиком по секундам до первого контентного токена, снимающего индикатор.

**Контекст веб-поиска**: `_get_context_for_model()` ставит результаты веб-поиска
перед контекстом с заметным заголовком («Результаты веб-поиска — используйте эти данные как основной источник.»), чтобы модель рассуждений считала их достоверными; `reasoning.template` (ru + en) содержит то же смягчённое правило («использовать их как основной источник»). (Исторически инструкция была строже — `"USE ONLY THIS DATA"`.)

## Глубокий анализ RLM (v12.1)

Явный переключатель **«Глубокий анализ»** в чате (`chat.html` `#rlm-toggle`; `sendRlmAnalysis()` в `chat-init.js` отходит от обычного потока отправки) отправляет текущий вопрос + выбранные документы в `POST /api/rlm/analyze` (`app/routes/rlm.py`). Документы выбираются кликом по ним в панели документов (`rlmSelectedDocs` в `chat-documents.js` синхронизирует скрытый мультивыбор `#rlm-docs` и подсвечивает выбор зелёной рамкой `.rlm-selected` + `✓`); вместе с вопросом можно приложить изображение. Если переключатель не может запуститься — нет ни документов, ни изображения, либо есть изображение без вопроса — `sendMessage()` снимает флажок и запрос уходит в **обычный** поток отправки. Эндпоинт принимает `multipart/form-data` (`session_id` + JSON `doc_ids` + `text` + необязательный `file`), требует аутентификации, проверяет владение сессией и документами, валидирует квоту/уменьшает изображение, сохраняет сообщение пользователя (текст + изображение), чтобы оно пережило перезагрузку страницы, и возвращает `202` с `task_id`/`position`/`user_message_id`/`resize_notice`.

### Оркестрация задачи

`rlm_analysis` — это GPU-задача медленного воркера: `_classify_queue_fast()` маршрутизирует её в медленную очередь, `_get_model_for_task()` отображает её в `reasoning`, а медленный воркер удерживает `_gpu_lock` на всё время задачи. `_process_rlm_task()` в `app/queue.py`:

1. запрашивает `ensure_vram_for_reasoning()`, затем помечает GPU занятой на всё время
   анализа (`ResourceManager.mark_rlm_busy()` / `mark_rlm_idle()`; `_rlm_busy` расширяет `is_gpu_busy()`, поэтому защита со сканированием watch-dog из v11.5 покрывает и RLM) и публикует стадию `loading_reasoning_model`;
2. собирает корпус **только из выбранных документов** (текст извлекается через
   `extract_text_from_file()`) — не из RAG;
3. если в запросе есть приложенное изображение (`file_data` в payload задачи),
   запрашивает `ensure_vram_for("multimodal")` и описывает его через `MultimodalModule.describe_image_for_rlm()` (новый `prompts/{ru,en}/rlm_image.template`), добавляя подробное текстовое описание в корпус как документ `«Изображение (file_name)»`; неудачное или пустое описание возвращает локализованную ошибку «Не удалось распознать изображение для глубокого анализа»; после фазы с изображением `ensure_vram_for_reasoning()` проверяется заново (мультимодальная модель выгружается);
4. отклоняет корпус до любой работы на GPU, если его суммарный размер превышает лимит
   OOM `RLM_MAX_CORPUS_CHARS` (по умолчанию 50 000 000 символов) — локализованная ошибка просит выбрать меньше документов или документы поменьше, и модель вообще не загружается; затем запускает цикл актора рассуждения (`modules/rlm.py:RlmModule.run()`) с ограничением `RLM_MAX_STEPS` (по умолчанию 18). Допустимое число шагов для хоста задаёт лестница ресурсов `_resource_step_budget()` (24 ГБ+→18, 16 ГБ→12, 12 ГБ→10, 8 ГБ→8, CPU/<8 ГБ→6); контекстное окно никогда не урезает шаги — вместо этого `_obs_trunc_for_context()` сжимает наблюдения каждого шага (до нижней границы в 800 символов), чтобы траектория помещалась в 95% контекстного окна `context_length` модели рассуждений минус резерв в 1000 токенов, а окно, слишком малое даже для минимальной траектории с одним наблюдением на шаг, всё равно деградирует до 1 шага вместо падения с «Request too long». Каждый шаг вызывает резидентную модель рассуждений с четырьмя инструментами `python` / `llm` / `web_fetch` / `final`; `final(answer)` (или обычный текстовый ответ) завершает цикл. **Последний шаг вызывается вообще без инструментов** — модель физически не может потратить его на ещё один вызов инструмента и обязана выдать текстовый ответ (предыдущий мягкий намёк можно было проигнорировать, и прогоны умирали на «достигнут лимит шагов»). `llm()` — это вызов под-модели с ограничением `RLM_SUB_MAX_TOKENS` (1024); `web_fetch()` выполняет поиск в SearXNG (топ-3 результата, по сниппетам) через **родительский** процесс, не чаще `RLM_WEB_MAX_FETCHES` (5) раз за анализ. Отмена (флаг в Redis) проверяется на каждом шаге. **Язык** ответа закрепляется через `{response_language}` в `prompts/{ru,en}/rlm.template`, а также локализованными `build_user_prompt()` и `broker_llm()`, и защита от преждевременного `final` отклоняет вызов `final()` для многофайлового корпуса, пока не выполнен ни один анализ через `python` — прогон продолжается корректирующим сообщением инструмента вместо досрочного закрытия.

Весь анализ — **одна GPU-задача**: модель рассуждений один раз загружается just-in-time и остаётся резидентной на все ходы актора (стоимость её перезагрузки с `ttl=1s` принимается). По завершении пошаговая трассировка (шаг/инструмент/аргументы/ наблюдение) сохраняется в ключ Redis `rlm_trace:<task_id>` (TTL 3600), а ответ сохраняется через `_save_and_respond()` с метаданными `extra` `model_type="rlm"` / `rlm_trace_task_id` / `rlm_steps`. Сообщение в БД несёт `model_type="rlm"` (свою собственную эмодзи-шапку 🔬🧠), и трассировка тоже сохраняется (как диагностируемый ключ), если прогон завершился ошибкой.

### Изоляция песочницы

`app/rlm_sandbox.py:RlmSandbox` выполняет сгенерированный моделью код в постоянном дочернем процессе, созданном через fork:

- код проверяется по белому списку AST до выполнения — `validate_code()` отклоняет
  импорты, определения функций и классов, `with`/`lambda`/`yield` и доступ к dunder-именам (`FORBIDDEN_NODES` / `FORBIDDEN_NAMES` / атрибут `FORBIDDEN`); пространство имён дочернего процесса ограничено `SAFE_BUILTINS`;
- `RLM_CODE_TIMEOUT` (по умолчанию 15 с, обновляется на каждом IPC-колбэке) ограничивает
  каждый фрагмент кода; по таймауту дочерний процесс убивается. rlimits: адресное пространство (2 ГБ), секунды CPU, ноль процессов/файлов/core-дампов;
- у дочернего процесса **нет прямого доступа к сети и файловой системе** — `llm()`
  и `web_fetch()` являются IPC-колбэками (`SandboxBroker`), которые ходят туда-обратно в родительский процесс, исполняющий инструмент и возвращающий результат потоком в пространство имён песочницы;
- `final(answer)` возбуждает внутренний сигнал, который завершает прогон с ответом;
  наблюдения обрезаются до `RLM_OBS_TRUNC` (4000 символов).

### Конфигурация, стадии и интерфейс

Переменные окружения (`app/config.py`, продублированы в `.env` / `.env.example`): `RLM_ENABLED` (true), `RLM_ACTOR_MODEL` (reasoning), `RLM_MAX_STEPS` (18 — жёсткий потолок; реальный бюджет определяют лестница ресурсов и платформа), `RLM_TASK_TIMEOUT` (0 — предельное время выводится автоматически из бюджета шагов и платформы: GPU 120+90×шагов, CPU 240+300×шагов секунд; `-1` отключает, любое положительное значение используется как есть; по истечении прогон завершается локализованной ошибкой «задача превысила лимит времени», а частичная трассировка сохраняется), `RLM_CODE_TIMEOUT` (15 с), `RLM_OBS_TRUNC` (4000 — верхняя граница; значение, подогнанное под контекст, может быть меньше), `RLM_SUB_MAX_TOKENS` (1024), `RLM_WEB_MAX_FETCHES` (5), `RLM_MAX_CORPUS_CHARS` (50 000 000).

Стадии прогресса передаются через `task_progress`: `loading_reasoning_model`, затем `rlm_reading` («Читаю документы...» / «Deep analysis: reading documents»), `rlm_step` («🔬 Глубокий анализ: фаза %s», со счётчиком шагов через `STAGE_COUNTER_KEYS`), `rlm_searching_web` (переиспользует существующий ярлык поиска), `rlm_submodel` и, наконец, `rlm_finalizing`. По завершении `appendRlmTraceBlock()` в `events.js` прикрепляет к последнему ответу ассистента сворачиваемую сводку «🔬 Глубокий анализ (N шагов)» — полная пошаговая трассировка остаётся в ключе Redis и пока не отображается.

## Обработка изображений документов и OCR отсканированных PDF (v12.1)

`describe_document_image` обрабатывает загруженные изображения-документы и PDF без извлекаемого текста. Для отсканированного PDF воркер читает число страниц через `pdfinfo`, рендерит каждую страницу в JPEG размером 1536 пикселей через `pdftoppm` и просит мультимодальную модель описать страницу и расшифровать читаемый текст. Для загруженного изображения модель описывает его напрямую. Результат сохраняется рядом с оригиналом как `.recognized_text` и ставится в очередь на обычную RAG-индексацию, благодаря чему отсканированные страницы, ярлыки и схемы становятся доступными для поиска. Утилиты Poppler установлены в веб-образ.

## Предпросмотр HTML-сообщений

`GET /api/html-preview/<message_id>` (`app/routes/messages.py`) отдаёт первый блок кода HTML из собственного сообщения чата аутентифицированного пользователя отдельным ответом со специальным CSP для предпросмотра. Это снимает блокировку локальных предпросмотров строгим CSP страницы чата. `_ensure_three_importmap()` чинит сгенерированные страницы на Three.js, которые импортируют аддон-модули из CDN без карты импортов: она внедряет сериализованную в JSON карту и переписывает совместимые импорты из CDN на алиасы `three`; страницы с уже существующей картой не трогаются.

## Отмена задач

- **Клиент**: кнопка отмены (`■`) в стримящихся сообщениях → POST
  `/api/cancel_task/{task_id}`.
- **Сервер**: `cancel_task(task_id)` ставит флаг в Redis `task:cancel:{task_id}` с
  TTL.
- `_is_task_cancelled(task_id)` проверяется в каждой итерации стриминговых циклов.
- **SSE-событие**: `stream_cancelled` → обновляет интерфейс.
- **Генерация/редактирование изображений**: проверки до и после блокирующих
  HTTP-вызовов (`_call_wrapper()`, `generate_image_params()`).
- **Генерация видео**: фоновый поток проверки отмены (`_start_cancel_checker()`)
  опрашивает каждые 2 с и перезапускает контейнер LTX при обнаружении отмены. 8 точек возврата при отмене в 4 типах задач.

## Прогресс генерации

- **SSE-события**: `task_progress` (ярлыки стадий), `video_step` (полоса прогресса),
  `image_step` (полоса прогресса), `image_preview` (base64-превью во время генерации).
- **Стадии чата/рассуждения** — `routing` → `searching_documents`/`searching_web` →
  `loading_reasoning_model` → `reasoning_thinking` → индикатор стриминга. Карты стадия→ярлык: `events.js:STAGE_LABEL_KEYS` (+ `STAGE_COUNTER_KEYS` для счётчиков `results`/`chunks` с плейсхолдерами `%s`), локализованные ярлыки — в TRANSLATIONS файла `chat.html`. Счётчики и таймер прошедших секунд по фазам работают на клиенте; фронтенд держит один элемент прогресса на сессию, потому что цепочки фаз пересекают id задач (поиск на быстром воркере → повторно поставленная задача рассуждения).
- **Серверные эндпоинты** в `app/routes/queue.py`:
  `POST /api/queue/internal/sd_preview`, `POST /api/queue/internal/sd_step`, `GET /api/queue/progress/<task_id>`.
- **Сохранение прогресса**: `_save_progress()` пишет в хеш Redis
  (`task_progress:{task_id}`) с TTL 30 минут. `_cleanup_progress()` удаляет его по завершении.
- **Восстановление на клиенте**: `restoreTaskProgress()` в `events.js` запрашивает
  `/api/queue/progress/{taskId}` при переподключении SSE и перезагрузке страницы.

**Названия стадий** (по-русски): `preparing_gpu`, `analyzing`, `analyzing_image`,
`analyzing_prompt`, `generating_video`, `generating_image`, `editing_image`, `loading_reasoning_model`, `capturing_snapshot`.

## Совместная запись голоса и изображения

`app/static/js/chat-recording.js`: если изображение уже прикреплено в момент записи голоса, голос сохраняется как `attachedVoiceBlob` вместо замены `attachedFile`. Превью показывает `"image.jpg + 🎤 voice.webm"`.

Сервер: `_process_transcribe_task()` создаёт задачу `type: "image"`, когда присутствуют одновременно `image_data` и `voice_record`.

## Вставка изображений из буфера обмена

`app/static/js/chat-init.js` добавляет обработчик `paste` на поле ввода сообщения. Приоритеты поведения:

1. **В буфере только текст** → обычная вставка текста по умолчанию (обработчик
   выходит рано, всё делает браузер).
2. **Только изображение** → `preventDefault()`, blob оборачивается в сгенерированный
   `File` с именем `pasted_YYYYMMDD_HHMMSS.<ext>` (расширение выводится из MIME-типа, `jpeg` → `jpg`), прикрепляется как `attachedFile` и показывается стандартное превью файла (имя + размер).
3. **И текст, и изображение** (например, при копировании картинки из браузера вместе
   с фрагментом HTML/текста) → побеждает изображение: срабатывает `preventDefault()`, а текст отбрасывается.

Изменений на сервере не требуется: вставленный файл идёт тем же путём загрузки через `FormData`, что и файл, выбранный кнопкой прикрепления. Неизображённое содержимое буфера (файлы, PDF) игнорируется.

## Исправление сессий при нескольких вкладках

**Проблема**: `session_id` читался исключительно из cookie Flask. Cookies Flask
общие для всех вкладок одного браузера. Когда пользователь создавал новую сессию в одной вкладке и отправлял сообщение в другой, сообщение могло попасть не в ту сессию.

**Решение**: клиент теперь отправляет `session_id` в теле запроса. Сервер проверяет
его (UUID v4 + владение пользователем) и использует, если он валиден, а иначе для совместимости возвращается к cookie Flask.

- `app/static/js/chat-init.js`: `sendMessage()` включает `session_id: currentSessionId`
  и в JSON-, и в FormData-запросы.
- `app/routes/messages.py`: `send_message()` читает `session_id` из тела запроса,
  проверяет его (UUID v4 + владение в БД) и обновляет сессию Flask.

## Индикаторы очереди в интерфейсе

`chat-queue.js`:
- `fetchQueueStatus()` собирает `newInfo` только из данных сервера (без защиты от
  гонки через `pendingRequestIds`).
- **Предотвращение нескольких ⚡**: только одна сессия показывает ⚡ — остальные
  показывают ⏳ с реальными позициями в очереди от сервера.
- **Отображение позиции в очереди**: используется оператор `??` (nullish coalescing) —
  позиция 0 (дополнительные задачи на обработке) показывает ⏳ без номера, обычные позиции очереди показывают ⏳ N.
- **Фоновые задачи не видны**: `fact_extraction_task` и `fact_merge_task`
  фильтруются через `_BACKGROUND_TASK_TYPES` в `get_user_requests_status()` — они никогда не вызывают индикаторы ⚡ или ⏳.

**Восстановление ⚡ после цепочки задач**: `events.js` — после каждого вызова
`clearSessionQueue()` планируется `setTimeout(fetchQueueStatus, 500)`. Это опрашивает сервер о следующей задаче в очереди и восстанавливает ⚡, когда следующая задача переходит из очереди в обработку.

## Счётчики токенов по каждому запросу

В шапке каждого ответа ассистента между сегментами ⏱️ (время) и 🚀 (токенов в секунду) показываются реальные тарифицируемые токены: `…| ⏱️ 12.4 s | 🔢 (▲45 ▼1 234) ток | 🚀 0,8 ток/с |` (▲ — выход, ▼ — вход, msgid `tokens_unit` — ru «ток» / en «tok»).

**Бэкенд** (`app/queue.py` + `app/utils.py`):
- `_process_request()` открывает ОДИН thread-local учётный счёт расхода на задачу
  (`begin_usage_account()` в `app/utils.py` — семейство `begin/record/finish/current`) для каждого LLM-типа задач; чисто служебные типы (`index_document`, `reindex_all_embeddings`, `fact_extraction_task`, `fact_merge_task`) исключены, а `_process_single_task()` в конце списывает остатки.
- Каждый вызов LLM накапливает реальные `prompt_tokens`/`completion_tokens` через
  `_record_prompt_tokens()` в `app/llamacpp_client.py` → `record_usage_for_current()`.
- Повторно поставленные задачи (рассуждение, image_gen, video) несут полу-счёт
  быстрого воркера внутри `request_data` (`request_id`, `submitted_at`, `usage_accum`; `_requeue_*_task()`), а `_process_request()` пересоздаёт его с тем же смещением на медленном воркере.
- `_save_and_respond()` списывает счёт (`finish_usage_account()`): и словарь
  результата, и колонка `messages.prompt_tokens` (новая колонка INTEGER, миграция в `app/database.py`) содержат итоги; `process_time` переопределяется полной длительностью запроса (от `submitted_at` до финиша). `consume_usage=False` оставляет счёт открытым для многосообщенческих задач (пара «снимок с камеры + описание»; описание списывает объединённые итоги).
- Неизвестные/отсутствующие значения (старые строки с `prompt_tokens=NULL`)
  сохраняются как NULL и отображают только известную сторону.

**Фронтенд** (`chat-utils.js:tokenStatsHTML()`, общий для отрисовки истории и
финализации в реальном времени):
- `tokenStatsHTML()` отображает только известные стороны (например, `🔢 (▲45) ток`,
  когда вход неизвестен); пустые/нулевые итоги не отображаются.
- Обёртка `window.displayMessage` в `chat-init.js` обязана передавать ВСЕ
  позиционные параметры обёрнутой функции — раньше она теряла 19-й (`promptTokens`), из-за чего входные токены были скрыты во всех SSE-путях. Защита: `tests/test_js_signatures.py` проверяет, что сигнатура обёртки равна сигнатуре обёрнутой функции и что позиционные параметры передаются дальше.

## Суммарные токены пользователей в админке

`GET /admin/api/users` возвращает `outgoing_tokens` и `incoming_tokens` для каждой неадминистративной учётной записи. Они считаются по сообщениям, присоединённым через сессии `chat_sessions` пользователя: исходящие (с точки зрения пользователя) — это сумма `messages.prompt_tokens`, входящие — сумма `messages.completion_tokens`. Таблица пользователей в админке показывает эти колонки сразу после Sessions; обе — сортируемые числовые поля. Изменения схемы не требуется. Полные резервные копии включают `chat_sessions` и `messages`, поэтому оба входа этих агрегатов восстанавливаются; копии только пользователей включают лишь `users` и намеренно не сохраняют историю чатов и суммы токенов.

## Автопрокрутка чата

- **Флаг `_isLoadingMessages`** в `chat-messages.js` не даёт N конкурирующим
  асинхронным колбэкам прокрутки запускаться при загрузке истории сообщений.
- **`isNearBottom()`**, порог = 200px — автопрокрутка срабатывает только когда
  пользователь близко к низу чата.
- **`scrollToBottom()`** упрощён — один вызов `scrollTo()` с `behavior: 'smooth'`.
- **`overflow-anchor: none`** в CSS контейнера чата — не даёт браузеру
  автопрокручиваться к якорному элементу во время обновлений DOM.

## Конфигурация llama-swap

- Все модели llama.cpp используют одну группу `llm_fast` с `swap: true`.
- Множество `seen_aliases` в `generate_yaml()` не даёт появиться дублирующимся
  алиасам, когда несколько модулей используют один и тот же GGUF-файл.
- Конфигурация автоматически генерируется из БД при старте в
  `llama-swap-config/`.
- Параметр `include_preload` управляет хуком предзагрузки `hooks.on_startup`:
  `False` при первом старте (предотвращает падение из-за устаревшего YAML на диске), `True` при перезагрузке из админки и при dry_load.
