# Измерение качества RAG

Инструмент отвечает на один вопрос: **стал ли поиск по документам лучше или хуже?** Он прогоняет
фиксированный набор вопросов через реальный путь поиска и показывает метрики выдачи плюс задержку
каждого запроса. Два прогона на одном наборе напрямую сравнимы.

Код: `app/rag_eval.py` (метрики и отчёт), CLI-команды `rag-eval` и `rag-eval-generate`
(`app/cli.py`). Тесты: `tests/test_rag_eval.py`.

## Формат набора

JSONL, один вопрос на строку:

```json
{"question": "Какой штраф за просрочку платежа?", "relevant": ["<doc_id>", "contract.pdf"], "reference": "Штраф составляет 5% за каждый день просрочки"}
```

- `relevant` — id документов или имена файлов, которые считаются правильным ответом.
- `reference` — необязательный фрагмент, из которого сгенерирован вопрос. Если он есть, проверка
  становится **на уровне чанка**: найденный фрагмент должен содержать этот текст, а не просто быть
  из нужного файла. Без него проверка документная, а на маленьком корпусе она быстро упирается в 1.0.

## Команды

```bash
# Собрать набор вопросов из проиндексированных чанков (один вызов модели на вопрос)
flask rag-eval-generate --user <login> --count 20 --out data/rag_eval/questions.jsonl

# Замерить
flask rag-eval --user <login> --dataset data/rag_eval/questions.jsonl \
               --top-k 10 --label "dense baseline" --out data/rag_eval/baseline.json
```

Опции: `--coverage` включает проход покрытия файлов, `--lang` и `--model` управляют генерацией.
В отчёт пишется снимок настроек (`RAG_TOP_K`, размер и перекрытие чанков, стратегия, доля контекста),
поэтому отчёт самодостаточен.

### Качество ответа (end-to-end)

Метрики поиска не поймают случай, когда модель нашла нужные фрагменты, но всё равно считает неверно —
а это типичный провал на вопросах «сколько мест работы в этом городе». Добавьте в элемент набора поле
`"answer"` и запустите ту же команду с `--answers`:

```json
{"question": "Сколько рабочих мест было в Твери?", "relevant": ["<doc_id>"], "answer": "0"}
```

Инструмент делает поиск, собирает контекст так же, как запрос в чате, просит модель ответить (ей
сказано отвечать `НЕТ ДАННЫХ`, если во фрагментах ответа нет) и сравнивает результат: числа — по
числу, свободный текст — по нормализованному вхождению, а ожидаемый `0` принимает и явный ответ
«нет данных». В отчёт попадает каждый промах с ожидаемым и фактическим ответом.

## Метрики

| Метрика | Смысл |
|---|---|
| `hit@k` | Доля вопросов, где в top-k есть хотя бы один релевантный фрагмент |
| `recall@k` | Доля найденных релевантных документов в top-k |
| `MRR` | Средний обратный ранг первого релевантного результата (1.0 — всегда первый) |
| `nDCG@k` | Качество ранжирования, каждый документ считается один раз |
| `latency p50/p95` | Время поиска на запрос (эмбеддинг + Qdrant), миллисекунды |
| `context chars` | Сколько символов запрос отдаёт модели |

Задержка важна не меньше качества: гибридный поиск и реранкер покупают точность временем, и именно
эти цифры решают, оправдана ли сделка.

## Сетка политики (v12.9)

Три константы политики передаются в `flask rag-eval` опциями запуска, поэтому для
сетки не нужен правка кода: `--answer-share`, `--depth-over-coverage`,
`--breadth-share`, плюс `--budget`, чтобы `top_k` выбирал аллокатор, а не `--top-k`.

Замер на 11 фактических вопросах по корпусу из 29 документов (один ответ на
вопрос, оценка сквозная), на эталонном хосте с 16 ГБ:

| Прогон | точность ответа |
|---|---|
| answer-share 0.05 / 0.10 / 0.15 | 1.000 / 1.000 / 1.000* |
| depth-over-coverage 1.0 / 1.5 / 2.0 | 1.000 / 1.000 / 1.000 |
| breadth-share 0.15 / 0.25 / 0.50 | 1.000 / 1.000 / 1.000 |
| та же сетка с долей документов, зажатой до 10 % | 1.000 везде |

\* один прогон дал 0.909, потому что модель написала «асiyat» (кириллическая «а»)
там, где ожидался `asiyat` — артефакт транслитерации в скорере, а не промах поиска.

**Вывод:** на корпусе, который помещается в окно, константы не меняют качество
ответа — аллокатор уже подбирает объём доказательств по корпусу, поэтому все три
настройки покрывают все документы. Они начинают влиять только тогда, когда
доказательства *не могут* покрыть корпус (намного больший корпус или намного
меньшее окно) — этот случай сетка не достигает. Значения по умолчанию остаются, а
реально работающая величина — аллокатор, а не эти три.

**Отдельное ограничение:** вопросы, требующие агрегации по целым документам
(«сколько всего часов по всем файлам», «сколько файлов»), валятся в RAG с одним
фрагментом на файл (2 из 9 в первом, агрегационном прогоне) — это территория
глубокого анализа, а не вопрос политики поиска.

## Базовая линия

Важны два набора, и они расходятся — в этом и есть вывод.

**Синтетический набор** (19 вопросов, сгенерированных по чанкам, проверка на уровне чанка,
`top_k=10`): такие запросы уже близки к своему фрагменту, плотный поиск силён, а лексическая половина
чаще добавляет шум.

| Прогон | hit@10 | recall@10 | MRR | nDCG@10 | p50 | p95 |
|---|---|---|---|---|---|---|
| dense | 0.842 | 0.842 | 0.781 | 0.796 | 14 мс | 44 мс |
| hybrid (RRF) | 0.842 | 0.842 | 0.671 | 0.715 | 31 мс | 59 мс |
| hybrid + rerank | 0.842 | 0.842 | 0.816 | 0.823 | 190 мс | 398 мс |

**Вопросы-подсчёты** (три реальных «сколько мест работы в городе» с известными ответами) — там, где
плотный поиск проваливается: экспорт чата оказывается выше резюме. Поиск на смешанном наборе из 22
вопросов: 0.773 → 0.864 hit@10, а ответы end-to-end при рабочем `top_k=20`:

| Конфигурация | верных ответов |
|---|---|
| dense | 0/3 |
| hybrid | 3/3 |
| hybrid + rerank | 3/3 |

Гибрид включён по умолчанию (`RAG_HYBRID_ENABLED=true`): на смешанном наборе из 22 вопросов он лучше
по всем метрикам (hit 0.909 против 0.864, MRR 0.744 против 0.688, nDCG 0.965 против 0.751) и для
20-фрагментного окна чата, и для 5-фрагментного окна задач (hit 0.864 против 0.727, nDCG 0.815 против
0.688). Реранкер по умолчанию выключен: с включённым гибридом он снижает nDCG на 20-фрагментном окне
(0.922) и стоит ~280 мс на поиск, помогая только 5-фрагментному окну инструмента (0.831 против 0.815).

Каждое изменение (реранкер, фильтры по метаданным, нарезка) меряется на обоих наборах.

- **Графовые доказательства (v13.2).** Один и тот же набор прогоняется дважды: с выключенным и
  включённым `GRAPH_RAG_ENABLED`; падение MRR или nDCG на любом из существующих наборов — блокер.
  `tests/data/graph_eval.jsonl` содержит десять вопросов на связи и агрегацию по вымышленным
  демонстрационным предложениям (`demo/pdfs/ru/`): пять вида «как связаны X и Y» и пять таких,
  где ответ собирается из нескольких документов; критерий приёмки — каждый ожидаемый документ
  в первых пяти.

## Замечания

- Набор из 5 вопросов ничего не доказывает: генерация дешёвая, берите 20–30.
- Вопросы намеренно перефразируются (промпт запрещает копировать формулировки фрагмента), иначе
  плотный поиск даёт 1.0 «из коробки» и инструмент не различает подходы.
- Пересобирать набор стоит только при существенном изменении корпуса, иначе прогоны перестают быть
  сравнимыми.
- Наборы и отчёты содержат реальные документы и персональные данные: держите их в `data/rag_eval/`, эта
  папка в `.gitignore`. Оттуда ничего не коммитится и не пушится.
