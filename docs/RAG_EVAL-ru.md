# Измерение качества RAG

Инструмент отвечает на один вопрос: **стал ли поиск по документам лучше или хуже?** Он прогоняет
фиксированный набор вопросов через реальный путь поиска и показывает метрики выдачи плюс задержку
каждого запроса. Два прогона на одном наборе напрямую сравнимы.

Код: `app/rag_eval.py` (метрики и отчёт), CLI-команды `rag-eval` и `rag-eval-generate`
(`app/cli.py`). Тесты: `tests/test_rag_eval.py`.

## Формат набора

JSONL, один вопрос на строку:

```json
{"question": "Какой штраф за просрочку платежа?", "relevant": ["<doc_id>", "contract.pdf"], "reference": "Штраф составляет 5% за каждый день просрочки"}
```

- `relevant` — id документов или имена файлов, которые считаются правильным ответом.
- `reference` — необязательный фрагмент, из которого сгенерирован вопрос. Если он есть, проверка
  становится **на уровне чанка**: найденный фрагмент должен содержать этот текст, а не просто быть
  из нужного файла. Без него проверка документная, а на маленьком корпусе она быстро упирается в 1.0.

## Команды

```bash
# Собрать набор вопросов из проиндексированных чанков (один вызов модели на вопрос)
flask rag-eval-generate --user valery --count 20 --out data/rag_eval/questions.jsonl

# Замерить
flask rag-eval --user valery --dataset data/rag_eval/questions.jsonl \
               --top-k 10 --label "dense baseline" --out data/rag_eval/baseline.json
```

Опции: `--coverage` включает проход покрытия файлов, `--lang` и `--model` управляют генерацией.
В отчёт пишется снимок настроек (`RAG_TOP_K`, размер и перекрытие чанков, стратегия, доля контекста),
поэтому отчёт самодостаточен.

## Метрики

| Метрика | Смысл |
|---|---|
| `hit@k` | Доля вопросов, где в top-k есть хотя бы один релевантный фрагмент |
| `recall@k` | Доля найденных релевантных документов в top-k |
| `MRR` | Средний обратный ранг первого релевантного результата (1.0 — всегда первый) |
| `nDCG@k` | Качество ранжирования, каждый документ считается один раз |
| `latency p50/p95` | Время поиска на запрос (эмбеддинг + Qdrant), миллисекунды |
| `context chars` | Сколько символов запрос отдаёт модели |

Задержка важна не меньше качества: гибридный поиск и реранкер покупают точность временем, и именно
эти цифры решают, оправдана ли сделка.

## Базовая линия

Замер на наборе из 20 вопросов, сгенерированных по 29 реальным документам (вопросы перефразированы,
проверка на уровне чанка), плотный поиск, `top_k=10`:

| Прогон | hit@10 | recall@10 | MRR | nDCG@10 | p50 | p95 |
|---|---|---|---|---|---|---|
| dense baseline | 0.950 | 0.950 | 0.900 | 0.913 | 15 мс | 37 мс |

Каждое изменение (гибридный поиск, реранкер, фильтры по метаданным, нарезка по структуре) меряется
против этой строки на том же наборе и том же `top_k`.

## Замечания

- Набор из 5 вопросов ничего не доказывает: генерация дешёвая, берите 20–30.
- Вопросы намеренно перефразируются (промпт запрещает копировать формулировки фрагмента), иначе
  плотный поиск даёт 1.0 «из коробки» и инструмент не различает подходы.
- Пересобирать набор стоит только при существенном изменении корпуса, иначе прогоны перестают быть
  сравнимыми.
- Наборы и отчёты содержат реальные документы и персональные данные: держите их в `data/rag_eval/`, эта
  папка в `.gitignore`. Оттуда ничего не коммитится и не пушится.
