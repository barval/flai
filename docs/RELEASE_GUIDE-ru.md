# Руководство по релизам — ПЛИИ v12.4

В этом документе описывается процесс выпуска новой версии, обновления README и поддержания документации. Читайте его при подготовке нового релиза.

> **Шаги релиза v10.0:** Обновление версии с 9.2 до 10.0 (`pyproject.toml`, скрипты развёртывания, документация, метрики, колонтитулы `.po`). Удалена отдельная чат-модель (Qwen3-4B-Instruct) — мультимодальная модель (Qwen3VL-8B-Instruct) теперь используется как единая модель для чата, маршрутизации и работы с изображениями. В скриптах развёртывания обновлена загрузка (вместо чат-модели загружается мультимодальная). Из конфигурации llama-swap удалён раздел chat (`ttl=0` для мультимодальной, `preload: on_startup`). Удалена карточка чата из панели администратора. Обновлены тестовые фикстуры: `chat` → `multimodal` во всех проверках типа модуля. Самовосстановление БД: при старте выполняется `DELETE FROM model_configs WHERE module = 'chat'`.

> **Примечание (v9.2):** Обновление версии с 9.1 до 9.2 повсеместно (`pyproject.toml`, скрипты развёртывания, документация, метрики, заголовки и колонтитулы `.po`). Критические обновления зависимостей: CVE-2026-25645 (`requests`→≥2.33), CVE-2025-71176 (`pytest`→≥9.0), `gunicorn`→26.1, `redis`→8.x, `qdrant-client`→1.19. Сервер Qdrant v1.12.1→v1.19.0 (требуется чистый старт — формат сегментов несовместим). Переподключение RAG (`check_availability()` с 3× попытками при старте и переподключением на каждый запрос). Оптимизация извлечения из SLM (один вызов, таймаут 30→15 с). Умный выбор уровня выгрузки SD (бюджет VRAM с буфером декодирования VAE). Исправление нумерации категорий роутера (камера=4, документы=5). Исправление VRAM камеры (`ensure_vram=False` в `chat_with_image_stream()`). Исправление регрессии VRAM (`ensure_vram_for()` возвращает True, если модель уже загружена). Троттлинг потокового вывода (рендер 120 мс, сохранение 500 мс). Повтор при пустом ответе модели рассуждений. Резервный разбор JSON с одинарными кавычками в вызовах инструментов (`ast.literal_eval()`). Исправление промпта рассуждений (модель больше не ищет в интернете). Миграция API клиента Qdrant (`search()`→`query_points()`). Исправление промпта роутера (запросы с именами людей → RAG). Исправление зависания потокового вывода (O(n²) → троттлинг рендера).

> **Шаги релиза v9.1:** Обновление версии с 9.0 до 9.1 повсеместно (`pyproject.toml`, скрипты развёртывания, документация, метрики). Добавлена зависимость `trafilatura>=2.0.0` в основные зависимости. Снято жёсткое ограничение `pytz==2023.3` → `pytz>=2023.3` (требуется транзитивной зависимостью `dateparser` из состава `trafilatura`). Упрощены тома Docker — 35 отдельных монтирований файлов заменены на 3 директории (`./app:/app/app`, `./modules:/app/modules`, `./prompts:/app/prompts`), добавлен `PYTHONDONTWRITEBYTECODE=1`. Улучшен веб-поиск: параллельная загрузка страниц для коротких сниппетов, смягчены инструкции в промптах. Исправлено переполнение бюджета: `format_results_context()` обрезает до 2К на результат и до динамического общего ограничения, `_get_context_for_model()` возвращает RAG+SLM без истории при превышении бюджета. (Примечание: явное `categories=general,news` добавлялось, затем убрано — вызывало ограничение частоты запросов в DuckDuckGo.)

## Процесс документирования релиза

При выпуске новой версии обновляйте эти файлы **в указанном порядке**:

### 1. README.md и README-ru.md — раздел «Что нового»

- Находится в разделе «Архитектура» (под заголовком `### What's New in vX.X`)
- Перечислите только **самые значимые изменения** из новой версии
- Формат: `| **Название возможности** | Краткое описание |`
- Описания должны быть краткими (1–2 строки на возможность)

### 2. README.md и README-ru.md — раздел «Дорожная карта → Выполнено»

- Находится внизу раздела «Дорожная карта» (под заголовком `### ✅ Completed`)
- Добавьте **только самые значимые новые возможности, крупные изменения и критичные исправления ошибок**
- НЕ добавляйте мелкие правки, изменения тестов или внутренний рефакторинг
- Формат: `- **Название возможности** — краткое описание`

### 3. AGENTS.md — раздел с версией

- Обновите заголовок с версией: `# AGENTS.md — ПЛИИ vX.Y`
- Опишите технические детали новых возможностей (архитектура, алгоритмы, параметры)
- Обновите раздел «Известные проблемы»: перенесите исправленные пункты в раздел с версией
- Перенесите исторические детали в `CHANGELOG.md` или в файлы `docs/`

### 4. CHANGELOG.md

- Добавьте новый раздел для версии
- Включите все значимые изменения, исправления ошибок и примечания по миграции
- См. шаблон `CHANGELOG.md` ниже

### 5. Git: ветка релиза и отправка в репозиторий

Начиная с v10.0 каждый релиз живёт в собственной **ветке версии** (`vX.Y`), а не в теге (теги существовали только до v9.3):

```bash
git checkout -b vX.Y                      # branch from the previous release branch
# ...release commits...
git push origin vX.Y                      # 'origin' = gitea (the authoritative remote for vX.Y)
```

Переводы поставляются **уже скомпилированными**: файлы `.po` **и** `.mo` отслеживаются в git (начиная с v11.5, коммиты f93d4a7/dd8564e). Если при обновлении версии затронуты файлы `.po`, перекомпилируйте их в каждой ветке и закоммитьте:

```bash
pybabel compile -d translations           # per branch — footers differ between vX.Y and master
```

Старые релизы сливаются вперёд в долгоживущие ветки публичного зеркала: `master` (gitea) и `main` (github). Ветка gitea хранит состояние конкретной версии; `github/main` получает слияние и сохраняет ссылку на видеоассет github без изменений.

## Чек-лист обновления версии
При выпуске новой версии:

### 1. Обновите номер версии в:
  - `pyproject.toml`: `version = "X.Y.Z"`
- `app/config.py`: `APP_VERSION = "X.Y"` — единственное место, где определяется версия (её читают метрики, шаблоны и `window.ПЛИИ_VERSION`)
  - `AGENTS.md`: заголовок с версией `# AGENTS.md — ПЛИИ vX.Y`
  - `README.md`: `### What's New in vX.Y`
  - `translations/{en,ru}/LC_MESSAGES/messages.po`: только заголовок `Project-Id-Version` (затем `pybabel compile -d translations` и коммит обоих файлов — `.po` и `.mo`) — строки колонтитула больше не содержат версию
  - `deploy.sh`, `deploy-ru.sh`: строка версии в заголовках, сообщениях об успехе и тексте справки
  - `docs/*.md`: версия в заголовках и примечаниях к изменениям

### 2. Обновите раздел «Что нового» в обоих README:
  - Добавьте новые возможности в таблицу
  - Уберите возможности, которые больше не новые
  - Описания должны быть краткими (1–2 строки на возможность)

### 3. Обновите раздел «Дорожная карта → Выполнено» в обоих README:
  - Добавьте значимые новые возможности и крупные изменения
  - НЕ добавляйте мелкие правки, изменения тестов или внутренний рефакторинг
  - Формат: `- **Название возможности** — краткое описание`

### 4. Обновите список моделей, если модели изменились:
  - Добавьте новые модели в таблицу бенчмарков
  - Обновите требования к VRAM
  - Обновите числа производительности

### 5. Обновите команды развёртывания, если профили изменились:
  - Добавьте новые флаги `--profile`
  - Обновите примеры команд
  - Обновите описание каждого профиля

### 6. Создайте/обновите ветку релиза:
```bash
git checkout -b vX.Y        # if not created yet
git push origin vX.Y        # gitea — authoritative remote for the version branch
# merge into master (gitea) and main (github) only when promoting the release
```

## Руководство по обновлению README
При обновлении README.md и README-ru.md следуйте правилам из [LOCALIZATION-ru.md](LOCALIZATION-ru.md).

### README.md (английский)

Разделы, которые нужно обновлять:
  1. **Список возможностей** (`### ✨ Features`) — добавить новые возможности, убрать устаревшие
  2. **Таблица «Что нового»** (`### What's New in vX.X`) — обновить номер версии и добавить новые возможности
  3. **Таблица основных компонентов** (`### Core Components`) — добавить/убрать сервисы, обновить порты
  4. **Уровни оборудования** (``### Hardware Tiers`) — обновить требования к VRAM/ОЗУ, если они изменились
  5. **Бенчмарки моделей** (`### Model Benchmarks`) — добавить новые модели, обновить данные о производительности
  6. **Команды быстрого старта** (`### Quick Start`) — обновить флаги deploy.sh, если изменились профили
  7. **Профили Docker Compose** — перечислить все доступные профили с описаниями
  8. Раздел **«Конфигурация»** — обновить переменные окружения, если они добавлены или изменены
  9. **Синхронизация `.env` / `.env.example`** — если переменные окружения добавлены или изменены в `app/config.py`, убедитесь, что обновлены и `.env`, и `.env.example`. В `.env` лежат реальные значения, в `.env.example` — плейсхолдеры и комментарии. Порядок секций должен совпадать.

Правила оформления:
  - Используйте таблицы для структурированных данных (компоненты, бенчмарки, тиры)
  - Используйте префиксы-эмодзи для списков возможностей (в соответствии с существующим стилем)
  - Держите описания краткими (1–2 строки на возможность)
  - Указывайте номер версии в заголовке «Что нового»: ### What's New in vX.X

### README-ru.md (русский)

Правила перевода:
  - Переводите ВСЁ новое содержимое из README.md на русский
  - Оставляйте технические термины на английском (Docker, GPU, VRAM, llama.cpp и т. д.)
  - Оставляйте блоки кода и примеры команд на английском
  - Переводите заголовки разделов, описания возможностей и пояснительный текст
  - Поддерживайте идентичную структуру и форматирование, как в README.md

Разделы, которые ОБЯЗАНЫ быть переведены:
  - Список возможностей (все пункты)
  - Таблица «Что нового» (столбец «Возможность» переведён, столбец «Примечания» переведён)
  - Таблица основных компонентов (столбцы «Компонент» и «Назначение» переведены)
  - Уровни оборудования (столбец «Возможность» переведён)
  - Инструкции быстрого старта (описания, а не команды)
  - Весь пояснительный текст и примечания

Разделы, которые остаются на английском:

  - Блоки кода (```bash ... ```)
  - Примеры команд (`./deploy.sh --download-models`)
  - Технические параметры (порты, имена моделей, пути к файлам)
  - Текст бейджей (уже на английском)
  - Ссылки на GitHub и URL

### Типичные ошибки, которых следует избегать
  - ❌ Не добавляйте изменения кода в обновления README — это отдельные коммиты
  - ❌ Не меняйте порядок разделов без причины — поддерживайте единообразие
  - ❌ Не удаляйте существующие возможности из списков — только добавляйте новые
  - ❌ Не переводите блоки кода и примеры команд
  - ❌ Не меняйте префиксы-эмодзи — сохраняйте существующий стиль
  - ✅ Всегда проверяйте, что оба README имеют идентичную структуру
  - ✅ Всегда проверяйте работоспособность команд deploy.sh после обновления

## Шаблон CHANGELOG.md

```markdown
# Changelog

All notable changes to FLAI are documented in this file.

## [vX.Y] — YYYY-MM-DD

### ✨ New Features
- **Feature name** — brief description

### 🐛 Bug Fixes
- **Fix description** — what was broken and how it was fixed

### 🔧 Improvements
- **Improvement description**

### 📦 Dependencies
- Updated `package` from `X.Y` to `A.B`

### 🗑️ Removed
- Removed deprecated `feature_name`

### 🔒 Security
- Security fix description

### 📝 Migration Notes
- Any breaking changes or migration steps
```

### Философия документации
  - **AGENTS.md** — Конституция: команды, критичные правила, жёсткие ограничения. Её всегда читают ИИ-агенты. Карта документации в ней — указатель всех файлов в `docs/`.
  - **README.md** — Короткий обзор и быстрый старт. У каждой темы есть отдельный файл в `docs/`, на который ссылается раздел, упоминающий эту тему.
  - **Одна тема — один файл** — читатель с конкретным вопросом должен сразу попасть на ответ. Не превращайте README обратно в руководство.
  - **Без дублирования** — факт живёт ровно в одном файле; остальные файлы ссылаются на него. Перенося материал, удаляйте оригинал.
  - **Паритет переводов** — у каждого пользовательского или административного `docs/X.md` есть пара `docs/X-ru.md` с той же структурой разделов, обновляемая в том же коммите.
