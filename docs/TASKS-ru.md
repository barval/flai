# Фоновые задачи (Задачи)

**Для чего?** Некоторые работы слишком велики для одного запроса в чате: подготовить отчёт на 10 страниц из нескольких источников, изучить тему по десятку веб-страниц и составить структурированную справку, сгенерировать набор изображений и описать их. **Задачи** — это долгоиграющие фоновые работы: вы описываете желаемый результат, система раскладывает запрос на план из шагов и выполняет их по очереди с **более низким приоритетом, чем чат** — задача никогда не заставляет ваш запрос в чате ждать, а любой запрос в чате замораживает идущую задачу и забирает ресурсы себе.

## Как пользоваться

1. Откройте вкладку **Задачи** в левой колонке (между **Документами** и **Сессиями**), нажмите ➕ и опишите желаемый результат. Вкладка заново открывает последнюю открытую задачу (в том числе после перезагрузки страницы) — как чат открывает свой последний сеанс; пустое состояние показывается только когда восстанавливать нечего.
2. Можно также создать задачу и описать её позже: ➕ открывает **черновик** (статус «draft», поле ввода становится полем описания); отправка описания ставит задачу в очередь.
3. Задача планируются и начинает выполняться. Её переписка открывается в главном окне и выглядит как обычный чат: запрос пользователя, сообщение «План из N шагов:», затем результат каждого шага с префиксом «Шаг N из M:» и финальный ответ. Префиксы плана/шага рендерятся отдельной курсивной сервисной строкой, а каждое сообщение ассистента несёт такую же шапку, как в чате: 📅 дата | имя модели | ⏱️ время исполнения | 🔢 расход токенов | 🚀 ток/с, плюс кнопки 🗣️ (озвучить) и 📋 (копировать). Сообщение плана несёт ту же шапку — исполнитель сохраняет метаданные вызова планировщика (`plan_meta`: имя модели рассуждений, время, реальные токены) вместе с планом, и маршрут сообщений их отдаёт. Запросы пользователя получают те же кнопки 🗣️/📋, что и ответы (в обеих ветках `displayMessage` и в `renderTaskMessage`); у whisper-транскрипций и system/ошибок кнопок нет. Поля шапки независимы друг от друга — финальная сводка показывает свои токены, хотя отдельного времени у неё нет. Шаг, выполненный инструментом, а не моделью рассуждений (calculate, search, медиа-подзадача), называет этот инструмент — локализовано и с эмодзи — отдельной курсивной строкой сразу под строкой шага (тем же шрифтом, что и «⚙️ Шаг N из M:»), например «🔎 Веб-поиск:», а его шапка показывает модель и токены верификатора-проверяющего (единственный вызов модели на таком шаге). Шаги медиа и RLM сообщают модель, которая реально сделала работу: шаг камеры/зрения показывает мультимодальную модель (🖼️) с реальными токенами, генерация изображения — `SD_MODEL_TYPE` (🖌️), редактирование — `flux-2-klein-4b` (🎨), видео — `LTX_VIDEO_MODEL` (🎥), RLM — модель рассуждений (🔬🧠). Пока составляется план, баннер статуса показывает живую стадию со счётчиком секунд — «Загружаю модель рассуждений... (Nс)» при холодной загрузке модели рассуждений, затем «Составляю план... (Nс)» до появления плана (SSE-события `task_stage`, снимаются, как только план готов или фаза завершилась неудачей).
4. Живой статус показывается у каждого элемента списка: ⏳ в очереди / ▶ Выполняется (шаг n из m) / ⏸ Приостановлено / ⏳ Ожидает ответа / ✔ Завершено / ✖ Ошибка / ✖ Отменено / ⏰ Время истекло. Пока задача планируется, статусная строка показывает «Составляю план…»; нефинальные статусы пульсируют, как статусные сообщения чата. Кроме того, у каждой строки перед заголовком есть мерцающий значок, как у карточек сессий: ⚡ выполняется, ❓ ждёт ответа, ⏳ в очереди со своей позицией (порядок исполнителя — класс, затем FIFO).
5. Когда модель задаёт уточняющий вопрос, задача показывает «Ожидает ответа» со счётчиком секунд, а поле ввода сообщений становится полем ответа («Ответьте на уточнение…»). Ответьте — и задача продолжится. Уточняющий вопрос возникает двумя путями: планировщик закладывает его в план, или **верификатор запрашивает недостающие данные пользователя** посреди шага — шаг прерывается (попытка не считается), вопрос задаётся дословно, и после ответа **тот же шаг выполняется заново** с ним.
6. ■ (Остановить задачу) отменяет идущую или ожидающую задачу; 🗑️ удаляет её (нефинальная задача сначала отменяется, затем удаляется вместе со всей перепиской). Удаление задачи, открытой в главном окне, открывает следующую задачу списка (или пустое состояние «задача не выбрана») — окно никогда не возвращается к сеансу чата.

## Приоритеты и вытеснение

- Класс приоритета задачи наследуется от сервис-класса пользователя при создании: `0 → 3`, `1 → 4`, `2 → 5`. Классы 3/4/5 — **внутренние** и в админ-панели не предлагаются — у пользователей остаются классы 0/1/2.
- **Активна глобально одна задача** (выбор: класс 3 раньше 5, затем FIFO). Ожидание ответа пользователя или заморозка освобождают слот для следующей задачи.
- **Тихое окно (скользящее):** после последнего запроса в чат задача может стартовать/возобновиться, только если за `TASK_QUIET_PERIOD_S` (по умолчанию 15 с) не было новых запросов в чат, очереди чата пусты и GPU свободен. Любой новый запрос в чат сбрасывает окно и **прерывает идущий шаг**: его частичный результат отбрасывается, шаг помечается `interrupted` (причина `chat`) и возобновляется с нуля. Чат никогда не ждёт задачу.
- **Бюджет:** задача может накопить не более `TASK_TOTAL_BUDGET_S` (по умолчанию 24 ч) **чистого исполнения** — ожидания, заморозки и время ожидания ответа пользователя не учитываются. По исчерпании задача получает статус `expired`, и из промежуточных результатов генерируется финальная сводка.

## Что происходит внутри

1. **Планирование** — вызов модели рассуждений раскладывает запрос на шаги (название, цель, одна способность на шаг, у каждого проверяемый `checkpoint_criteria`). Нехватка информации становится уточняющим вопросом. Вызов жадный (`temperature=0`): один и тот же запрос даёт один и тот же план, а все текстовые поля плана (название, цели, критерии) выдержаны на языке задачи — реестр способностей тоже отдаётся на этом языке (англоязычный блок реестра в русском промпте планирования однажды утянул в английский весь план, и каждый медиашаг затем использовал английскую цель как свой запрос).
2. **Шаги** — каждый шаг выполняет одну способность из реестра (`app/tasks/tools.py`):

| Инструмент | Что делает |
|------|--------------|
| `llm` | вызов модели рассуждений с накопленными промежуточными результатами (мультимодальная — только если шаг должен разглядывать ранее созданные изображения) |
| `search` | поиск в интернете (Tavily → откат на SearXNG) |
| `rag` | поиск по собственным документам пользователя — приложенные к задаче документы задают область, а если ничего не приложено, идёт поиск по всем проиндексированным документам с покрытием файлов (правило RAG как в чате); следующий шаг `llm` формулирует ответ по найденным фрагментам |
| `history` | поиск по прошлым перепискам пользователя (CPU-only полнотекстовый поиск PostgreSQL, зеркало пути `[-HISTORY-]` чата); цель-джокер или отсутствие прямых совпадений откатывается к компактному обзору последних сессий; ответ формулирует следующий шаг `llm` |
| `camera` | снимок одной указанной комнаты делается и описывается мультимодальной моделью как подзадача очереди (`camera_task`); планировщик создаёт один шаг на комнату (список комнат пользователя подмешивается в промпт планирования). Комната распознаётся из цели шага с учётом склонений (родительный «кухни» находит сохранённую «кухню»); вопрос для анализа приходит из названия задачи, а не сырой императивной цели (она уводит классификатор изображений к маршрутизационному маркеру), а ошибочное эхо-обращение срезается одним ретраем с чистым аналитическим промптом |
| `vision` | изображения, приложенные к задаче в окне задачи (чипы как в чате), ЧИТАЮТСЯ мультимодальной моделью как подзадача очереди (`vision_task`): возвращается двухсекционное извлечение — подробное описание всего видимого плюс весь текст на изображении — и шаг никогда не отвечает на цель плана; ответ формирует следующий `llm`-шаг по этому извлечению. Один вызов на изображение — промпт извлечения требует ровно одного блока описания, поэтому совместный вызов над несколькими описал бы только первое из них, — и перед каждым извлечением стоит имя файла, записанное вызывающим кодом, а не моделью. Шаг читает только те изображения, чьё имя файла названо в его цели: планировщик ставит ОДИН шаг `vision` на изображение и указывает в цели имя его файла (тот же приём, что «один шаг на комнату» у камеры), а цель без имени файла читает все изображения; в промпте планирования указывается ТОЛЬКО когда есть вложения; эхо маршрутизационного маркера в результате срезается (пользователю не показывается) |
| `crawl` | глубокое изучение сайта через sidecar Crawl4AI как подзадача очереди (`crawl_task`); собранные страницы становятся результатом шага (без перезаказа рассуждений) и индексируются как документ пользователя |
| `calculate` | безопасный AST-калькулятор; планировщик записывает в цель шага чистое выражение («2 + 2 * 2»), а прозаичная цель откатывается к извлечению выражения из текста |
| `rlm` | Глубокий анализ как подзадача очереди |
| `image_gen` / `image_edit` / `video_gen` | медиа-подзадачи через существующую GPU-очередь. Если приложено несколько изображений, `image_edit` редактирует то, чьё имя названо в цели (один шаг на изображение, как у `vision`), а при цели без имени — первое приложенное. Шаг, привязанный планом к шагу-источнику (`source_step`), у которого источник не создал изображение, **пропускается** — в причине назван этот шаг, для пропущенного шага ничего не ставится в очередь, а задача продолжается (финальная сводка объясняет отсутствие медиа); у `video_gen` без такой привязки сохраняется откат к генерации из текста, как в чате |

### Контекст и проверка медиашагов

Медиашаг получает результат объявленного `source_step` первым (до 12 000 символов из бюджета `MEDIA_CONTEXT_CHARS` = 16 000, остаток заполняет дайджест прочих шагов), поэтому длинный результат шага-источника не может вытеснить из промпта ту часть, которую шаг иллюстрирует. Каждое созданное изображение затем описывается мультимодальной моделью через структурированный `task_describe_image.template` (объекты, количество, действия, обстановка, стиль, видимый текст) и оценивается в фиксированном порядке: сначала — против ожидаемого содержимого (**фрагмента** результата шага-источника, названного целью и критерием шага; цель и критерий передаются отдельными полями), потом — против промпта, который реально получил генератор (`backend_prompt` в конверте подзадачи). Промпт генератора — вспомогательный контекст, а не эталон: расхождение с ним при соответствии эталону, цели и критерию не является провалом. Медиашаг без привязки к источнику оценивается по своей цели, а шаг правки — по запрошенному изменению, поэтому корректная картинка не отклоняется за законное расхождение с эталоном. Отклонённый артефакт открывает **цикл исправления**. Каждое расхождение несёт `severity` (`critical`/`minor`) и флаг `repairable`: локальный дефект — лишний или дублированный объект, неверный текст/время на объекте, цвет, мелкая деталь — сначала исправляется **редактированием текущей картинки** (один edit после каждой генерации, `TASK_STEP_MAX_REPAIRS` = 3, `strength` ограничен 0.35–0.5, дефект в `edit_prompt`, сцена/стиль/объекты в `preserve`); неверная композиция (не та сцена, персонаж, количество или действие) сразу идёт в следующую генерацию. Цикл: генерация → edit → генерация → edit → генерация → edit, причём неудачный edit не расходует попытку генерации (≤ `TASK_STEP_MAX_ATTEMPTS` = 3). Промпт генератора — вспомогательный контекст, не эталон. Если все попытки провалились, шаг **не** помечается failed: все кандидаты (3–6 картинок) ранжируются по `score` верификатора (при равенстве — меньше critical, затем меньше minor, затем более поздняя попытка), и самый близкий становится артефактом шага с пометкой «best effort» — последняя попытка не считается лучшей автоматически. Проигравшие файлы удаляются. Повторный отказ с той же причиной тоже принимается. Финальный SD-промпт проверяется по листу непрерывности до диффузии: объекту, выпавшему при переформулировке, детерминированно дописывается его look. Осмотр артефактов — реестр (`app/tasks/artifacts.py:ARTIFACT_INSPECTORS`): пустой критерий больше не отменяет проверку, тип шага без записи в реестре (камера, vision) не проверяется, неудавшееся описание пропускает проверку вместо провала шага, а новый тип артефакта добавляется одной регистрацией.

### Визуальная непрерывность (внутренний механизм)

Задача, которая планирует несколько сгенерированных изображений, сохраняет их визуальную согласованность с помощью внутреннего листа непрерывности: один стиль плюс фиксированный облик каждого персонажа, места и предмета, названного в запросе. Лист извлекается одним вызовом модели рассуждений **перед первым шагом `image_gen`** и только если в плане два и более генерируемых изображения; план из одних редактирований лист не извлекает, чтобы придуманный стиль не менял фотографии пользователя. Лист хранится в задаче (`tasks.visual_bible`) и подставляется в промпт каждого шага генерации изображения, поэтому последующие сцены сохраняют тех же персонажей и стиль. Это guard, а не шаг плана: планировщику возможность `continuity` не предлагается, а извлечение никогда не появляется ни в плане, ни в заголовках «Шаг N из M», ни где-либо в окне задачи. Переменные: `TASK_CONTINUITY_ENABLED` (вкл/выкл), `TASK_CONTINUITY_MAX_CHARS` (бюджет листа).

### Долговременная память (SLM)

Задачи разделяют профиль SuperLocalMemory с чатом. Напомненные факты встраиваются в промпты планирования, шага (`llm`) и финальной сводки точно как в чате (сначала сессионные, не больше `SLM_RECALL_LIMIT`); без SLM секция пуста, а ошибка recall никогда не роняет задачу. Пройденные шаги `llm` и финальные сводки запускают то же правило-базированное фоновое извлечение фактов, что и ответы чата, — утверждения пользователя задаче («я не ем грибы») попадают в ту же персональную память. Факты извлекаются только из запроса пользователя, никогда из ответа модели; тексты ошибок «⚠️» и фрагменты инструментов (search/rag/calculate) памятью не являются.

3. **Контрольная точка** — короткий вызов модели рассуждений проверяет результат шага по `checkpoint_criteria`; при провале шаг перезапускается с описанием расхождения (до `TASK_STEP_MAX_ATTEMPTS` = 3 попыток), затем помечается `failed`, и задача продолжается. Верификатор — текстовый вызов, поэтому для медиашага созданное изображение сначала описывает мультимодальная модель, и это описание добавляется к входу верификатора (шаг отклонялся с «в результате нет изображения и его описания», хотя его артефакт шёл в следующие шаги). Для сгенерированного видео репрезентативный (средний) кадр возвращается видео-обёрткой как `preview_data` и описывается так же — без этого верификатор видел только цель, и его вердикт был случайным (5 из 10 видеошагов провалились, хотя mp4 существовал). Когда провал означает **нехватку данных пользователя** (а не ошибку модели), верификатор возвращает третий вердикт `needs_user_input`: шаг приостанавливается как `awaiting_user`, в переписку добавляется дословный вопрос, и после ответа тот же шаг выполняется заново с ним (приостановленная попытка не учитывается в лимите 3 попыток).
4. **Финал** — ответ/действие на основе накопленных результатов со ссылками на медиа; задача становится `completed`. Финальная сводка, которая лишь повторяет ответ последнего шага, распознаётся и подавляется (ответ шага показывается один раз, со своей шапкой-метаданными). Промпты шага и финала требуют математику и формулы обычным текстом (без LaTeX — в веб-интерфейсе нет рендера формул, поэтому `$…$`/`\times` доходили бы до пользователя сырой разметкой).

Медиа-подзадачи выполняются в существующей очереди с классом задачи (3/4/5). Защита на медленном worker'е не даёт им стартовать при закрытом шлюзе — они ждут в списке отложенных и возвращаются в очередь, когда в чате наступает тишина. ■ Остановка и 🗑️ удаление отменяют подзадачу, уже поставленную идущим шагом в очередь, а worker отбрасывает помеченный запрос, чей шаг исчез (или уже не в статусе «в очереди/выполняется»), — поэтому удалённая задача не может оставить «сироту», держащую медленный worker и GPU. Медиа-подзадача возвращает свой артефакт в конверте результата (`extra.media` шага), а не пишет сообщение в чат — у шага задачи нет чат-сессии, такая строка была бы сиротской.
Занятая GPU никогда не становится провалом шага: подзадача, чья проверка живости не смогла ответить (сбой Redis), опрашивается заново до `TASK_SUBTASK_ALIVE_UNKNOWN_MAX` циклов, вместо того чтобы признать результат просроченным за миллисекунды до его появления; провал проверки работоспособности sd-wrapper (обёртка однопоточная и не может ответить на `/health`, пока рисует) больше не блокирует запрос генерации; а любое ожидание VRAM (`ensure_vram_for`, собственный шлюз очереди, шлюз видео) использует `VRAM_WAIT_TIMEOUT_S` (120 с) и возвращается, как только память освободится — фиксированные дедлайны 15/30 с приводили к провалу задачи, пока 12-гигабайтная модель рассуждений ещё выгружалась.

## Хранение и восстановление

`tasks` + `task_steps` (PostgreSQL) хранят всё состояние; исполнитель **возобновляет работу после перезапуска** — каждый шаг, оставшийся в работе (прямой в статусе `running` или очередь-подзадача в `subtask_queued`/`subtask_running`, чей запрос погиб вместе с worker'ом), получает новую попытку с причиной `restart`. В бюджет идёт только реальное время каждой попытки, поэтому перезапуски никогда не съедают 24-часовой бюджет. Переписка рендерится из `task_steps` — параллельной таблицы сообщений нет. Обе таблицы входят в полные бэкапы.

## Корректировка плана

Работающая задача сама пересматривает свой оставшийся план. Проверка запускается после **проваленного или пропущенного шага**, **нового ответа пользователя**, **исчерпанного плана** (он ещё может вырасти) и после каждого информационного шага (`llm`, `rlm`, `rag`, `search`, `crawl`, `history`); обычный успешный медиашаг запускает её только раз в `TASK_REPLAN_EVERY_N` шагов (по умолчанию 3). Перед проверкой и перед составлением финального ответа один вызов модели рассуждений (`prompts/{en,ru}/task_replan.template`, жадное декодирование) видит запрос пользователя, выполненные шаги с их результатами, ответы пользователя на уточняющие вопросы и оставшиеся шаги, пронумерованные по их **глобальной** позиции в плане. Он отвечает либо `{"changed": false}` (план остаётся), либо `{"changed": true, "reason": "...", "steps": [...]}` с **полным** новым хвостом плана; пустой список — допустимый ответ, означающий «оставшейся работы нет», и задача завершается. Отсутствие `reason` записывается как `unspecified` и не блокирует исправление.

- **Только вперёд.** Менять можно лишь ещё не выполненный хвост; выполненный шаг сохраняет свою строку, свою цель и свой результат. Перезапись удаляет устаревшие *ожидающие* строки шагов (терминальные строки не трогаются никогда) и создаёт новые строки для нового хвоста с правильным видом по способности — медиашаг уходит в очередь, шаг с `user_input_expected` становится уточняющим вопросом.
- **Ревизия — не второй планировщик.** Она никогда не планирует заново: хвост меняется только тогда, когда выполнение уже открыло требующий этого факт — результат шага называет объём работы, которого в плане нет, ответ пользователя просит работу, которой не покрывает ни один шаг (или план не покрывает найденный объём: найдено 10 сцен, а шагов рисования 4), или оставшийся шаг стал ненужен или невозможен. Если всё идёт по плану — не меняется ничего.
- **Плохая ревизия никогда не вредит задаче.** Неразбираемый ответ, ответ с несуществующей способностью, отсутствие поля `steps` или ошибка транспорта — всё это сохраняет текущий план, и задача продолжает работу: ревизия не может провалить задачу, и её ошибка никогда не показывается пользователю.
- **Ревизор видит самые свежие факты.** Его дайджест результатов взвешен к концу (последняя часть результатов, а не первые, что важно для задачи, идущей часами), и ответы пользователя идут вместе с ним. Ревизия разделяет с планировщиком контракт 🔬 Глубокого анализа и тот же реестр способностей.
- **Ограничители.** Ревизия запускается под теми же тремя ограничителями, что и старт шага — бюджет выполнения, шлюз тишины и флаг отмены, — поэтому ни один вызов модели не идёт при закрытом шлюзе; ревизия, срок которой наступил при закрытом шлюзе, ждёт и запускается, когда он откроется. Остановка пользователем во время ревизии чисто отменяет задачу. Рост ограничен `TASK_MAX_REVISIONS` (по умолчанию 8 принятых перезаписей), `TASK_MAX_STEPS` (по умолчанию 40) и 24-часовым `TASK_TOTAL_BUDGET_S`; когда лимит ревизий исчерпан, проверка пропускается и текущий план окончателен. Пока идёт ревизия, баннер статуса показывает обычную стадию планирования (загрузка модели рассуждений, затем «Составляю план…») — нового статуса не добавлялось.
- **Перефразирование — не новая работа.** Шаг, чей tool и набор лемм goal повторяют уже выполненный шаг, отбрасывается; дубли внутри нового хвоста тоже отбрасываются, а сравнение хвоста (`_same_plan_tail`) идёт по леммам — «нарисуй сцену 3» и «нарисовать сцену 3» читаются как «без изменений». Перезапись, не оставившая новых шагов, сохраняет план и не добавляет уведомление о ревизии.
- **Что видит пользователь.** Каждая применённая перезапись добавляет в переписку задачи служебную строку «План обновлён (N шагов).», привязанную сразу после шага, который её вызвал. Сообщение плана и заголовки «Шаг N из M» рендерятся из **текущего** плана, поэтому все последующие статусные сообщения уже следуют новому плану.
- **Переделка — не новая позиция плана.** Ревизору предписано повторять goal неудавшегося шага **дословно**; `_apply_replan` распознаёт дословный повтор goal только что выполненного шага (тот же tool), переоткрывает его строку (`status=pending`, `attempts=0`, `extra.redos+1`, уточнённый критерий ревизора применяется на месте), убирает дубль из хвоста и продолжает с той же позиции. Число таких переоткрытий ограничено `TASK_STEP_REDO_MAX` (по умолчанию 1); когда лимит исчерпан, дубль отбрасывается, а шаг остаётся failed. До этого каждая переделка становилась новой строкой со сброшенным счётчиком попыток — сцену можно было генерировать шесть раз через два «шага», — а план содержал одну и ту же цель дважды.

## Примечания

- Медиа задач (созданные изображения и видео, снимки камер, любой другой артефакт медиа-подзадачи) живут в обычной папке загрузок под id самой задачи — `<UPLOAD_FOLDER>/<id_задачи>/…`, потому что сессия очереди у подзадачи и есть id задачи, — и указываются в `extra.media` шага, поэтому рендерятся в сообщении шага как в чате (`.image-container` + модальное окно увеличения), а `/api/files` проверяет владельца по таблице `tasks`, когда сессия чата не нашлась. Удаление задачи удаляет и её переписку (шаги и сообщения чата, которые упавший шаг записал под id задачи, удаляются вместе с ней — больше эти строки никто не читает).
- Документы и изображения прикладываются так же, как в чате (чипы в окне задачи). Изображения уходят в запрос/ответ как multipart `images` (≤ `MAX_CHAT_IMAGES`, квота и даунскейл как в чате, на диске хранится `{file_path, file_name}` — байты никогда не попадают в БД), а планировщик анонсирует способность `vision` только при наличии картинок. Документ, приложенный скрепкой, становится **полноценным документом пользователя** ровно по цепочке панели «Документы» (проверка файла, лимит размера и квота, хранение в `DOCUMENTS_FOLDER/<login>/<id><ext>`, строка в `documents`, постановка `index_document` в очередь); сохраняется только его id, и он вливается **первым** в `tasks.doc_ids` перед выделением панели «Документы», поэтому вложение никогда не означает молча «все документы». `doc_ids` может также заполняться из выделения панели «Документы» в момент отправки запроса/ответа; пустой набор означает «искать по всем документам пользователя» — то же правило, что использует чат для RAG. В сообщении запроса вложения рендерятся отдельными служебными строками — «Приложенные изображения: …» и «Приложенные документы: …» (шрифт строки плана, маркер 📎, заголовок отдельной строкой и по одному имени файла в строке; локализованные строки строит сервер, в текст запроса они не подмешиваются). Шаг `rag` дожидается, пока свежие вложения задачи покинут состояния индексации, и только потом ищет, а шаг `rlm` так же ждёт перед чтением своего корпуса (у сканированного PDF нет текста на диске, пока не завершён его OCR) — оба ожидания ограничены `OCR_TIME_BUDGET_S` и прерываются, как только запрос в чат закрывает шлюз: шаг помечается `interrupted` и возобновляется с нуля.
- Аудио и голос прикладываются так же, как в чате (чипы, скрепка или микрофон): они уходят в запрос/ответ как multipart `audio`, сохраняются в папку задачи и расшифровываются фоновой нитью (Whisper-сайдкар — HTTP-вызов, без GPU-блокировки; видеоконтейнер расшифровывается по своей аудиодорожке). **Расшифровка — контекст задачи, а не документ панели «Документы», и никогда не индексируется** (то же правило, что у описания изображения). Пока Whisper работает, задача `frozen` (причина `audio_transcript`, в баннере — «Распознаю аудио…»): продиктованная голосом задача не может быть спланирована раньше появления её текста, поэтому планировщик читает расшифровку запроса как слова пользователя, а текстовая задача с аудиоматериалом («проанализируй аудиозапись …») получает расшифровку в контексте каждого шага. Задача, продиктованная без текста, берёт заголовок из расшифровки; аудио-ответ дописывается к шагу ответа (контракт описания изображений). В одной отправке — не более `MAX_CHAT_AUDIO` (4) аудиоэлементов: одна запись плюс аудиофайлы (1 голосовое + 3 файла или 4 файла); при превышении отправка отклоняется локализованным сообщением `max_audio_reached` до сохранения файлов. Сообщение запроса/ответа рендерит запись как «Приложенные аудиозаписи: …» (служебная строка 📎), а саму расшифровку — «🎤 Распознано (имя): …» обычным шрифтом чтения; неудача расшифровки завершает задачу локализованной ошибкой ⚠️ вместо постановки пустого запроса в очередь.
- Галочка 🔬 **Глубокий анализ** доступна при отправке задачи/ответа как в чате: в момент запроса планировщик получает указание включить шаг `rlm` по документам задачи; при наличии плана ответ с галочкой добавляет шаг `rlm` (идемпотентно — не более одного). Вызов `final()` с пустым ответом получает один подгоняющий нудж («составь содержательный ответ») до того, как прогон упадёт.
- Обновления задач приходят в тот же персональный SSE-поток, что и события чата (тип `task_update`) — список и открытая переписка обновляются без опроса. Обновления статуса/плана/шагов публикуются **во время** исполнения (начало планирования, появление плана, постановка шага в очередь, переход в «выполняется» и завершение шага), а не одним блоком в конце.
- Сообщения задач показывают время исполнения и расход токенов по шагу (шапка как в чате), а финальный ответ не повторяет дословно результат последнего шага. Ошибочный шаг с пустым результатом показывает свой `last_error`, а не остаётся пустым. **Итог в заголовке списка задач** суммирует каждый LLM-вызов задачи: модели шагов, их верификаторы (`extra.checkpoint_usage`), планировщик (`step_plan.plan_meta`) и каждую принятую ревизию плана (`step_plan.revision_meta`); корректирующие попытки накапливаются в `usage_total` / `checkpoint_usage_total`, поэтому отклонённые генерации не теряются. Вкладка Users в админ-панели добавляет тот же расход задач и плана к токенам чата.
- **Каждый шаг объясняет своё состояние проверки.** На строке шага — чип: `✅ проверено автоматически`, `🔁 переделано ×N`, `🔁 переделываю N/M`, `✖️ не выполнено`, `⏭ пропущено`, `⏸ прервано`, `⚠️ без проверки` — под ним причина последнего отклонения (для идущей переделки: «Автопроверка не пройдена: <причина>. Переделываю (попытка N из M)»; после успеха: «Переделано после проверки: <причина>»), плюс свёрнутый журнал попыток (`extra.attempts_log`, последние десять записей, пишется при каждом вердикте). `⚠️ без проверки` означает, что описание артефакта получить не удалось и проверка пропущена — шаг не провален, попытки не потрачены.
- **Финальный ответ завершается принятыми результатами.** Финальный шаг несёт `extra.final_items` — прошедший проверку шаг с файлом становится карточкой (подпись — цель шага, при переделках бейдж `🔁 переделано ×N`), прошедший текстовый шаг — строкой с кратким итогом, — и `extra.final_failures` — одной сноской о том, что не получилось. Правило — «прошедший проверку шаг, который что-то произвёл», а не «у сцены есть картинка», поэтому секция одинакова для задач любой формы. Сводка для модели описывает только прошедшие шаги и отдельно перечисляет недоставленное; модели запрещено перечислять принятые результаты — интерфейс показывает их сам.
- Внутренний API живёт на `/api/tasks*` (сессионная авторизация, доступ владельцу, как у сессий); публичного API задач в `/v1` **в этой версии нет**.
- Реестр способностей — место для будущей концепции **навыков (skills)**: навык будет именованным набором способностей в том же реестре без изменений хранения.

## Настройка
