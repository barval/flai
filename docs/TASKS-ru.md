# Фоновые задачи (Задачи)

**Для чего?** Некоторые работы слишком велики для одного запроса в чате: подготовить отчёт на 10 страниц из нескольких источников, изучить тему по десятку веб-страниц и составить структурированную справку, сгенерировать набор изображений и описать их. **Задачи** — это долгоиграющие фоновые работы: вы описываете желаемый результат, система раскладывает запрос на план из шагов и выполняет их по очереди с **более низким приоритетом, чем чат** — задача никогда не заставляет ваш запрос в чате ждать, а любой запрос в чате замораживает идущую задачу и забирает ресурсы себе.

## Как пользоваться

1. Откройте вкладку **Задачи** в левой колонке (между **Документами** и **Сессиями**), нажмите ➕ и опишите желаемый результат. Вкладка заново открывает последнюю открытую задачу (в том числе после перезагрузки страницы) — как чат открывает свой последний сеанс; пустое состояние показывается только когда восстанавливать нечего.
2. Можно также создать задачу и описать её позже: ➕ открывает **черновик** (статус «draft», поле ввода становится полем описания); отправка описания ставит задачу в очередь.
3. Задача планируются и начинает выполняться. Её переписка открывается в главном окне и выглядит как обычный чат: запрос пользователя, сообщение «План из N шагов:», затем результат каждого шага с префиксом «Шаг N из M:» и финальный ответ. Префиксы плана/шага рендерятся отдельной курсивной сервисной строкой, а каждое сообщение ассистента несёт такую же шапку, как в чате: 📅 дата | имя модели | ⏱️ время исполнения | 🔢 расход токенов | 🚀 ток/с, плюс кнопки 🗣️ (озвучить) и 📋 (копировать). Поля шапки независимы друг от друга — финальная сводка показывает свои токены, хотя отдельного времени у неё нет. Шаг, выполненный инструментом, а не моделью рассуждений (calculate, search, медиа-подзадача), называет этот инструмент — локализовано и с эмодзи — отдельной курсивной строкой сразу под строкой шага (тем же шрифтом, что и «⚙️ Шаг N из M:»), например «🔎 Веб-поиск:», а его шапка показывает модель и токены верификатора-проверяющего (единственный вызов модели на таком шаге).
4. Живой статус показывается у каждого элемента списка: ⏳ в очереди / ▶ Выполняется (шаг n из m) / ⏸ Приостановлено / ⏳ Ожидает ответа / ✔ Завершено / ✖ Ошибка / ✖ Отменено / ⏰ Время истекло. Пока задача планируется, статусная строка показывает «Составляю план…»; нефинальные статусы пульсируют, как статусные сообщения чата. Кроме того, у каждой строки перед заголовком есть мерцающий значок, как у карточек сессий: ⚡ выполняется, ❓ ждёт ответа, ⏳ в очереди со своей позицией (порядок исполнителя — класс, затем FIFO).
5. Когда модель задаёт уточняющий вопрос, задача показывает «Ожидает ответа» со счётчиком секунд, а поле ввода сообщений становится полем ответа («Ответьте на уточнение…»). Ответьте — и задача продолжится. Уточняющий вопрос возникает двумя путями: планировщик закладывает его в план, или **верификатор запрашивает недостающие данные пользователя** посреди шага — шаг прерывается (попытка не считается), вопрос задаётся дословно, и после ответа **тот же шаг выполняется заново** с ним.
6. ■ (Остановить задачу) отменяет идущую или ожидающую задачу; 🗑️ удаляет её (нефинальная задача сначала отменяется, затем удаляется вместе со всей перепиской).

## Приоритеты и вытеснение

- Класс приоритета задачи наследуется от сервис-класса пользователя при создании: `0 → 3`, `1 → 4`, `2 → 5`. Классы 3/4/5 — **внутренние** и в админ-панели не предлагаются — у пользователей остаются классы 0/1/2.
- **Активна глобально одна задача** (выбор: класс 3 раньше 5, затем FIFO). Ожидание ответа пользователя или заморозка освобождают слот для следующей задачи.
- **Тихое окно (скользящее):** после последнего запроса в чат задача может стартовать/возобновиться, только если за `TASK_QUIET_PERIOD_S` (по умолчанию 60 с) не было новых запросов в чат, очереди чата пусты и GPU свободен. Любой новый запрос в чат сбрасывает окно и **прерывает идущий шаг**: его частичный результат отбрасывается, шаг помечается `interrupted` (причина `chat`) и возобновляется с нуля. Чат никогда не ждёт задачу.
- **Бюджет:** задача может накопить не более `TASK_TOTAL_BUDGET_S` (по умолчанию 24 ч) **чистого исполнения** — ожидания, заморозки и время ожидания ответа пользователя не учитываются. По исчерпании задача получает статус `expired`, и из промежуточных результатов генерируется финальная сводка.

## Что происходит внутри

1. **Планирование** — вызов модели рассуждений раскладывает запрос на шаги (название, цель, одна способность на шаг, у каждого проверяемый `checkpoint_criteria`). Нехватка информации становится уточняющим вопросом.
2. **Шаги** — каждый шаг выполняет одну способность из реестра (`app/tasks/tools.py`):

| Инструмент | Что делает |
|------|--------------|
| `llm` | вызов модели рассуждений с накопленными промежуточными результатами (мультимодальная — только если шаг должен разглядывать ранее созданные изображения) |
| `search` | поиск в интернете (Tavily → откат на SearXNG) |
| `rag` | поиск по собственным документам пользователя — приложенные к задаче документы задают область, а если ничего не приложено, идёт поиск по всем проиндексированным документам с покрытием файлов (правило RAG как в чате); следующий шаг `llm` формулирует ответ по найденным фрагментам |
| `history` | поиск по прошлым перепискам пользователя (CPU-only полнотекстовый поиск PostgreSQL, зеркало пути `[-HISTORY-]` чата); цель-джокер или отсутствие прямых совпадений откатывается к компактному обзору последних сессий; ответ формулирует следующий шаг `llm` |
| `camera` | снимок одной указанной комнаты делается и описывается мультимодальной моделью как подзадача очереди (`camera_task`); планировщик создаёт один шаг на комнату (список комнат пользователя подмешивается в промпт планирования). Комната распознаётся из цели шага с учётом склонений (родительный «кухни» находит сохранённую «кухню»); вопрос для анализа приходит из названия задачи, а не сырой императивной цели (она уводит классификатор изображений к маршрутизационному маркеру), а ошибочное эхо-обращение срезается одним ретраем с чистым аналитическим промптом |
| `vision` | изображения, приложенные к задаче в окне задачи (чипы как в чате), анализируются мультимодальной моделью как подзадача очереди (`vision_task`): один совместный вызов для нескольких изображений, откат к поизображенческим описаниям; в промпте планирования указывается ТОЛЬКО когда есть вложения; эхо маршрутизационного маркера в ответе срезается (пользователю не показывается) |
| `crawl` | глубокое изучение сайта через sidecar Crawl4AI как подзадача очереди (`crawl_task`); собранные страницы становятся результатом шага (без перезаказа рассуждений) и индексируются как документ пользователя |
| `calculate` | безопасный AST-калькулятор; планировщик записывает в цель шага чистое выражение («2 + 2 * 2»), а прозаичная цель откатывается к извлечению выражения из текста |
| `rlm` | Глубокий анализ как подзадача очереди |
| `image_gen` / `image_edit` / `video_gen` | медиа-подзадачи через существующую GPU-очередь |

### Долговременная память (SLM)

Задачи разделяют профиль SuperLocalMemory с чатом. Напомненные факты встраиваются в промпты планирования, шага (`llm`) и финальной сводки точно как в чате (сначала сессионные, не больше `SLM_RECALL_LIMIT`); без SLM секция пуста, а ошибка recall никогда не роняет задачу. Пройденные шаги `llm` и финальные сводки запускают то же правило-базированное фоновое извлечение фактов, что и ответы чата, — утверждения пользователя задаче («я не ем грибы») попадают в ту же персональную память. Факты извлекаются только из запроса пользователя, никогда из ответа модели; тексты ошибок «⚠️» и фрагменты инструментов (search/rag/calculate) памятью не являются.

3. **Контрольная точка** — короткий вызов модели рассуждений проверяет результат шага по `checkpoint_criteria`; при провале шаг перезапускается с описанием расхождения (до `TASK_STEP_MAX_ATTEMPTS` = 3 попыток), затем помечается `failed`, и задача продолжается. Когда провал означает **нехватку данных пользователя** (а не ошибку модели), верификатор возвращает третий вердикт `needs_user_input`: шаг приостанавливается как `awaiting_user`, в переписку добавляется дословный вопрос, и после ответа тот же шаг выполняется заново с ним (приостановленная попытка не учитывается в лимите 3 попыток).
4. **Финал** — ответ/действие на основе накопленных результатов со ссылками на медиа; задача становится `completed`. Финальная сводка, которая лишь повторяет ответ последнего шага, распознаётся и подавляется (ответ шага показывается один раз, со своей шапкой-метаданными). Промпты шага и финала требуют математику и формулы обычным текстом (без LaTeX — в веб-интерфейсе нет рендера формул, поэтому `$…$`/`\times` доходили бы до пользователя сырой разметкой).

Медиа-подзадачи выполняются в существующей очереди с классом задачи (3/4/5). Защита на медленном worker'е не даёт им стартовать при закрытом шлюзе — они ждут в списке отложенных и возвращаются в очередь, когда в чате наступает тишина.

## Хранение и восстановление

`tasks` + `task_steps` (PostgreSQL) хранят всё состояние; исполнитель **возобновляет работу после перезапуска** — прерванный шаг получает новую попытку с причиной `restart`. В бюджет идёт только реальное время каждой попытки, поэтому перезапуски никогда не съедают 24-часовой бюджет. Переписка рендерится из `task_steps` — параллельной таблицы сообщений нет. Обе таблицы входят в полные бэкапы.

## Примечания

- Медиа задач (созданные изображения/видео) живут в обычной папке загрузок со ссылками в `extra` шага; удаление задачи удаляет и её переписку (шаги удаляются вместе с ней). Снимки камер сохраняются на диск так же (`<UPLOAD_FOLDER>/<id_задачи>/…`), и картинка, и видео рендерятся в сообщении шага как в чате (`/api/files` при поиске владельца проверяет и таблицу `tasks`, если сессия не нашлась — id задачи и есть имя папки).
- Документы, приложенные к задаче, снимаются из выделения панели «Документы» (`tasks.doc_ids`) в момент отправки запроса/ответа; пустой набор означает «искать по всем документам пользователя» — то же правило, что использует чат для RAG. Изображения прикладываются так же, как в чате (чипы в окне задачи): запрос и ответ на уточнение принимают multipart `images` (≤ `MAX_CHAT_IMAGES`, квота и даунскейл как в чате, на диске хранится `{file_path, file_name}` — байты никогда не попадают в БД), сообщение запроса показывает «Приложенные изображения: …», а планировщик анонсирует способность `vision` только при наличии картинок.
- Галочка 🔬 **Глубокий анализ** доступна при отправке задачи/ответа как в чате: в момент запроса планировщик получает указание включить шаг `rlm` по документам задачи; при наличии плана ответ с галочкой добавляет шаг `rlm` (идемпотентно — не более одного). Вызов `final()` с пустым ответом получает один подгоняющий нудж («составь содержательный ответ») до того, как прогон упадёт.
- Обновления задач приходят в тот же персональный SSE-поток, что и события чата (тип `task_update`) — список и открытая переписка обновляются без опроса. Обновления статуса/плана/шагов публикуются **во время** исполнения (начало планирования, завершение каждого шага), а не одним блоком в конце.
- Сообщения задач показывают время исполнения и расход токенов по шагу (шапка как в чате), а финальный ответ не повторяет дословно результат последнего шага. Ошибочный шаг с пустым результатом показывает свой `last_error`, а не остаётся пустым.
- Внутренний API живёт на `/api/tasks*` (сессионная авторизация, доступ владельцу, как у сессий); публичного API задач в `/v1` **в этой версии нет**.
- Реестр способностей — место для будущей концепции **навыков (skills)**: навык будет именованным набором способностей в том же реестре без изменений хранения.

## Настройка

Все параметры со значениями по умолчанию: `docs/CONFIGURATION-ru.md` («Фоновые задачи»). Аварийный выключатель `TASKS_ENABLED=0` останавливает подбор новых задач исполнителем.
