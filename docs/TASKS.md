# Background Tasks (Задачи)

**For what?** Some jobs are too big for one chat request: prepare a 10-page report from several sources, research a topic across a dozen web pages and draft a structured memo, generate a set of images and describe them. **Tasks** are long-running background jobs: you describe the result, the system decomposes the request into a plan of steps and executes them one by one at **lower priority than chat** — a task never makes your chat request wait, and any chat request freezes the running task and takes the resources back.

## How to use it

1. Open the **Задачи / Tasks** tab in the left column (between **Documents** and **Sessions**), press ➕ and describe the desired result. The tab reopens the task you last had open (also after a page reload) — like the chat reopens its last session; the empty state appears only when there is nothing to restore.
2. You can also create the task first and describe it later: ➕ opens a **draft** task (draft status, the input becomes the description box); sending the description enqueues the task.
3. The task is planned and starts running. Its conversation opens in the main window and looks like a normal chat: the user request, a «Plan of N steps:» message, then each step's output prefixed with «Шаг N из M:» (Step N of M), and the final answer. The plan/step prefixes are rendered as their own italic service line, and every assistant message carries the same header as chat messages: 📅 date | model name | ⏱️ execution time | 🔢 token usage | 🚀 tokens/s, plus 🗣️ (read aloud) and 📋 (copy) buttons. The plan message carries the header too — the executor stores the planner call's metadata (`plan_meta`: reasoning model name, wall-clock time, real token usage) with the plan and the messages route exposes it. User requests get the same 🗣️/📋 buttons as answers (both sides of `displayMessage` and `renderTaskMessage`); whisper transcriptions and system/error rows stay button-free. Each header field stands on its own — a final summary shows its tokens even though it has no separate duration. A step handled by a tool rather than the reasoning model (calculate, search, a media sub-task) names that tool — localized and with its emoji — on its own italic service line right below the step line (same font as «⚙️ Step N of M:»), e.g. «🔎 Web search:», and its header reports the checkpoint verifier's model and tokens (the only model call that step makes). Media and RLM steps report the model that actually produced the artifact: a camera/vision step shows the multimodal model (🖼️) with its real token totals, an image-gen step `SD_MODEL_TYPE` (🖌️), an image-edit step `flux-2-klein-4b` (🎨), a video step `LTX_VIDEO_MODEL` (🎥), an RLM step the reasoning model (🔬🧠). While the plan itself is being made, the status banner shows the live stage with a per-second counter — «Загружаю модель рассуждений... (Ns)» while the reasoning model cold-loads, then «Составляю план... (Ns)» until the plan appears (SSE `task_stage` events, cleared as soon as the plan arrives or the phase fails).
4. Live status is shown on each list item: ⏳ queued / ▶ Running (step n of m) / ⏸ Frozen / ⏳ Awaiting answer / ✔ Completed / ✖ Failed / ✖ Cancelled / ⏰ Expired. While the task is being planned, the status line shows «Составляю план…» (Making the plan…); non-terminal statuses pulse like chat stage labels. Each row also carries a blinking badge before its title, like the session cards: ⚡ running, ❓ awaiting an answer, ⏳ queued with its 1-based queue position (the executor's own order — class, then FIFO).
5. When the model asks a clarifying question, the task shows «Ожидает ответа» (Awaiting answer) with an elapsed-seconds counter and the message input becomes the answer box («Ответьте на уточнение…»). Answer and the task continues. A clarifying question can appear in two ways: the planner builds it into the plan, or **the verifier requests missing user data** mid-step — the step is interrupted (the attempt is not counted), the question is asked verbatim, and after the answer **the same step re-runs** with it.
6. ■ (Stop task) cancels a running or waiting task; 🗑️ deletes it (a non-terminal task is cancelled first, then removed with its whole conversation). Deleting the task that is open in the main window opens the next task of the list (or the «no task selected» empty state) — the window never falls back to a chat session.

## Priorities and preemption

- A task's priority class is derived from the user's service class at creation: `0 → 3`, `1 → 4`, `2 → 5`. Classes 3/4/5 are **internal** and never offered in the admin panel — users keep classes 0/1/2.
- **One task is active globally** (selection by class 3 before 5, then FIFO). Awaiting user input or being frozen releases the slot for the next task.
- **Quiet window (sliding):** after the last chat request, a task may start/resume only when `TASK_QUIET_PERIOD_S` (default 15 s) passed with no new chat requests, chat queues are empty and the GPU is free. Any new chat request resets the window and **aborts the in-flight step**: its partial output is discarded, the step is marked `interrupted` (reason `chat`) and re-executed from scratch on resume. Chat never waits for a task.
- **Budget:** a task may accumulate at most `TASK_TOTAL_BUDGET_S` (default 24 h) of **pure execution** — waits, freezes and awaiting-user time never count. On expiry the task is `expired` and a final summary is generated from the intermediate results.

## What happens inside

1. **Planning** — a reasoning-model call decomposes the request into steps (title, goal, one capability per step, a verifiable `checkpoint_criteria` each). Missing information becomes a clarifying question step.
2. **Steps** — each step runs one capability from the registry (`app/tasks/tools.py`):

| Tool | What it does |
|------|--------------|
| `llm` | reasoning-model call with the accumulated intermediate results (multimodal only when a step must inspect earlier produced images) |
| `search` | web search (Tavily → SearXNG fallback) |
| `rag` | search the user's own documents — the documents attached to the task scope it, and with none attached every indexed document is searched with file coverage (the chat's RAG rule); the following `llm` step composes the answer from the returned fragments |
| `history` | search the user's previous conversations (CPU-only PostgreSQL full-text search, mirrors the chat's `[-HISTORY-]` path); a wildcard goal or no direct matches degrades to a compact overview of recent sessions; the following `llm` step composes the answer |
| `camera` | a camera snapshot of one named room is taken and described by the multimodal model as a queue sub-task (`camera_task`); the planner emits one step per room (the user's room list is advertised in the planning prompt). The room is resolved from the step goal with declension-aware token matching (a genitive «кухни» finds the stored «кухня»); the analysis question travels from the task title, never the raw imperative goal (which misroutes the image classifier to a router marker), and a misrouted marker echo is stripped with one pure-analysis retry |
| `vision` | the images attached to the task in the task view (chat-style chips) are READ by the multimodal model as a queue sub-task (`vision_task`): it returns a two-section extraction — a detailed description of everything visible plus all text on the image — and never answers the planner goal; the following `llm` step composes the answer from the extraction. One call per image — the extraction prompt mandates exactly one description block, so a joint call over several images would describe only the first of them — and each extraction is preceded by the image's file name, written by the caller. The step reads only the images whose file name its goal names: the planner plans ONE vision step per image with that file name in the goal (the camera's one step per room pattern), and a goal naming no attached file reads them all; advertised in the planning prompt ONLY when images are attached; a router-marker echo in the result is stripped (never shown to the user) |
| `crawl` | deep site study through the Crawl4AI sidecar as a queue sub-task (`crawl_task`); the collected pages become the step result (no reasoning requeue) and index as a per-user document |
| `calculate` | the safe AST-based calculator; the planner puts the bare expression in the step goal («2 + 2 * 2»), and a prose goal falls back to extracting the math expression from the text |
| `rlm` | Deep Analysis run as a queue sub-task |
| `image_gen` / `image_edit` / `video_gen` | media sub-tasks through the existing GPU queue. With several images attached, `image_edit` edits the image its goal names (one step per image, like `vision`) and falls back to the first attached image when the goal names none |

### Long-term memory (SLM)

Tasks share the chat's SuperLocalMemory profile. Recalled facts are embedded in the planning, step (`llm`) and final-summary prompts exactly as in chat (session-specific first, capped at `SLM_RECALL_LIMIT`); the section is empty without SLM and a recall error never fails a task. Passed `llm` steps and final summaries trigger the same rule-based background fact extraction as chat answers — user statements made to a task («я не ем грибы») land in the same per-user memory. Facts are extracted from the user's request only, never from model output; ⚠️ error texts and tool fragments (search/rag/calculate) are not memories.

3. **Checkpoint** — a short reasoning call verifies the step result against `checkpoint_criteria`; on failure the step reruns with the mismatch description (up to `TASK_STEP_MAX_ATTEMPTS` = 3 total), then is marked `failed` and the task continues. When the failure means **user data is missing** (not a model error), the verifier returns a third verdict `needs_user_input`: the step pauses as `awaiting_user`, a verbatim question is appended to the conversation, and after the answer the same step re-runs with it (the paused attempt is not counted against the 3-attempt limit).
4. **Final** — the answer/action over the accumulated results, with media references; the task becomes `completed`. A final summary that merely restates the last step's answer is detected and suppressed (the step's answer is shown once, with its own header metadata). Step and final prompts require math and formulas as plain text (no LaTeX — the web UI ships no formula renderer, so `$…$`/`\times` would reach the user as raw markup).

Media sub-tasks run in the existing queue at the task's class (3/4/5). A slow-worker guard keeps them from starting while the gate is closed — they wait in a deferred list and return to the queue when chat goes quiet. ■ Stop and 🗑️ delete cancel the sub-task the running step already put on the queue, and the worker drops a tagged request whose step is gone (or is no longer queued/running), so a removed task can never leave an orphan holding the slow worker and the GPU. A media sub-task returns its artifact in the result envelope (the step's `extra.media`) instead of writing a chat message — a task step has no chat session, the row would be an orphan.

## Persistence and recovery

`tasks` + `task_steps` (PostgreSQL) persist the whole state; the executor **resumes after a restart** — an interrupted step gets a fresh attempt with reason `restart`. Only each attempt's real runtime counts toward the budget, so restarts never eat the 24 h budget. The conversation is rendered from `task_steps` — there is no parallel messages table. Both tables are included in full backups.

## Notes

- Task media (generated images and videos, camera snapshots, every other media sub-task artifact) live in the regular upload folder under the task's own id — `<UPLOAD_FOLDER>/<task_id>/…`, because the queue session of a sub-task IS the task id — and are referenced from step `extra.media`, so they render in the step message chat-style (`.image-container` + zoom modal) and `/api/files` resolves ownership through the `tasks` table when the chat-session lookup misses. Deleting a task deletes its conversation (steps are removed with it).
- Documents, images and audio attach the chat way (chips in the task view). Images ride the request/answer as multipart `images` (≤ `MAX_CHAT_IMAGES`, quota + downscale like chat, `{file_path, file_name}` stored on disk — bytes never enter the DB), and the planner advertises the `vision` capability only when images exist. A document attached with the paperclip becomes a **full user document** through the exact Documents-panel chain (validation, size/quota checks, storage under `DOCUMENTS_FOLDER/<login>/<id><ext>`, a `documents` row, `index_document` enqueued); only its id persists, merged **first** into `tasks.doc_ids` before the Documents-panel selection, so an attachment never silently means «all documents». `doc_ids` may also be filled from the Documents-panel selection at request/answer submit time; an empty set means «search all of the user's documents» — the same rule the chat uses for RAG. The request message renders the attachments as their own service lines — «Attached images: …» and «Attached documents: …» (the plan line's font, a 📎 marker, the label on its own line and one file name per line; the localized strings are built server-side and never ride inside the request text). A `rag` step waits for the task's freshly attached documents to leave the indexing states before searching, and an `rlm` step waits the same way before its corpus is read (a scanned PDF has no text on disk until its OCR finished) — both waits are bounded by `OCR_TIME_BUDGET_S` and abort as soon as a chat request closes the gate, so the step dies `interrupted` and re-executes on resume.
- Audio and voice attach the chat way too (chips, the paperclip or the microphone): they ride the request/answer as multipart `audio` parts, are saved under the task's upload folder and transcribed by a background thread (Whisper sidecar — an HTTP call, no GPU lock; a video container is transcribed by its audio track). **The transcript is task context, never a Documents-panel document and never indexed** (the same rule an image description follows). While Whisper runs the task is `frozen` (reason `audio_transcript`, the banner shows «Распознаю аудио…») — a dictated task cannot be planned before its text exists, so the planner reads the request transcript in the user's own words and a text task with audio material («проанализируй аудиозапись …») gets the transcript in every step's context. A task dictated with no text takes its title from the transcript; an audio answer is appended to the answer step (the image-description contract). One submission carries at most `MAX_CHAT_AUDIO` (4) audio items — one recording plus audio files (1 voice + 3 files, or 4 files); the excess is refused with the localized `max_audio_reached` message before anything is stored. The request/answer message renders the recording as «Attached audio recordings: …» (a 📎 service line) and the transcript itself as «🎤 Распознано (name): …» in the regular reading font; a transcription failure fails the task with a localized ⚠️ error instead of queueing an empty request.
- The 🔬 **Deep Analysis** toggle is available on task send/answer like in chat: at request time the planner gets a note to include an `rlm` step over the task's documents; with a plan already in place, answering with the toggle appends an `rlm` step (idempotent — one at most). A `final()` call with an empty answer is nudged once with an explicit «compose a substantive answer» message before the run fails.
- Tasks updates arrive on the same per-user SSE stream as chat events (`task_update` type) — the list and the open conversation refresh without polling. Status/plan/step updates are published **during** execution (planning starts, the plan materializes, each step is queued, flips to running and completes), not dumped at the end.
- Task messages show per-step execution time and token usage (same header as chat), and the final answer does not repeat the last step's result verbatim. A failed step with an empty result body shows its `last_error` instead of staying blank.
- The internal API lives at `/api/tasks*` (session-auth, owner-scoped like sessions); there is **no public `/v1` task API** in this version.
- The capabilities registry is the seam for a future **skills** concept: a skill would be a named capability bundle appearing in the same registry without storage changes.

## Configuration

All settings with defaults: `docs/CONFIGURATION.md` («Background Tasks»). Kill switch `TASKS_ENABLED=0` stops the executor from picking up new tasks.
