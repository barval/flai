# Background Tasks (Tasks)

**For what?** Some jobs are too big for one chat request: prepare a 10-page report from several sources, research a topic across a dozen web pages and draft a structured memo, generate a set of images and describe them. **Tasks** are long-running background jobs: you describe the result, the system decomposes the request into a plan of steps and executes them one by one at **lower priority than chat** — a task never makes your chat request wait, and any chat request freezes the running task and takes the resources back.

## How to use it

1. Open the **Tasks / Tasks** tab in the left column (between **Documents** and **Sessions**), press ➕ and describe the desired result. The tab reopens the task you last had open (also after a page reload) — like the chat reopens its last session; the empty state appears only when there is nothing to restore.
2. You can also create the task first and describe it later: ➕ opens a **draft** task (draft status, the input becomes the description box); sending the description enqueues the task.
3. The task is planned and starts running. Its conversation opens in the main window and looks like a normal chat: the user request, a «Plan of N steps:» message, then each step's output prefixed with «Step N of M:» (Step N of M), and the final answer. The plan/step prefixes are rendered as their own italic service line, and every assistant message carries the same header as chat messages: 📅 date | model name | ⏱️ execution time | 🔢 token usage | 🚀 tokens/s, plus 🗣️ (read aloud) and 📋 (copy) buttons. The plan message carries the header too — the executor stores the planner call's metadata (`plan_meta`: reasoning model name, wall-clock time, real token usage) with the plan and the messages route exposes it. User requests get the same 🗣️/📋 buttons as answers (both sides of `displayMessage` and `renderTaskMessage`); whisper transcriptions and system/error rows stay button-free. Each header field stands on its own — a final summary shows its tokens even though it has no separate duration. A step handled by a tool rather than the reasoning model (calculate, search, a media sub-task) names that tool — localized and with its emoji — on its own italic service line right below the step line (same font as «⚙️ Step N of M:»), e.g. «🔎 Web search:», and its header reports the checkpoint verifier's model and tokens (the only model call that step makes). Media and RLM steps report the model that actually produced the artifact: a camera/vision step shows the multimodal model (🖼️) with its real token totals, an image-gen step `SD_MODEL_TYPE` (🖌️), an image-edit step `flux-2-klein-4b` (🎨), a video step `LTX_VIDEO_MODEL` (🎥), an RLM step the reasoning model (🔬🧠). While the plan itself is being made, the status banner shows the live stage with a per-second counter — «Loading reasoning model... (Ns)» while the reasoning model cold-loads, then "Making the plan... (Ns)" until the plan appears (SSE `task_stage` events, cleared as soon as the plan arrives or the phase fails).
4. Live status is shown on each list item: ⏳ queued / ▶ Running (step n of m) / ⏸ Frozen / ⏳ Awaiting answer / ✔ Completed / ✖ Failed / ✖ Cancelled / ⏰ Expired. While the task is being planned, the status line shows «Making the plan…» (Making the plan…); non-terminal statuses pulse like chat stage labels. Each row also carries a blinking badge before its title, like the session cards: ⚡ running, ❓ awaiting an answer, ⏳ queued with its 1-based queue position (the executor's own order — class, then FIFO).
5. When the model asks a clarifying question, the task shows «Awaiting answer» (Awaiting answer) with an elapsed-seconds counter and the message input becomes the answer box («Answer the clarification…»). Answer and the task continues. A clarifying question can appear in two ways: the planner builds it into the plan, or **the verifier requests missing user data** mid-step — the step is interrupted (the attempt is not counted), the question is asked verbatim, and after the answer **the same step re-runs** with it.
6. ■ (Stop task) cancels a running or waiting task; 🗑️ deletes it (a non-terminal task is cancelled first, then removed with its whole conversation). Deleting the task that is open in the main window opens the next task of the list (or the «no task selected» empty state) — the window never falls back to a chat session.

## Priorities and preemption

- A task's priority class is derived from the user's service class at creation: `0 → 3`, `1 → 4`, `2 → 5`. Classes 3/4/5 are **internal** and never offered in the admin panel — users keep classes 0/1/2.
- **One task is active globally** (selection by class 3 before 5, then FIFO). Awaiting user input or being frozen releases the slot for the next task.
- **Quiet window (sliding):** after the last chat request, a task may start/resume only when `TASK_QUIET_PERIOD_S` (default 15 s) passed with no new chat requests, chat queues are empty and the GPU is free. Any new chat request resets the window and **aborts the in-flight step**: its partial output is discarded, the step is marked `interrupted` (reason `chat`) and re-executed from scratch on resume. Chat never waits for a task.
- **Budget:** a task may accumulate at most `TASK_TOTAL_BUDGET_S` (default 24 h) of **pure execution** — waits, freezes and awaiting-user time never count. On expiry the task is `expired` and a final summary is generated from the intermediate results.

## What happens inside

1. **Planning** — a reasoning-model call decomposes the request into steps (title, goal, one capability per step, a verifiable `checkpoint_criteria` each). Missing information becomes a clarifying question step. The call is greedy (`temperature=0`), so the same request yields the same plan, and every text field of the plan (title, goals, criteria) is pinned to the task language — the capabilities registry is rendered in that language too (an English registry block inside the Russian planning prompt once pulled the whole plan into English, and every media step then used the English goal as its query).
2. **Steps** — each step runs one capability from the registry (`app/tasks/tools.py`):

| Tool | What it does |
|------|--------------|
| `llm` | reasoning-model call with the accumulated intermediate results (multimodal only when a step must inspect earlier produced images) |
| `search` | web search (Tavily → SearXNG fallback) |
| `rag` | search the user's own documents — the documents attached to the task scope it, and with none attached every indexed document is searched with file coverage (the chat's RAG rule); the following `llm` step composes the answer from the returned fragments |
| `history` | search the user's previous conversations (CPU-only PostgreSQL full-text search, mirrors the chat's `[-HISTORY-]` path); a wildcard goal or no direct matches degrades to a compact overview of recent sessions; the following `llm` step composes the answer |
| `camera` | a camera snapshot of one named room is taken and described by the multimodal model as a queue sub-task (`camera_task`); the planner emits one step per room (the user's room list is advertised in the planning prompt). The room is resolved from the step goal with declension-aware token matching (a genitive «kitchen» finds the stored «kitchen»); the analysis question travels from the task title, never the raw imperative goal (which misroutes the image classifier to a router marker), and a misrouted marker echo is stripped with one pure-analysis retry |
| `vision` | the images attached to the task in the task view (chat-style chips) are READ by the multimodal model as a queue sub-task (`vision_task`): it returns a two-section extraction — a detailed description of everything visible plus all text on the image — and never answers the planner goal; the following `llm` step composes the answer from the extraction. One call per image — the extraction prompt mandates exactly one description block, so a joint call over several images would describe only the first of them — and each extraction is preceded by the image's file name, written by the caller. The step reads only the images whose file name its goal names: the planner plans ONE vision step per image with that file name in the goal (the camera's one step per room pattern), and a goal naming no attached file reads them all; advertised in the planning prompt ONLY when images are attached; a router-marker echo in the result is stripped (never shown to the user) |
| `crawl` | deep site study through the Crawl4AI sidecar as a queue sub-task (`crawl_task`); the collected pages become the step result (no reasoning requeue) and index as a per-user document |
| `calculate` | the safe AST-based calculator; the planner puts the bare expression in the step goal («2 + 2 * 2»), and a prose goal falls back to extracting the math expression from the text |
| `rlm` | Deep Analysis run as a queue sub-task |
| `image_gen` / `image_edit` / `video_gen` | media sub-tasks through the existing GPU queue. With several images attached, `image_edit` edits the image its goal names (one step per image, like `vision`) and falls back to the first attached image when the goal names none. A step the plan binds to a producer step (`source_step`) and whose producer produced no image is **skipped** — the reason names that step, nothing is enqueued for the skipped step, and the task continues (the final summary explains the missing media); an unbound `video_gen` keeps its chat-parity fallback to text-to-video |

### Media step context and verification

A media step receives the declared `source_step`'s own result first (up to 12 000 characters of the `MEDIA_CONTEXT_CHARS` = 16 000 budget, the digest of the other steps fills the rest), so a long producer result cannot push the part a step materializes out of its prompt. Each produced image is then described by the multimodal model through the structured `task_describe_image.template` (objects, counts, actions, setting, style, visible text) and judged in a fixed order: first against the expected content — the **fragment of the source step's result named by the step's goal and criterion**, with the goal and criterion passed as separate fields — and then against the prompt the generator actually received (`backend_prompt` in the sub-task envelope). The generation prompt is supporting context, not a reference: a mismatch with it while the reference, goal and criterion are satisfied is not a failure. A media step without a source binding is judged by its goal, and an edit step by the requested change, so a correct picture is not rejected for legitimately diverging from the reference. A rejected artifact opens the **repair loop**. Every mismatch carries a `severity` (`critical`/`minor`) and a `repairable` flag: a local defect — an extra or duplicated object, wrong text/time on an object, colour, a small detail — is first fixed by **editing the current picture** (one edit after each generation, `TASK_STEP_MAX_REPAIRS` = 3, `strength` clamped to 0.35–0.5, the defect in `edit_prompt`, the scene/style/entities in `preserve`); a new composition (wrong scene, character, count or action) goes straight to the next generation. The cycle is generation → edit → generation → edit → generation → edit, and an unsuccessful edit does not spend a generation attempt (≤ `TASK_STEP_MAX_ATTEMPTS` = 3). The generation prompt is supporting context, not a reference. When every attempt fails, the step does **not** fail: every candidate (3–6 pictures) is ranked by the verifier's `score` (tie: fewer critical, then fewer minor mismatches, then the later attempt) and the closest one becomes the step artifact with a «best effort» note — the last attempt is not automatically the best. Losing files are deleted. A rejection repeated with the same reason is accepted as well. The final SD prompt is checked against the continuity sheet before diffusion: an entity the prompt builder dropped has its look appended deterministically. Artifact inspection is a registry (`app/tasks/artifacts.py:ARTIFACT_INSPECTORS`): a content-free criterion no longer skips the check, a step type without an entry (camera, vision) is not checked, a failed description skips the check instead of failing the step, and a new artifact type is added by registering an inspector. The step body never shows the artifact's file name: the name is verifier-only metadata, so a rejected polish attempt cannot replace the accepted image's name in the text.

Anatomical anomalies are always critical: the image description counts the visible paws/hands/legs of every person and animal, and an extra, missing or duplicated limb fails the step even when the reference does not mention it.

Every repair/polish edit is tone-matched back to its source after the model run (YCbCr Y mean/std, full correction) so a Flux edit cannot lighten or flatten the series; explicit lighting/colour changes are left alone.

**Polish of an accepted image.** A passing verdict with only `minor` mismatches (wrong style, lighting, a small detail) used to keep the picture as is. The executor now schedules **one** corrective edit for it (`polish_used`, image artifacts only, never video/RLM): the minor mismatches become the edit instruction, and a style mismatch is sent as a change — the old style is removed from `preserve`, the continuity-sheet style becomes the target. The polished image is verified again; if it passes it is kept, and if it is rejected no new generation cycle starts — every candidate is ranked with the accepted one first (then score/severity) and the best is kept with the usual best-of note. `polish_used` makes the polish a one-time step per image.

### Visual continuity (internal)

A task that plans several generated images keeps them visually consistent through an internal continuity sheet: one style plus the fixed look of every character, place and prop named in the request. The sheet is extracted by one reasoning call **before the first `image_gen` step**, and only when the plan has two or more generated images; an edit-only plan never extracts, so an invented style cannot alter the user's own photos. The sheet is stored on the task (`tasks.visual_bible`) and rendered into the prompt of every image step, so later scenes keep the same characters and style. It also carries `style_lock`: it defaults to true. When the user explicitly asks for different images **in different styles** ("different styles"), the extractor sets `style_lock: false` and leaves `style` empty; neither the prompt builder nor the verifier then imposes one style. A request for different scenes/content alone keeps the shared style. It is a guard, not a plan step: the planner is not offered a `continuity` capability, and the extraction never appears in the plan, in «Step N of M» headers or anywhere in the task view. Env: `TASK_CONTINUITY_ENABLED` (on/off), `TASK_CONTINUITY_MAX_CHARS` (sheet budget).

The extraction call (`prompts/{ru,en}/task_continuity.template`) receives the task request, the plan goals, the current step goal and criterion, the previous step results and — in merge mode after a replan — the existing sheet, and must answer a strict JSON object: `style` (English), plus `characters` / `places` / `props` entries `{id, aliases, look}`. `id` is lowercase Latin letters, digits and underscores; `aliases` are in the task language (short forms and synonyms); `look` is **English only** — one concrete sentence with the identifying features (age, face, hair, eyes, clothes, silhouette, palette). Source-reference markers (`lines 100-150`, `(source: …)`) are stripped from the corpus before the call. An invalid JSON or an over-budget sheet gets one corrective retry; a still-oversized sheet is accepted **whole** and a second failure stamps `visual_bible_attempted` (the images proceed without the sheet).

For each image step `render_sheet` selects the cards whose id or aliases occur in the goal and criterion (case-insensitive substring first, then pymorphy3 lemmas; a multi-word alias matches word-wise) and emits `Style:` plus grouped `Characters:` / `Places:` / `Props:` lines; no matching card yields the style line only. The block is prepended to the generation query, and the same cards form the transient continuity clause of the verifier. After the multimodal prompt builder produces the final SD prompt, `ensure_entities_in_prompt` appends the `look` of any selected card whose id/aliases are absent from that prompt, so a rephrasing cannot silently drop an entity, and `ensure_style_in_prompt` puts the sheet's style at the **front** (a trailing style was routinely ignored), adds `2D`/`hand-drawn`/`flat colors`/`clean outlines` cues for a 2D illustration style (never for 3D), removes `photorealistic` from every non-photo style and, for 2D only, also removes `high detail`/`sharp focus`/`masterpiece` (a 3D style keeps them). A photorealistic or 3D style is honored: no 2D cues, and a 3D style keeps the quality tags (only `photorealistic` is dropped); the media checkpoint treats a clear medium change against the sheet (photograph vs drawing/render, 2D vs 3D or 3D vs 2D) as `critical`, and a photograph is the correct medium when the sheet names photorealism.

### Long-term memory (SLM)

Tasks share the chat's SuperLocalMemory profile. Recalled facts are embedded in the planning, step (`llm`) and final-summary prompts exactly as in chat (session-specific first, capped at `SLM_RECALL_LIMIT`); the section is empty without SLM and a recall error never fails a task. Passed `llm` steps and final summaries trigger the same rule-based background fact extraction as chat answers — user statements made to a task («I do not eat mushrooms») land in the same per-user memory. Facts are extracted from the user's request only, never from model output; ⚠️ error texts and tool fragments (search/rag/calculate) are not memories.

3. **Checkpoint** — a short reasoning call verifies the step result against `checkpoint_criteria`; on failure the step reruns with the mismatch description (up to `TASK_STEP_MAX_ATTEMPTS` = 3 total), then is marked `failed` and the task continues. The verifier is a text-only call, so for a media step the produced image is described by the multimodal model first and that description is added to the verifier input (a step was rejected with «the result provides no image or its description» while its artifact still fed the following steps). For a generated video the representative (middle) frame is returned by the video wrapper as `preview_data` and described the same way — without it the verifier saw only the goal and its verdict was a coin flip (5 of 10 video steps failed while the mp4 existed). When the failure means **user data is missing** (not a model error), the verifier returns a third verdict `needs_user_input`: the step pauses as `awaiting_user`, a verbatim question is appended to the conversation, and after the answer the same step re-runs with it (the paused attempt is not counted against the 3-attempt limit).
4. **Final** — the answer/action over the accumulated results, with media references; the task becomes `completed`. A final summary that merely restates the last step's answer is detected and suppressed (the step's answer is shown once, with its own header metadata). Step and final prompts require math and formulas as plain text (no LaTeX — the web UI ships no formula renderer, so `$…$`/`\times` would reach the user as raw markup).

Media sub-tasks run in the existing queue at the task's class (3/4/5). A slow-worker guard keeps them from starting while the gate is closed — they wait in a deferred list and return to the queue when chat goes quiet. The gate guards **starting** work only: while a task's own media sub-task is queued or running, the task stays `active` (that sub-task is what keeps `is_gpu_busy()` true — freezing it showed a running deep analysis as «Frozen»), and chat preemption is delivered by the per-step cancel flag, not by the gate. ■ Stop and 🗑️ delete cancel the sub-task the running step already put on the queue, and the worker drops a tagged request whose step is gone (or is no longer queued/running), so a removed task can never leave an orphan holding the slow worker and the GPU. A media sub-task returns its artifact in the result envelope (the step's `extra.media`) instead of writing a chat message — a task step has no chat session, the row would be an orphan.
A busy GPU is never a step failure: a sub-task whose liveness probe cannot answer (a Redis hiccup) is re-polled for up to `TASK_SUBTASK_ALIVE_UNKNOWN_MAX` cycles instead of expiring a result that may land milliseconds later, a failed sd-wrapper health probe (the wrapper is single-threaded and cannot answer `/health` while it renders) no longer blocks the generation request, and every VRAM wait (`ensure_vram_for`, the queue's own gate, the video gate) uses `VRAM_WAIT_TIMEOUT_S` (120 s) and returns as soon as the memory frees — fixed 15/30 s deadlines used to fail a task while a 12 GB reasoning model was still unloading.

## Persistence and recovery

`tasks` + `task_steps` (PostgreSQL) persist the whole state; the executor **resumes after a restart** — every step left in flight (a direct step in `running`, or a queue sub-task in `subtask_queued`/`subtask_running` whose request died with the worker) gets a fresh attempt with reason `restart`. Only each attempt's real runtime counts toward the budget, so restarts never eat the 24 h budget. The conversation is rendered from `task_steps` — there is no parallel messages table. Both tables are included in full backups.

## Plan correction

A running task reviews its own remaining plan. A review is triggered by a **failed or skipped step**, a **fresh user answer**, an **exhausted plan** (it may still grow) and by every information-producing step (`llm`, `rlm`, `rag`, `search`, `crawl`, `history`); an ordinary passing media step only triggers one every `TASK_REPLAN_EVERY_N` steps (default 3). Before the review and before the final answer is composed, one reasoning call (`prompts/{en,ru}/task_replan.template`, greedy decoding) sees the user request, the executed steps with their results, the user's answers to clarifying questions and the remaining steps numbered by their **global** plan position. It answers either `{"changed": false}` (the plan stands) or `{"changed": true, "reason": "...", "steps": [...]}` with the **full** replacement tail; an empty list is a legitimate answer meaning «nothing remains» and the task finalizes. A missing `reason` is logged as `unspecified` and does not block a correction.

- **Forward-only.** Only the not-yet-executed tail may change; an executed step keeps its row, its goal and its result. A rewrite deletes the superseded *pending* step rows (terminal rows are never touched) and creates fresh rows for the new tail with the right kind per capability — a media step goes through the queue, a `user_input_expected` step becomes a clarifying question.
- **The review is not a second planner.** It never re-plans from scratch: it changes the tail only when execution already revealed a fact that requires it — a step result names more work than the plan covers, the user's answer asks for work no step covers (or the plan does not cover the discovered volume: 10 items found, 4 action steps planned), or a remaining step became unnecessary or impossible. If everything goes to plan, it changes nothing.
- **Enumerations come from the source, not from a digest.** When a task must enumerate ALL items of a document (scenes, chapters, sections, list entries, requirements, characters, dates, amounts, etc.) and act on each, the enumeration step must read the source: `rlm` when available (Deep Analysis on), otherwise a `rag` step before the `llm` step. Goals and criteria demand ALL items, numbered or unambiguously identified, with no reduction to «key» items; the reviewer adds one action step per item when the tail covers fewer.
- **Pre-flight plan audit.** Before the first step, a document plan that contains an `llm` step is audited by one reasoning call (`prompts/{ru,en}/task_plan_audit.template`). The auditor checks only the enumeration contract — an `llm` step must not enumerate the document itself without an earlier `rlm`/`rag` read; an `llm` step that composes from an obtained result is valid. An invalid verdict re-runs the planner once with the localized reason (`task_plan_audit_retry.template`); an unparsable or failed audit, or a failed retry, keeps the current plan (fail-open). The audit's tokens and time are included in the plan header and the task total. Plans without documents or without an `llm` step are not audited.
- **Media goals stay in the profile language.** The planner and reviewer must not append a foreign style name or generator prompt to an image/video goal — the style is applied by the image pipeline from the continuity sheet. As a safety net, a trailing paragraph in the other script (English in a Russian profile and the reverse) is removed when a plan is created or rewritten. Only `image_gen`/`image_edit`/`video_gen` goals are touched; URLs, paths, file names and mixed-language lines are preserved.
- **A bad review never damages a task.** An unparsable reply, a reply naming a capability that does not exist, a missing `steps` field or a transport error all keep the current plan and the task runs on: the review can never fail the task and its error is never shown to the user.
- **The reviewer sees the freshest facts.** Its results digest is tail-weighted (the last part of the results, not the first ones, which is what matters on a task that has been running for hours) and the user's answers ride along. Each step may use the full 16,000-character review budget: the old 4,000-character per-step cut ended a 15-scene list exactly at scene 8, so the reviewer added only 8 image steps. The review shares the planner's 🔬 Deep Analysis contract and the same capability registry.
- **Guardrails.** The review runs under the same three guards as a step start — the execution budget, the quiet-window gate and the cancel flag — so no model call runs outside the gate; a review that comes due while the gate is closed waits and runs when it opens. A user stop during the review cancels the task cleanly. Growth is bounded by `TASK_MAX_REVISIONS` (default 8 accepted rewrites), `TASK_MAX_STEPS` (default 40) and the 24 h `TASK_TOTAL_BUDGET_S`; once the revision budget is spent the review is skipped and the current plan is final. During the review the status banner shows the ordinary planning stage (reasoning model load, then «Making the plan…») — no new status was added.
- **A paraphrase is not new work.** A candidate step whose tool and goal lemma set repeat an already executed step is dropped, duplicates inside the new tail are dropped too, and the tail comparison (`_same_plan_tail`) is lemma-based — «draw scene 3» and «drawing scene 3» read as «no change». A rewrite that leaves no new steps keeps the plan and adds no revision notice.
- **What the user sees.** Every applied rewrite adds a service line «Plan updated (N steps).» to the task conversation, anchored right after the step that triggered it. The plan message and the «Step N of M» headers are rendered from the **current** plan, so all later status messages already follow the new plan.
- **A redo is not a new plan position.** The reviewer is told to repeat a failed step's goal **verbatim**; `_apply_replan` recognises the verbatim repeat of the just-consumed step's goal (same tool), re-opens that row (`status=pending`, `attempts=0`, `extra.redos+1`, the reviewer's refined criterion applied in place), drops the duplicate from the tail and resumes at the same position. `TASK_STEP_REDO_MAX` (default 1) caps the re-opens; when it is spent the duplicate is dropped and the step stays failed. Before this, every redo became a new row with a fresh attempt budget — a scene could be generated six times through two «steps» — and the plan carried the same goal twice.

## Notes

- Task media (generated images and videos, camera snapshots, every other media sub-task artifact) live in the regular upload folder under the task's own id — `<UPLOAD_FOLDER>/<task_id>/…`, because the queue session of a sub-task IS the task id — and are referenced from step `extra.media`, so they render in the step message chat-style (`.image-container` + zoom modal) and `/api/files` resolves ownership through the `tasks` table when the chat-session lookup misses. Deleting a task deletes its conversation (steps and the chat messages a failed step persisted under the task id are removed with it — nothing else reads those rows), removes the task's whole upload directory and subtracts the freed bytes from the owner's storage quota. A media step that settles keeps only its winning artifact: losing candidates are deleted as soon as the step passes or picks a best-effort image.
- Documents, images and audio attach the chat way (chips in the task view). Images ride the request/answer as multipart `images` (≤ `MAX_CHAT_IMAGES`, quota + downscale like chat, `{file_path, file_name}` stored on disk — bytes never enter the DB), and the planner advertises the `vision` capability only when images exist. A document attached with the paperclip becomes a **full user document** through the exact Documents-panel chain (validation, size/quota checks, storage under `DOCUMENTS_FOLDER/<login>/<id><ext>`, a `documents` row, `index_document` enqueued); only its id persists, merged **first** into `tasks.doc_ids` before the Documents-panel selection, so an attachment never silently means «all documents». `doc_ids` may also be filled from the Documents-panel selection at request/answer submit time; an empty set means «search all of the user's documents» — the same rule the chat uses for RAG. The request message renders the attachments as their own service lines — «Attached images: …» and «Attached documents: …» (the plan line's font, a 📎 marker, the label on its own line and one file name per line; the localized strings are built server-side and never ride inside the request text). A `rag` step waits for the task's freshly attached documents to leave the indexing states before searching, and an `rlm` step waits the same way before its corpus is read (a scanned PDF has no text on disk until its OCR finished) — both waits are bounded by `OCR_TIME_BUDGET_S` and abort as soon as a chat request closes the gate, so the step dies `interrupted` and re-executes on resume.
- Audio and voice attach the chat way too (chips, the paperclip or the microphone): they ride the request/answer as multipart `audio` parts, are saved under the task's upload folder and transcribed by a background thread (Whisper sidecar — an HTTP call, no GPU lock; a video container is transcribed by its audio track). **The transcript is task context, never a Documents-panel document and never indexed** (the same rule an image description follows). While Whisper runs the task is `frozen` (reason `audio_transcript`, the banner shows «Transcribing audio…») — a dictated task cannot be planned before its text exists, so the planner reads the request transcript in the user's own words and a text task with audio material («analyze the audio recording …») gets the transcript in every step's context. A task dictated with no text takes its title from the transcript; an audio answer is appended to the answer step (the image-description contract). One submission carries at most `MAX_CHAT_AUDIO` (4) audio items — one recording plus audio files (1 voice + 3 files, or 4 files); the excess is refused with the localized `max_audio_reached` message before anything is stored. The request/answer message renders the recording as «Attached audio recordings: …» (a 📎 service line) and the transcript itself as "🎤 Transcribed (name): …" in the regular reading font; a transcription failure fails the task with a localized ⚠️ error instead of queueing an empty request.
- The 🔬 **Deep Analysis** toggle is available on task send/answer like in chat: at request time the planner gets a note to include an `rlm` step over the task's documents; with a plan already in place, answering with the toggle appends an `rlm` step (idempotent — one at most). A `final()` call with an empty answer is nudged once with an explicit «compose a substantive answer» message before the run fails.
- Tasks updates arrive on the same per-user SSE stream as chat events (`task_update` type) — the list and the open conversation refresh without polling. Status/plan/step updates are published **during** execution (planning starts, the plan materializes, each step is queued, flips to running and completes), not dumped at the end.
- Task messages show per-step execution time and token usage (same header as chat), and the final answer does not repeat the last step's result verbatim. The **task-list header total** sums every LLM call of the task: step models, their checkpoint verifiers (`extra.checkpoint_usage`), the planner (`step_plan.plan_meta`) and every accepted plan review (`step_plan.revision_meta`); a corrective retry accumulates into `usage_total` / `checkpoint_usage_total`, so rejected generations are not lost. The admin Users tab adds the same task and plan spend to the chat token totals. A failed step with an empty result body shows its `last_error` instead of staying blank.
- **Every step explains its validation state.** The step line carries a chip — `✅ checked automatically`, `🔁 redone ×N`, `🔁 retrying N/M`, `✖️ not delivered`, `⏭ skipped`, `⏸ interrupted`, `⚠️ not verified` — with the last rejection's reason under it (for a retry in progress: «Auto-check failed: <reason>. Redoing (attempt N of M)»; after success: «Redone after the check: <reason>»), plus a collapsed per-attempt log (`extra.attempts_log`, the newest ten entries, written at every verdict). `⚠️ not verified` means the artifact could not be described, so the check was skipped — the step did not fail and no attempt was spent. Every reason the view prints is localized: internal verifier markers (an unreadable verdict, a verifier that could not start) are translated before they reach the step row, and a step that never produces a file — any text step — fails with its own wording instead of the media one.
- **The final answer ends with the accepted results.** The final step carries `extra.final_items` — a passed step that produced a file becomes a card (the step goal is its caption, a `🔁 redone ×N` badge when it took retries), a passed text step becomes a row with a word-boundary preview and a collapsible full text — and `extra.final_failures`, one footnote naming what was not delivered. The rule is «a passed step that produced something», never «a scene has an image», so any task shape gets the same section. The heading reports the total and the image/text split (e.g. `Accepted results: 5 (images: 3, texts: 2)`), so a count of results is never mistaken for a count of images. The summary digest describes only passed steps and appends the not-delivered items separately; the model is told not to enumerate the accepted results, because the interface lists them under the answer.
- The internal API lives at `/api/tasks*` (session-auth, owner-scoped like sessions); there is **no public `/v1` task API** in this version.
- The capabilities registry is the seam for a future **skills** concept: a skill would be a named capability bundle appearing in the same registry without storage changes.
