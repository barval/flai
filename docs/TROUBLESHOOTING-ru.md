# Диагностика проблем

Типичные проблемы развёртывания и работы. Если вы столкнулись с чем-то, чего здесь нет, сначала посмотрите `docker logs` у затронутого контейнера, затем [../CHANGELOG.md](../CHANGELOG.md) — возможно, это известная регрессия.

Каждая пользовательская ошибка FLAI начинается с `⚠️ `. Сообщения в чате без этого префикса приходят из браузера или прокси, а не от FLAI.

## Первые три команды

```bash
docker compose ps                      # какие контейнеры подняты и здоровы
docker logs flai-web --tail 100        # веб-приложение
curl -s localhost:5000/health | python3 -m json.tool
```

`/health` сообщает о доступности базы данных, Redis, Qdrant и о состоянии загруженной модели. Это самый быстрый способ отличить «FLAI упал» от «упала одна подсистема».

## Проблемы развёртывания

### `detect_cuda` сообщает, что драйвер ниже минимума

```
CUDA driver 12.1 is below the minimum supported version (CUDA 12.2)
```

FLAI нужен хост-драйвер от **CUDA 12.2** и выше (драйвер 525.60.13+). Скрипт развёртывания принимает 12.2 как нестандартное развёртывание — требования NVIDIA к образам для llama-swap, LTX-Video и sd.cpp снимаются, потому что minor-version compatibility в CUDA 12.x позволяет им работать (проверено пользователями на RTX 3090 + CUDA 12.2).

Ниже 12.2 скрипт отказывается от GPU-режима и переходит на режим только CPU. Чтобы исправить, обновите драйвер — не заставляйте GPU-режим на неподдерживаемом драйвере.

### Контейнеры падают с `could not select device driver "" with capabilities: [[gpu]]`

Не установлен NVIDIA Container Toolkit или он не подключён к Docker. Проверьте:

```bash
nvidia-smi                 # работает ли драйвер на хосте?
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi
```

Если вторая команда падает, установите NVIDIA Container Toolkit для вашей версии Docker и перезапустите демон Docker. Это проблема уровня хоста — никакая настройка FLAI её не обойдёт.

### `port is already allocated`

Порт 5000 занят другим процессом:

```bash
ss -ltnp | grep 5000
```

Измените публикуемый порт в `docker-compose.gpu.yml` (`"5000:5000"` → `"8080:5000"`) или остановите то, что держит 5000.

### Контейнер краулера сразу завершается

Sidecar Crawl4AI привязывается только к loopback, если не задан токен, поэтому веб-контейнер не может до него достучаться:

```bash
grep CRAWL4AI_API_TOKEN .env        # must be non-empty and match CRAWL_API_TOKEN in the web service
docker logs flai-crawler --tail 50
```

Без токена sidecar остаётся привязанным к `127.0.0.1` внутри сети контейнеров, и каждый запрос падает. См. [SEARCH-ru.md](SEARCH-ru.md).

## Модели и VRAM

### GPU-задача зависает, а затем сообщает о таймауте VRAM

FLAI выстраивает GPU-работу в очередь за одним единственным замком и ждёт освобождения VRAM перед загрузкой следующей модели. Если ожидание не заканчивается, значит память держит кто-то ещё:

```bash
nvidia-smi                                   # кто сейчас использует VRAM
curl -s localhost:5000/health | python3 -m json.tool
docker logs flai-web --tail 200 | grep -i vram
```

Почти во всех случаях причина одна из двух:

1. **Модель была перезапущена извне**, пока FLAI ждал. Цикл ожидения самовосстанавливающийся — он повторно выгружает модель, появившуюся в `/running` llama-swap, на каждом опросе, — но второй процесс на хосте (ручной llama-server, другой контейнер) будет продолжать с ним бороться. Остановите этот процесс.
2. **LTX-Video завис.** Три таймаута подряд заставляют FLAI перезапустить видеоконтейнер. Посмотрите `docker logs flai-ltxvideo`.

Сторож health-монитора намеренно пропускает весь свой тик, пока GPU-задача держит замок, поэтому повторное появление модели в логе — это симптом, а не причина.

### `compute_llamacpp_config` снижает n_gpu_layers до 0 и всё равно падает

Модель вообще не помещается в VRAM. FLAI деградирует до загрузки, а не падает с OOM, значит модель больше доступной VRAM даже при всех слоях на CPU. Либо выберите меньшую квантизацию, либо позвольте авто-подбору снизить окно контекста — см. [VRAM_MANAGEMENT-ru.md](VRAM_MANAGEMENT-ru.md) и [BENCHMARKS-ru.md](BENCHMARKS-ru.md).

### Генерация умирает с «Image generation timeout» примерно на шаге 3/10

Это был старый путь на CPU: полное разрешение на CPU не укладывается в `SD_CPP_TIMEOUT`. На CPU FLAI уменьшает разрешение вдвое по обеим сторонам (~в 4 раза меньше пикселей) и уведомляет вас через канал `resize_notice`. Если таймаут всё равно случается, увеличьте `SD_CPP_TIMEOUT` для вашего CPU-контейнера.

### Генерация видео на CPU завершается аварийно

Видео на CPU в 4–6× медленнее, чем на GPU. Планировщик выбирает наибольший формат, который помещается и в доступную ОЗУ, и во временной бюджет (`LTX_VIDEO_CPU_TIME_BUDGET_S`, по умолчанию 85% от `LTX_VIDEO_TIMEOUT`), и сообщает выбранный формат. Если даже минимальная ступень не помещается, он останавливается с явным сообщением вместо зависания — проверьте цифры перед повтором.

### LTX-Video требует более нового драйвера

На CUDA 12.2 скрипт развёртывания выставляет `LTX_DISABLE_REQUIRE=1`, что снимает требование к образу, но не гарантирует работу видео. Если генерация видео падает на старом, но поддерживаемом драйвере — вот почему; обновите драйвер.

## Недоступные подсистемы

### Веб-поиск возвращает «Search services are temporarily unavailable»

SearXNG не запущен или недоступен:

```bash
docker ps -a --filter name=flai-searxng
docker logs flai-searxng --tail 50
curl -s "localhost:8080/search?q=test&format=json" | head -c 300
```

FLAI делает одну повторную попытку на пустом наборе результатов и только потом показывает это мягкое уведомление. Обратите внимание: некоторые движки отвечают нулём результатов, не падая, — диагностика `0 results` в логе перечисляет ответившие и не ответившие движки, что и различает эти два случая.

### Tavily отображается как недоступный во всплывающем окне профиля

Ключ принадлежит конкретному пользователю и должен быть валиден на стороне Tavily. `GET /api-keys/tavily` возвращает `status` как `ok`, `unavailable`, `exhausted`, `invalid` или `no_key`. `exhausted` означает, что месячный кредит исчерпан — поиск молча переключается на SearXNG, который бесплатен. См. [SEARCH-ru.md](SEARCH-ru.md).

### Долговременная память ничего не запоминает

```bash
grep -E "^SLM_URL" .env                 # commented out means memory is off
docker inspect --format '{{.State.Health.Status}}' flai-slm
```

Обратите внимание: `docker-compose.gpu.yml` настраивает контейнер SLM с `SLM_PORT=8765`, тогда как его healthcheck опрашивает **8766**. Если healthcheck сообщает об unhealthy — причина в этом несовпадении; сначала посмотрите собственные логи контейнера, а не ищите проблему в FLAI. См. [MEMORY-ru.md](MEMORY-ru.md).

### Поиск по документам ничего не возвращает

```bash
docker inspect --format '{{.State.Health.Status}}' flai-qdrant
```

Убедитесь, что профиль Qdrant активен и что документ действительно проиндексирован — ошибки индексации сообщаются по каждому документу в панели Документы, а не молча.

### Тип файла отклонён при загрузке

FLAI принимает PDF, DOC, DOCX, TXT, ODT, RTF, CSV, JSON и EPUB с учётом `MAX_DOCUMENT_SIZE_MB` и квоты документов пользователя. Загруженные изображения уменьшаются и конвертируются перед сохранением. См. [DOCUMENTS-ru.md](DOCUMENTS-ru.md).

## Медленная работа и расход ресурсов

### Хост исчерпывает память во время тестов

Прогон pytest создаёт новое Flask-приложение на каждый тест, поэтому за время жизни набора в нём накапливаются сотни экземпляров приложения. **Никогда не запускайте два процесса pytest одновременно** и проверяйте, что завершившийся прогон действительно вышел, прежде чем начинать следующий:

```bash
free -h
pgrep -c pytest         # must be 0 before the next run
```

Останавливайте прогон, если доступная ОЗУ падает ниже ~4 ГиБ или swap заполнен больше чем наполовину. Предпочитайте точечные прогоны (`pytest -m unit`) плюс наборы тестов, покрывающие изменённое.

### Веб-контейнер постоянно перезапускается

```bash
docker inspect --format '{{.RestartCount}} {{.State.Health.Status}}' flai-web
docker logs flai-web --tail 200
```

Цикл падений обычно означает ошибку конфигурации, а не баг в коде. Самая частая причина — некорректное значение в `.env`. `FLM_SESSION_LIFETIME_SECONDS` и подобные параметры времени жизни заданы в коде и не имеют переопределения через окружение — их установка ничего не делает.

### Запросы ощущаются медленными, но ни одна модель не загружена

Посмотрите, что делает очередь:

```bash
curl -s localhost:5000/api/queue/status | python3 -m json.tool
docker logs flai-web --tail 100 | grep -i "gpu_lock\|waiting"
```

GPU-работа сериализована по замыслу. Долгая видео- или задача генерации изображения намеренно блокирует чат, потому что VRAM безусловно очищается между каждой GPU-задачей.

## Всё ещё не работает

Соберите это перед обращением:

```bash
docker compose ps
docker logs flai-web --tail 200
nvidia-smi
curl -s localhost:5000/health | python3 -m json.tool
python3 --version && docker --version
```

Затем откройте issue на https://github.com/barval/flai с этим выводом. Для подозреваемой регрессии укажите версию из `APP_VERSION` в `app/config.py` и сначала проверьте [../CHANGELOG.md](../CHANGELOG.md).
