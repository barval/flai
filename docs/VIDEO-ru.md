# Генерация видео

FLAI поставляет **два взаимозаменяемых видеобэкенда**, выбор — переменной `VIDEO_BACKEND`:

| | **LTX** (по умолчанию) | **Wan** |
|---|---|---|
| Модель | LTX-Video 2B 0.9.8 **distilled** | Wan 2.2 **TI2V 5B Turbo** (Q4_K_M) |
| Характер | быстрый, длинные клипы | медленнее, лучше движение и детали |
| Длина клипа | до **10 с** (240 кадров) | **5 с** (121 кадр) |
| Разрешение | 768×512 ландшафт, 512×768 портрет, 512×512 квадрат | 832×480 ландшафт, 480×832 портрет, 640×640 квадрат |
| Шаги денойза | 8 | 4 (Turbo), CFG 1.0, Euler, flow-shift 3.0 |
| Измеренный пик VRAM | **~3,1 ГБ** | **15,0 ГБ** на 832×480×121 (9,0 ГБ с выгруженным энкодером) |
| Измеренное время (карта 16 ГБ) | десятки секунд | **209 с** на 5-секундный клип 480p |
| Контейнер | `flai-ltxvideo` (PyTorch, порт 7872) | `flai-sd` (stable-diffusion.cpp, порт 7861) |
| Профиль compose | `with-video` | `with-video-wan` |
| Флаг deploy | `--with-video` | `--with-video-wan` |
| Хосты только с CPU | поддерживается (авто-понижение) | **отказ** (см. ниже) |

Оба бэкенда отвечают по одному контракту — `POST /v1/video/generations` — поэтому очередь,
VRAM-гейт, видео-из-картинки и интерфейс чата общие.

Выбор делается при развёртывании; профили взаимоисключающие:

```bash
./deploy.sh --with-video      --download-models   # LTX  (по умолчанию)
./deploy.sh --with-video-wan  --download-models   # Wan  (только GPU)
```

Скрипт записывает `VIDEO_BACKEND=ltx|wan` в `.env`. Переключение позже — повторный запуск
скрипта с другим флагом либо сохранение того же ключа в **Админ-панель → Настройки**: значение
применяется без перезапуска (модуль перечитывает бэкенд, URL обёртки, модель и таймаут на каждом
запросе), а модели неактивного бэкенда остаются на диске и оба контейнера могут работать
одновременно.

## Параметры генерации

Оба бэкенда запрашивают у мультимодальной модели промпт и разрешение через
`prompts/{lang}/create_video.template`; шаблон получает собственный набор разрешений,
правило кадров и имя модели, поэтому запрос соответствует тому, на чём модель обучалась.

| Параметр | LTX | Wan |
|---|---|---|
| Ландшафт | 768×512 | 832×480 |
| Портрет | 512×768 | 480×832 |
| Квадрат | 512×512 | 640×640 |
| Кадры | 240 (10 с) или 120 (5 с) | 121 (5 с), 81 (≈3,4 с), 49 (≈2 с) |
| Частота кадров | 24 fps | 24 fps |
| Negative prompt | общий по умолчанию | общий по умолчанию |

У Wan два жёстких правила формы: число кадров обязано быть **4n+1** (его VAE сжимает время в
четыре раза), а стороны кратны **32**. Обёртка приводит любой запрос к этим значениям, а
приложение обрезает более длинный запрос до 121 кадра с видимым уведомлением («Wan
генерирует клипы до 5 секунд — видео сокращено с 10 с до 5 с»).

## LTX-Video 2B

- Дистиллированный конвейер на 8 шагов, текстовый энкодер T5-XXL (~8,9 ГБ в bf16) остаётся
  на CPU.
- Измеренный пик конвейера: **3057 МБ** — VRAM-гейт использует измеренное значение, а не
  константу.
- Исходное изображение для видео-из-картинки ужимается до **768 px** по длинной стороне;
  аспект результата следует за источником: квадрат → 512×512, широкое → 768×512,
  вертикальное → 512×768.
- Карты 8/10 ГБ ограничиваются 512×512×120; фрагментированная карта (меньше 6 ГБ свободно
  после выгрузки LLM) получает то же ограничение.
- **Хосты только с CPU:** планировщик (`plan_cpu_generation`) выбирает наибольший формат,
  который укладывается и в доступную RAM, и во временной бюджет (85 % от
  `LTX_VIDEO_TIMEOUT`, если не задан `LTX_VIDEO_CPU_TIME_BUDGET_S`). Цепочка понижения:
  768×512×240 → 384×256×120 @ 12 fps → 256×192×57 @ 6 fps → 256×192×24 @ 6 fps. Статическая
  часть — ~17,4 ГБ; формат, который не влезает, отклоняется заранее с локализованной ошибкой,
  а не обрывается по таймауту посреди генерации.

## Wan 2.2 TI2V 5B

- Turbo GGUF (Apache-2.0), 4 шага, CFG 1.0, сэмплер Euler, flow-shift 3.0.
- Работает внутри **контейнера sd.cpp** — того же, что генерирует изображения — через
  `POST /v1/video/generations`; второй стек Python/Torch не нужен.
- sd.cpp умеет писать только avi/webm, поэтому обёртка конвертирует клип в **mp4 (h264,
  yuv420p, faststart)** встроенным в образ ffmpeg.
- **Текстовый энкодер:** umt5-xxl Q8_0 (~6 ГБ). Он остаётся на GPU, если карта не меньше
  12 ГБ; ниже этого порога обёртка передаёт `--offload-to-cpu`, стримит веса из RAM и требует
  примерно на 9 ГБ меньше VRAM (ценой скорости). Порог: `WAN_OFFLOAD_BELOW_VRAM_MB`.
- **Профили VRAM** (расчётные, откалиброваны по измеренному пику):

  | Клип | Кадры | Пик VRAM (на GPU) | Пик VRAM (энкодер выгружен) |
  |---|---|---|---|
  | 832×480 | 121 (5 с) | 15,0 ГБ | 9,0 ГБ |
  | 640×384 | 121 (5 с) | 13,0 ГБ | 7,0 ГБ |
  | 512×288 | 121 (5 с) | 11,7 ГБ | 5,7 ГБ |
  | 512×288 | 49 (2 с) | 10,6 ГБ | 4,6 ГБ |
  | 1280×704 | 121 (5 с) | 21,5 ГБ | 15,5 ГБ |

  Приложение идёт по этой цепочке от запрошенного размера вниз, пока клип не влезет в
  свободную VRAM; при ошибке нехватки памяти обёртка повторяет тот же шаг вниз. Поэтому карта
  меньше 12 ГБ всё равно получает 5-секундный клип, а карте на 24 ГБ можно запросить 720p.
- **Измерено:** 832×480×121, 4 шага → **209 с** на карте 16 ГБ (207,8 с времени модели, из
  них 128 с — декод VAE), пик **15 340 МБ** общего потребления карты.
- **Хосты только с CPU по умолчанию получают отказ.** Замер на 12-ядерном CPU: 256×192×17
  занял **98 с** и ~12 ГБ RAM; 512×288×49 уже превысил лимит контейнера в 12 ГБ и уронил
  свободную память 30-гигабайтного хоста до 3,3 ГБ. Для 5-секундного клипа 480p экстраполяция
  даёт **~90 минут и заметно больше 12 ГБ RAM**. `WAN_VIDEO_ALLOW_CPU=1` разрешает попытку с
  тем же планировщиком RAM/времени, что у LTX; без него пользователь видит локализованное
  «Генерация видео Wan требует GPU».

## Общее поведение

- **VRAM-гейт перед генерацией.** Каждая видеозадача выгружает модели llama.cpp, ждёт, пока
  `llama-swap /running` не покажет ноль загруженных и не освободится расчётный объём
  (`VRAM_WAIT_TIMEOUT_S`, 120 с), и только затем генерирует. Занятая карта пережидается, а не
  считается отказом.
- **Уборка после генерации.** LTX выгружается через `POST /v1/unload`, а если его CUDA-контекст
  переживает выгрузку — контейнер перезапускается. Wan не нужно ни то, ни другое: `sd-cli` —
  одноразовый процесс, драйвер освобождает VRAM при его завершении.
- **Видео из картинки.** Исходное изображение ужимается до 768 px (LTX) или 832 px (Wan) и
  передаётся в теле запроса; обе обёртки принимают `image_data` и передают его движку
  (`-i` для sd.cpp).
- **Уведомления.** Пониженное разрешение, сокращённый клип или отказ записываются системным
  сообщением в чат, чтобы пользователь понимал, чем результат отличается от запроса.

## Конфигурация

```bash
# Выбор бэкенда (записывается deploy.sh)
VIDEO_BACKEND=ltx                  # ltx | wan

# LTX-Video (flai-ltxvideo)
LTX_VIDEO_WRAPPER_URL=http://flai-ltxvideo:7872
LTX_VIDEO_MODEL=ltxv-2b-0.9.8-distilled
LTX_VIDEO_TIMEOUT=10800            # секунды; на CPU нужно большое значение
LTX_VIDEO_CPU_TIME_BUDGET_S=0      # 0 = 85 % от LTX_VIDEO_TIMEOUT

# Wan 2.2 TI2V 5B (flai-sd)
WAN_VIDEO_URL=http://flai-sd:7861
WAN_VIDEO_MODEL=wan2.2-ti2v-5b-turbo-Q4_K_M.gguf
WAN_VIDEO_TIMEOUT=1800             # измерено 209 с на 832×480×121
WAN_VIDEO_STEPS=4
WAN_VIDEO_CFG_SCALE=1.0
WAN_VIDEO_FLOW_SHIFT=3.0
WAN_VIDEO_ALLOW_CPU=0              # 1 = попытаться запустить Wan на CPU (очень медленно)
```

Лимиты на стороне обёрток живут в контейнерах: `WAN_CLI_TIMEOUT` (1800 с, 7200 с на CPU),
`WAN_OFFLOAD_BELOW_VRAM_MB` (12000), `SD_CLI_TIMEOUT` (генерация изображений).

## Требуемые модели

**LTX:**
1. `ltxv-2b-0.9.8-distilled.safetensors` (~5,9 ГБ) — диффузионный трансформер + VAE
2. Текстовый энкодер / токенизатор `PixArt-alpha/PixArt-XL-2-1024-MS` — T5-XXL (~18 ГБ на
   диске, ~8,9 ГБ в bf16 на CPU)

**Wan:**
1. `wan2.2-ti2v-5b-turbo-Q4_K_M.gguf` (~3,4 ГБ) — Turbo-чекпойнт
2. `Wan2.2_VAE.safetensors` (~1,4 ГБ)
3. `umt5-xxl-encoder-Q8_0.gguf` (~6 ГБ) — текстовый энкодер

```bash
# Скачивание через deploy-скрипт (берёт выбранный бэкенд)
./deploy.sh --download-models --with-video
./deploy.sh --download-models --with-video-wan

# Текстовый энкодер LTX вручную:
bash services/ltx_video/download-t5-encoder.sh
```

Файлы Wan попадают в `services/sd_cpp/models/{diffusion_models,vae,text_encoders}` — те же
каталоги, что уже использует конвейер изображений, поэтому ничего дополнительно монтировать
не нужно.

## Публичный API

`POST /v1/videos` принимает `prompt`, `width`, `height`, `num_frames`, `frame_rate` и `seed`.
Значения по умолчанию и потолок длительности следуют активному бэкенду: 768×512×240 (10 с)
для LTX, 832×480×121 (5 с) для Wan. Ответ — идентификатор задачи с URL опроса; готовый клип
отдаёт `GET /v1/flai/tasks/{id}/content`.

## Диагностика

- **«Генерация видео Wan требует GPU»** — хост в режиме CPU. Используйте `--with-video` (LTX)
  или задайте `WAN_VIDEO_ALLOW_CPU=1`, ожидая ~90 минут на 5-секундный клип.
- **«Video generation requires GPU; available VRAM … is below safe threshold»** — карту держит
  другой процесс или запрошенный клип больше уровня. Цепочка понижается автоматически; если
  не влезает ничего, упростите запрос.
- **Клип короче запрошенного** — Wan ограничен 121 кадром (5 с); уведомление в чате это
  объясняет.
- **Клип ниже запрошенного разрешения** — цепочка VRAM выбрала наибольший подходящий пресет.
  Выбранный размер виден в `docker logs flai-sd` (Wan) или `docker logs flai-ltxvideo` (LTX).
